## 1 解决什么问题

之前提升推理能力的两条路：

| 做法 | 缺陷 |
|---|---|
| CoT 提示（few-shot 示例或“Let's think step by step”） | 能力受限于模型已有水平，复杂问题仍不够 |
| 后训练阶段学习人工标注的多步推理轨迹 | 依赖人工标注，难以扩展，带入标注者的认知偏差；模型只能模仿人的思路，上限被示例卡住 |

论文的问题是：能不能几乎不用人工推理轨迹，只靠 RL 和“答案对不对”的信号，让模型自己发展出推理能力。

## 2 方法

论文有两个主角：R1-Zero 回答“纯 RL 行不行”，R1 回答“怎么做成一个好用的模型”。

### 2.1 R1-Zero：基座上直接做 GRPO

不做 SFT，直接在 DeepSeek-V3-Base 上用 GRPO。v2 正文式 1 到式 3：

```
J_GRPO(θ) = E[q~P(Q), {o_i}~π_θold(O|q)]
    (1/G) Σ_i { min( (π_θ(o_i|q)/π_θold(o_i|q)) A_i , clip(π_θ(o_i|q)/π_θold(o_i|q), 1−ε, 1+ε) A_i )
                − β · D_KL[π_θ ‖ π_ref] }                                          （式 1）
D_KL[π_θ ‖ π_ref] = π_ref(o_i|q)/π_θ(o_i|q) − log( π_ref(o_i|q)/π_θ(o_i|q) ) − 1    （式 2）
A_i = (r_i − mean({r_1 … r_G})) / std({r_1 … r_G})                                  （式 3）
```

符号同 [02 DeepSeekMath](02-deepseekmath-grpo.md)。注意这里的公式按整个回答 `o_i` 书写，没有展开到 token 和 `1/|o_i|`，是 DeepSeekMath 式 3 的简写，不要和 [06 GSPO](06-gspo.md) 的序列级比率混淆（GSPO 的比率还有 `1/|y_i|` 次方的长度归一化）。

**奖励只用规则**（2.2 节，式 4）：

```
Reward_rule = Reward_acc + Reward_format       （两项等权）
```

准确性奖励：数学题要求把最终答案写在指定格式里（如方框）再用规则比对，编程题用编译器跑预设测试用例。格式奖励：要求把推理过程写在 `<think>` 和 `</think>` 之间。

不用神经奖励模型（结果或过程奖励模型都不用）的理由：大规模 RL 中神经奖励模型容易被 reward hacking；重训它要额外计算资源，并让训练流程更复杂。

**模板**（表 1）只规定结构：先在 `<think>` 里推理，再在 `<answer>` 里作答，不加任何内容上的偏好，以便观察模型自然的演化。

**R1-Zero 的超参数**（2.1 节）：

| 项 | 值 |
|---|---|
| 学习率 | 3e-6 |
| KL 系数 β | 0.001 |
| rollout 温度 | 1 |
| 每题采样数 G | 16 |
| 最大长度 | 8.2k 步前 32,768，之后 65,536 |
| 总步数 | 10,400 步，约 1.6 个 epoch |
| 每步 | 32 道题，batch 512 |
| 参考模型 | 每 400 步换成最新策略 |
| 每次 rollout | 生成 8,192 个回答，随机分成 16 个 mini-batch，只训 1 个内层 epoch |

第 2.1 节没有写 R1-Zero 的 clip 范围。第 3.2.1 节给出 R1 第一阶段 RL 的 GRPO clip 比例 ε 为 10，远大于 PPO 常用的 0.2。论文的解释是 clip 太小会截断大量 token 的梯度、伤害效果，太大又会让训练不稳。读原文时要注意这是 v2 的说法。

最大长度在 8.2k 步从 32K 放到 64K 后，性能和回答长度都出现明显跳升。

### 2.2 R1：多阶段流水线

R1-Zero 的问题：可读性差，中英文混杂；规则奖励只覆盖推理任务，写作、开放问答等能力有限。R1 的流水线（图 2）：

| 阶段 | 做法 | 产物 |
|---|---|---|
| 冷启动 SFT | 几千条“对话式、第一人称”的长 CoT 数据微调 V3-Base | Dev-1 |
| 第一阶段 RL | 推理题，规则奖励加语言一致性奖励 | Dev-2 |
| 拒绝采样 + SFT | 约 60 万条推理样本和约 20 万条非推理样本，从 V3-Base 重新微调 | Dev-3 |
| 第二阶段 RL | 推理数据用规则奖励，通用数据用奖励模型 | R1 |

**语言一致性奖励**（式 7）：CoT 中目标语言词数占总词数的比例，直接加到最终奖励上。

```
Reward_language = Num(Words_target) / Num(Words)
```

**第二阶段 RL 的奖励**（式 8 到式 10）：

```
Reward = Reward_reasoning + Reward_general + Reward_language
Reward_reasoning = Reward_rule
Reward_general   = Reward_reward_model + Reward_format
```

奖励模型分两种：有用性奖励模型用约 66,000 对偏好数据训练，只评最终总结部分，不评推理过程；安全奖励模型用约 106,000 条标注安全或不安全的回答做逐点训练，评整个回答（推理和总结）。有用性偏好对的构造：让 DeepSeek-V3 判 4 次并随机交换 A、B 位置减少位置偏差，只保留分差大于 1 的对，并让整个数据集里 chosen 和 rejected 的长度相当，减少长度偏好。

第二阶段温度降到 0.7（更高温度会让生成不连贯），共 1,700 步，通用指令数据和偏好奖励只在最后 400 步加入，因为训练更久会出现 reward hacking（附录 B.5、图 6）。

**蒸馏**：用上面约 80 万条 SFT 数据直接微调 Qwen2.5 和 Llama 系列小模型，只做 SFT，不做 RL（附录 B.4.3、表 6）。

## 3 关键实验结论

- **纯 RL 能涌现推理行为**。R1-Zero 训练中回答长度稳定增长（图 1b），出现反思、验证、尝试其他解法等行为。附录 C.2 统计了 10 个反思词（wait、mistake、however、check 等），训练后出现频率是开始时的 5 到 7 倍；“wait”在早期几乎不出现，4000 到 7000 步偶尔出现，8000 步后明显激增。表 2 是著名的“aha moment”示例。
- **GRPO 与 PPO 的对比**（附录 A.3、图 4）。在 16B MoE 模型的 MATH 任务上，PPO 对 GAE 的 λ 很敏感：用开源实现常见的默认值 0.95 时明显不如 GRPO，调到 1.0 后接近 GRPO。论文因此认为 GRPO 在资源受限的大规模训练里更实用。
- **为什么 critic 在长 CoT 里更难训**（附录 A.3）。长推理里模型会反思和修改，前面写的内容可能被后面推翻，从部分回答预测最终奖励更不可行。
- **为什么 KL 不放进奖励**（附录 A.3）。PPO 把逐 token KL 当稠密奖励，RL 最大化累计奖励，等于惩罚累计 KL，会隐式惩罚回答长度、阻止长度增长。
- **clip 范围很关键**（3.2.1 节）。太小会截断大量 token 的梯度，性能下降；太大训练不稳。
- **语言一致性奖励的代价**（附录 B.6）。不加时语言一致性随训练逐步变差；加上后保持稳定，数学持平，代码略降。论文为了可读性接受了这个代价。
- **奖励模型会被 hack**（附录 B.5、图 6）。用有用性奖励模型训练时，奖励上升而 CodeForces 表现下降。
- **蒸馏优于小模型直接 RL**（附录 F.1）。在 Qwen2.5-32B-Base 上做超过 1 万步的大规模 RL，效果只和 QwQ-32B-Preview 相当，而从 R1 蒸馏的 32B 模型全面更好。论文结论：小模型靠大规模 RL 要很多算力，可能还不如蒸馏；但要突破上限仍需要更强的基座和更大规模的 RL。
- **基座规模决定纯 RL 是否有效**（附录 G.1）。早期在 7B dense 和 16B MoE 上做 RL，AIME 上一直没有实质提升，回答变长后出现重复，用不好长 CoT；换到 32B、230B、671B 后才看到纯 RL 的明显收益。

## 4 局限与后续工作

论文第 6 节列出的局限：结构化输出不如已有模型，也不能使用搜索引擎、计算器等工具；简单问题上仍有过度思考；主要优化中英文，其他语言的问题可能用英文推理和回答；对提示敏感，few-shot 会降低效果；软件工程任务评测耗时长，没有大规模做 RL。更根本的是，纯 RL 方法依赖可靠的奖励。写作等任务难以构造可靠的奖励，模型奖励会被利用，这类任务上扩展纯 RL 仍是开放问题。

附录 G.2 的失败尝试：

- **过程奖励模型**：通用推理里“一步”难定义；中间步骤对错难判断；引入模型 PRM 必然带来 reward hacking 和额外训练成本。
- **MCTS**：token 生成的搜索空间比棋类大得多，限制节点扩展又会陷入局部最优；细粒度价值模型难训，难以像 AlphaGo 那样迭代提升。

## 5 面试常见追问

1. R1-Zero 和 R1 有什么区别？→ R1-Zero 不做 SFT，基座直接 GRPO，奖励只有准确性和格式两条规则，用来验证纯 RL 能否涌现推理；R1 加了冷启动 SFT、语言一致性奖励、拒绝采样后的大规模 SFT 和带奖励模型的第二阶段 RL，解决可读性、语言混杂和通用能力问题。
2. 为什么推理任务不用神经奖励模型？→ 论文的理由：大规模 RL 里神经奖励模型容易被 hack；重训它需要额外资源，让流程更复杂。规则奖励在数学、代码上可以直接验证对错。附录 B.5 也给了有用性奖励模型被 hack 的实例，所以偏好奖励只在第二阶段最后 400 步使用。
3. “aha moment”说明了什么？要注意什么？→ 说明没有显式教，RL 也能让模型学会反思这类策略，并且某些反思模式在训练的特定阶段才出现。要注意论文自己在冷启动一节也提醒：R1 生动的第一人称推理风格主要是工程设计的启发式结果，不代表模型获得了类人智能；反思词频率是统计量，不等于每次反思都有效。
4. 为什么要冷启动数据？→ R1-Zero 可读性差、中英混杂。冷启动用几千条对话式第一人称长 CoT 先做 SFT，主要出于用户体验，同时给 RL 一个更好的起点。
5. 小模型怎么获得推理能力？→ 论文的结论是蒸馏：用 R1 产出的约 80 万条数据做 SFT，比在同规模基座上做大规模 RL 更好、更省；在 7B、16B 上直接纯 RL 甚至没看到实质提升。
6. PPO 在这里真的不如 GRPO 吗？→ 附录 A.3：PPO 对 GAE λ 敏感，默认 0.95 时差很多，调到 1.0 后接近 GRPO。所以差距主要在调参成本和价值模型的开销，不是 PPO 原理上做不到。Search-R1 也是用 λ = 1 的 PPO。
