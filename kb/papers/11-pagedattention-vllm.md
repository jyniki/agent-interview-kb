# 11 PagedAttention 与 vLLM：分页管理 KV Cache

> 论文：Efficient Memory Management for Large Language Model Serving with PagedAttention

> 相关章节：[inference/01 KV Cache 与显存估算](../tracks/inference/01-kv-cache-memory/README.md#5-pagedattention)、[inference/02 批处理与 PD 分离](../tracks/inference/02-batching-pd/README.md)、[inference/05 Agent 服务](../tracks/inference/05-agent-serving/README.md)

## 1 解决什么问题

**服务吞吐受显存限制**。Decode 阶段每步只处理一个 token，是访存受限的，要提高吞吐就要把更多请求放进一个 batch。论文图 1 的例子：A100 40GB 上服务 13B 模型，约 65% 显存是权重，近 30% 是 KV Cache，剩下少量给激活。能放多少请求，基本由 KV Cache 的显存决定。

KV Cache 很大，论文的算例（第 3 节）：OPT-13B 每个 token 的 KV 要

```
2（K 和 V） × 5120（隐藏维度） × 40（层数） × 2（FP16 字节） = 800 KB
```

一个 2048 token 的请求最多要 1.6 GB。论文还指出 GPU 算力增长快于显存容量（A100 到 H100 FLOPS 翻倍以上，显存仍最多 80GB），显存会越来越成为瓶颈。

**已有系统的做法和浪费**（3.1 节、图 3）。当时的系统（FasterTransformer、Orca）把一个请求的 KV Cache 存成连续张量，因为深度学习框架的大多数算子要求连续内存。输出长度事先未知，就按请求的最大可能长度预分配一整块。这带来三种浪费：

| 浪费 | 含义 |
|---|---|
| 预留（reserved） | 为将来的 token 预留、暂时没用的空间。最终会用上，但整个请求期间都占着，别的请求用不了 |
| 内部碎片（internal fragmentation） | 按最大长度分配，实际生成得短，多出来的永远用不上 |
| 外部碎片（external fragmentation） | 每个请求预分配的大小不同，分配器在块之间留下的空隙 |

论文的测量（图 2）：已有系统里真正存放 token 状态的 KV 显存只占 20.4% 到 38.2%。压缩整理（compaction）在 KV Cache 这么大的情况下不现实，而且预分配的连续块也无法在请求之间共享。

**无法共享**。并行采样、束搜索这类解码算法，一个请求会有多条序列，它们可以共享一部分 KV Cache（例如 prompt 部分），但连续存储的设计做不到。

## 2 方法

### 2.1 思路：操作系统的虚拟内存分页

| 操作系统 | vLLM |
|---|---|
| 页 | KV 块（block），固定存 B 个 token 的 K 和 V |
| 字节 | token |
| 进程 | 请求（序列） |
| 页表 | 块表（block table），记录逻辑块到物理块的映射和每块已填的 token 数 |

逻辑上连续的 KV 块在物理显存里不需要连续。这样做的效果：块小并按需分配，内部碎片只剩最后一个块；所有块大小相同，没有外部碎片；可以按块共享。

### 2.2 PagedAttention 计算（4.1 节，式 4）

把第 j 个 KV 块记为 `K_j = (k_{(j−1)B+1}, …, k_{jB})`、`V_j` 同理，B 为块大小。第 i 个 token 的注意力按块计算：

```
A_ij = exp(q_i^T K_j / √d) / Σ_{t=1..⌈i/B⌉} exp(q_i^T K_t 1 / √d)
o_i  = Σ_{j=1..⌈i/B⌉} V_j A_ij^T
```

`A_ij` 是第 i 个 query 对第 j 个块的注意力分数行向量。kernel 按块表分别找到并读取各个块。数学上和普通注意力等价，只是数据的存放和读取方式变了。

### 2.3 KV Cache 管理（4.2、4.3 节，图 6、图 7）

- GPU worker 上的显存被切成物理块；块表管理每个请求的逻辑块到物理块的映射。
- Prefill 时按 prompt 长度分配刚好够的块；Decode 时最后一个块写满才分配新块。
- 请求结束后块立即释放给其他请求。
- 浪费只剩每个序列最后一个没写满的块。

### 2.4 解码算法里的共享（4.4 节）

| 场景 | 共享方式 |
|---|---|
| 并行采样（图 8） | 同一 prompt 的多个采样共享 prompt 的物理块。每个物理块有引用计数；要往引用计数大于 1 的块里写时，先复制一份（写时复制，copy-on-write） |
| 束搜索（图 9） | 不同候选不仅共享 prompt，还共享各自的公共前缀，共享关系随解码动态变化。被淘汰的候选释放逻辑块，引用计数归零的物理块被回收 |
| 共享前缀（图 10） | 例如很多请求共用同一段指令和 few-shot 示例。服务方预先为这些前缀保留物理块，用户请求把逻辑块映射过去（最后一块标记为写时复制），Prefill 只需要算用户自己的输入 |
| 混合解码 | 模型和 kernel 只看到每个序列的物理块 ID 列表，不需要处理共享模式，所以不同解码方式的请求可以放在同一个 batch 里 |

### 2.5 调度与抢占（4.5 节）

- 调度策略为先到先服务（FCFS）；需要抢占时，最晚到的请求最先被抢占。
- **全有或全无**的驱逐：一个序列的所有块要么一起驱逐，要么都不动，因为处理一个请求需要它全部的 token 状态。同一请求的多条序列（如束搜索候选）作为序列组一起调度。
- 被驱逐的块怎么恢复，有两种方式：
  - **换出（swapping）**：拷到 CPU 内存，由 CPU 块分配器管理。抢占后暂停接收新请求，直到被抢占的序列完成。换出的块数不超过 GPU 上的总块数，所以 CPU 交换空间有上界。
  - **重算（recomputation）**：重新调度时重新计算 KV。因为已生成的 token 可以和原 prompt 拼成新 prompt，一次 Prefill 就能算完，比原始的逐步生成快。

### 2.6 分布式执行（4.6 节）

支持 Megatron-LM 式张量并行，SPMD 方式执行。各 GPU worker 处理不同的注意力头，但共享同一套块表，由中心调度器统一管理。

### 2.7 实现（第 5 节）

Python 约 8.5K 行、C++/CUDA 约 2K 行。为分页访存写了三个融合 kernel：融合 reshape 和块写入；融合块读取和注意力计算；融合写时复制产生的批量块拷贝。

## 3 关键实验结论

以下数字都是论文报告。对比对象是 FasterTransformer 和 Orca。Orca 闭源，论文自己实现了三个版本：Oracle（假设预先知道真实输出长度）、Pow2（按真实长度向上取 2 的幂，最多多分配 2 倍）、Max（按最大长度分配）。

- **整体吞吐**：在相同延迟水平下，吞吐是已有系统的 2 到 4 倍；序列越长、模型越大、解码算法越复杂，优势越明显（摘要、第 1 节）。
- **基本采样**（6.2 节、图 12、图 13）：ShareGPT 数据集上，vLLM 能承受的请求率是 Orca (Oracle) 的 1.7 到 2.7 倍、Orca (Max) 的 2.7 到 8 倍；相比 FasterTransformer 最多 22 倍。原因是同时能放进 batch 的请求更多，例如 OPT-13B 上同时处理的请求数是 Orca (Oracle) 的 2.2 倍。Alpaca 数据集序列短，在 OPT-175B 这种 KV 空间充裕的配置下优势变小。
- **并行采样和束搜索**（6.3 节、图 14、图 15）：采样数越多、束越宽，优势越大。共享节省的块比例，Alpaca 上并行采样为 6.1% 到 9.8%，束搜索为 37.6% 到 55.2%；ShareGPT 上分别为 16.2% 到 30.5% 和 44.3% 到 66.3%。
- **共享前缀**（6.4 节、图 16）：LLaMA-13B 做英译德，共享 1 个示例的前缀（80 token）时吞吐是 Orca (Oracle) 的 1.67 倍，共享 5 个示例的前缀（341 token）时为 3.58 倍。
- **聊天场景**（6.5 节、图 17）：把对话历史和最新问题拼成 prompt（截到最后 1024 token），能承受的请求率是三个 Orca 版本的 2 倍。注意论文没有在轮次之间保留 KV Cache，每轮都重新 Prefill。

消融（第 7 节）：

- **kernel 开销**（7.1 节、图 18a）：按块表间接寻址等带来的额外开销，让注意力 kernel 延迟比高度优化的 FasterTransformer 高 20% 到 26%。论文认为开销小，因为只影响注意力算子，端到端仍大幅领先。
- **块大小**（7.2 节、图 18b）：块太小不能充分利用 GPU 并行读写 KV；块太大内部碎片多、共享概率低。ShareGPT 上 16 到 128 都表现最好；Alpaca 上 16 和 32 好，更大的块因为序列比块还短而明显变差。默认块大小为 16。
- **换出与重算**（7.3 节、图 19）：块小时换出开销大，因为大量小数据传输用不满 PCIe 带宽；重算开销和块大小无关。块小时重算更好，块大时换出更好，但重算开销从不超过换出延迟的 20%；块大小 16 到 64 时两者端到端相当。

## 4 局限与后续工作

论文第 8 节自己说明的适用范围：

- 分页的好处来自两个前提：内存需求动态变化（输出长度事先未知），并且性能受显存容量限制。不是所有 GPU 负载都满足。训练时张量形状通常是静态的，可以提前优化分配；非 LLM 的 DNN 服务通常是计算受限，提高显存效率不一定带来性能提升。这些场景用 vLLM 的技术反而可能因为间接寻址和非连续内存变慢。
- 和 Orca 的关系：迭代级调度和 PagedAttention 是互补的。Orca 通过调度让更多请求交错执行，vLLM 通过提高显存利用率让更多请求放得下；细粒度调度反而让显存管理更难，所以 vLLM 的技术更重要。

从论文内容可以看到的边界：

- 不减少每个 token 的 KV 大小。要让 KV 变小，要靠 GQA、MLA 这类结构改动或 KV 量化，见 [inference/01 第 4 节](../tracks/inference/01-kv-cache-memory/README.md#4-mqa--gqa--mla-对-kv-的影响) 和 [inference/04 第 7 节](../tracks/inference/04-quantization/README.md#7-kv-cache-量化)。
- attention kernel 都要适配分页布局，有一定开销。
- 调度只用 FCFS，没有讨论 SLO 或优先级。

后续发展：

- Prefill 和 Decode 互相干扰的问题，由分块 Prefill 和 PD 分离处理，见 [inference/02](../tracks/inference/02-batching-pd/README.md)。
- 共享前缀在 Agent 场景尤其重要：系统提示、工具定义和历史轮次在每一轮都重复，见 [inference/05 Agent 服务](../tracks/inference/05-agent-serving/README.md)。
- RL 训练的 rollout 大多用 vLLM 这类推理引擎生成，见 [training/07 RL 训练框架](../tracks/training/07-training-systems/README.md)。

## 5 面试常见追问

1. PagedAttention 解决的是哪几种浪费？→ 按最大长度连续预分配带来的预留、内部碎片和外部碎片；另外解决了无法共享的问题。论文测得旧系统里有效 KV 只占 20.4% 到 38.2%。分页后浪费只剩每个序列最后一个块。
2. PagedAttention 会减少每个 token 的 KV 大小吗？→ 不会。它只省分配和碎片带来的浪费，并支持共享。KV 本身的大小由层数、KV 头数、头维度和精度决定，要靠 GQA、MLA、KV 量化来减小。
3. 写时复制怎么工作？→ 每个物理块有引用计数。多个序列共享一个块时引用计数大于 1；某个序列要往这个块写新 token 时，先分配新块、拷贝内容、更新自己的块表并把原块引用计数减 1，再写入。引用计数为 1 时直接写。
4. 块大小怎么选？→ 块小，尾部浪费少，但 kernel 读写不能充分并行、块表更长；块大，读取效率高，但内部碎片多、共享粒度粗。论文实验 16 到 128 在长序列数据上最好，短序列上大块明显变差，默认 16。
5. 显存不够时怎么办？→ 抢占最晚到的请求，整组驱逐它的块。恢复方式有换出到 CPU 和重算两种：块小时换出受 PCIe 小传输拖累，重算更好；块大时换出更好。重算之所以快，是因为已生成 token 可以和 prompt 拼起来一次 Prefill。
6. 和连续批处理（Orca）是什么关系？→ 互补。连续批处理解决“什么时候让请求进出 batch”，PagedAttention 解决“batch 里能放下多少请求”。前者让 batch 成员频繁变化，显存管理更难，更需要后者。
