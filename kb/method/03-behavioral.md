# 行为题

> 面试方法 · 阅读材料 · 约 30 分钟 · 返回 [索引](README.md)

## 1 这一篇解决什么问题

行为题问的是“你过去怎么做的”，用来预测你以后会怎么做。常见于主管面和 HR 面，技术面结尾也常问一两道。

技术候选人常犯的错：

- 讲观点，不讲事例，比如“我觉得沟通很重要”；
- 事例太长，讲了五分钟背景，没讲自己做了什么；
- 每道题临场想，结果同一个故事讲了三遍；
- 为了显得完美，编一个不存在的经历。

读完你应该能：用 STAR 结构讲一个两分钟的故事；准备一个覆盖常见题的故事库；知道哪些地方不能编。

## 2 STAR 结构

| 段 | 讲什么 | 占比 | 常见错误 |
|---|---|---|---|
| S 情境 | 时间、团队、背景，一两句 | 10% | 背景讲太多 |
| T 任务 | 你要解决什么，难在哪 | 10% | 没说清难点，听起来很平常 |
| A 行动 | **你**做了什么，为什么这样做 | 60% | 说“我们”，或只说结果不说过程 |
| R 结果 | 结果怎样，学到什么 | 20% | 没有结果，或只有好结果不提代价 |

重点在 A。面试官要的是你的判断过程：当时有哪些选项，你为什么选这个。

R 里加一句反思，比只说成功更有说服力。例如“如果重来，我会更早找某某对齐”。

整个故事控制在 2 分钟左右。面试官想听细节会追问。

## 3 Agent 岗常见的行为题

| 类型 | 典型问法 | 在看什么 |
|---|---|---|
| 冲突 | “和同事在技术方案上有过分歧吗？怎么处理的？” | 能不能用证据说服人，不能说服时怎么办 |
| 失败 | “讲一次失败的经历。” | 能否承认问题、找到原因、做出改变 |
| 推动没有权限的事 | “有没有推动过不归你管的事？” | 影响力，怎么让别人愿意配合 |
| 技术判断被否决 | “你的方案被否了，后来怎样？” | 能否接受决定并继续做好，是否复盘了谁对 |
| 在不确定中做决定 | “信息不全时怎么做技术决定？” | 怎么控制风险，怎么留退路 |
| 学新东西 | “最近学的一项新技术，怎么学的？” | 学习方法，对领域变化的跟进 |

Agent 领域变化快，“在不确定中做决定”和“学新东西”被问到的频率比传统后端岗位高。准备时多留一个这类故事。

## 4 两个示例

以下为虚构示例。人物、公司、项目都是编的，沿用 [02](02-project-pitch.md) 里的虚构 IT 工单助手项目。

### 4.1 技术判断被否决

> **S**：在青石软件做 IT 工单助手时，团队要决定工具调用失败后怎么处理。
>
> **T**：我主张失败就直接转人工；组长主张让 Agent 自己重试并换工具，理由是转人工太多会拉低关单率。
>
> **A**：我没有继续争论，而是提议用数据定。我从灰度日志里挑了 50 条工具失败的轨迹，按两种策略各回放一遍，人工看结果。结果是：只读工具失败时，自动重试大多能恢复；写操作工具失败时，自动重试有几次造成了重复提交。我把这个结果写成一页文档发给组长。
>
> **R**：最后定的是折中：只读工具自动重试，写操作失败直接转人工。我原来的方案被部分否了，但我接受，因为数据支持组长在只读场景的判断。我学到的是，分歧时先找能验证的小实验，比各自讲道理快。

这个故事同时覆盖“冲突”和“被否决”两个标签。

### 4.2 在不确定中做决定

> **S**：上线前两周，模型供应商通知要调整我们在用的模型版本。
>
> **T**：我们来不及完整重跑评测，但上线日期已经和 IT 部门定了。
>
> **A**：我先列出哪些能力变化风险最大：工具选择和结构化输出。只针对这两项，从评测集里抽了 80 条最关键的用例，新旧版本各跑三次。工具选择没有明显变化，有一类 JSON 输出偶尔缺字段。我加了一层输出校验，缺字段就重试一次，再失败转人工。同时和组长约定：上线第一周每天抽查 20 条轨迹，发现问题就回滚到旧版本。
>
> **R**：按时上线，第一周抽查没发现严重问题。代价是那层校验增加了一点延迟。反思是我们缺一套“模型换版本时的快速回归集”，后来我把这 80 条整理成了固定的回归集。

这个故事覆盖“不确定中决策”“风险控制”“主动补流程”三个标签。

## 5 故事库怎么准备

不要每道题准备一个故事。准备 5 到 7 个，每个覆盖多个标签。

| 故事 | 冲突 | 失败 | 推动无权限的事 | 被否决 | 不确定 | 学新东西 |
|---|---|---|---|---|---|---|
| 4.1 失败处理方案之争 | ✓ | | | ✓ | | |
| 4.2 模型临时换版本 | | | | | ✓ | |
| 你的故事 3 | | | | | | |
| 你的故事 4 | | | | | | |
| 你的故事 5 | | | | | | |

准备步骤：

1. 列出过去两三年里你印象深的 10 件事，不管大小。
2. 每件事按 STAR 写四五行，重点写 A。
3. 填进上表，看每个标签有没有至少两个故事。
4. 删掉只能覆盖一个标签、又不够有说服力的故事。
5. 每个故事讲出声三遍，录音听一遍，压到 2 分钟。

同一场面试里，一个故事最多用两次，而且要讲不同侧面。

## 6 不要编造经历

行为题最容易被追问细节：“当时那个同事具体说了什么？”“你用的是哪份数据？”“后来他怎么看这件事？”编出来的故事接不住两层。

| 可以做 | 不可以做 |
|---|---|
| 选你真实经历中最能说明问题的一件 | 编一件没发生过的事 |
| 小事讲清楚，比如一次代码评审的分歧 | 把别人做的事说成自己做的 |
| 承认结果一般，讲清学到了什么 | 改写结果，把失败说成成功 |
| 隐去公司名和未公开的业务细节 | 编造数字让故事更好看 |
| 没有对应经历时直接说，再讲你会怎么做 | 硬套一个不相关的故事 |

经历少的同学（比如应届生），课程项目、实习、开源贡献、比赛里的事都可以用。规模小没关系，判断过程讲清楚就行。

学习教练 skill 同样遵守这条：它不会替你编项目经历或数字，见 [SKILL.md](../../skills/interview-coach/SKILL.md) 第 5 条。

## 7 自测清单

- [ ] 说出 STAR 四段各占多少比例，哪段最重要
- [ ] 第 3 节表格的每类题，都有至少一个自己的真实故事
- [ ] 故事库表格每列至少两个勾
- [ ] 每个故事讲出声控制在 2 分钟左右
- [ ] 每个故事被追问三层细节都答得上
- [ ] 故事库存在本地，不在仓库里
