# 怎么讲自己的 Agent 项目

> 面试方法 · 阅读材料 · 约 40 分钟 · 返回 [索引](README.md)

## 1 这一篇解决什么问题

项目环节通常占一面、二面的一半时间。面试官想知道：这个项目难在哪，你做了哪部分，结果怎么证明，你从中学到了什么。

常见问题有四个：

- 讲成功能列表，听不出难点；
- 数字说得出，口径说不出；
- “我们做了”和“我做了”混着说；
- 被问到缺陷时回避，或者把缺陷说成优点。

本篇全程用一个虚构项目演示。你要做的是换成自己的项目，按同样的结构写一遍稿。

## 2 示例项目

以下为虚构示例。公司、团队、数字都是编的，只用来演示结构。

> 虚构公司“青石软件”，约 2000 名员工。内部 IT 服务台每天收到几百张工单：重置密码、申请软件、VPN 连不上、权限开通。项目是做一个 IT 工单助手 Agent：员工在聊天工具里描述问题，助手查知识库、调用 IT 系统的接口，能处理的直接处理，处理不了的整理好信息转人工。
>
> 候选人“小林”是团队三人之一，负责工具层和评测；另一位同事负责检索，组长负责整体架构和上线协调。

## 3 2 分钟版

开场或面试官说“简单介绍一下项目”时用。目标是让对方选出想追问的点。

| 段 | 讲什么 | 时长 |
|---|---|---|
| 1 背景与问题 | 谁在用、原来怎么做、痛点是什么 | 20 秒 |
| 2 方案 | 一句话架构，突出一个关键设计决定 | 30 秒 |
| 3 我的部分 | 明确说自己负责哪块 | 20 秒 |
| 4 结果 | 一两个数字，带口径 | 20 秒 |
| 5 难点或遗留问题 | 一个，留作追问入口 | 20 秒 |

以下为虚构示例：

> 这是一个内部 IT 工单助手。原来所有工单都靠人工分派，简单的密码重置也要排队半天。
>
> 我们做的是一个路由加 Agent 的结构：密码重置这类固定流程直接走 Workflow，描述不清的问题才进 Agent，让它查知识库、调接口排查。写操作，比如开权限，必须员工本人二次确认。
>
> 我负责工具层和评测：把六个 IT 系统接口包成工具，设计权限校验，搭了离线评测集。
>
> 上线三个月，在灰度的两个部门里，助手独立关单的比例是三成左右，口径是“工单关闭且七天内没有重开”。
>
> 现在最大的问题是多轮对话里助手会重复问员工已经说过的信息，我们还没完全解决。

最后一句是有意留的入口。面试官多半会顺着问，你就能讲准备好的内容。

## 4 10 分钟版

面试官说“详细讲讲”时用。按下表展开，每段之间停一下，看对方要不要追问。

| 段 | 讲什么 | 时长 | 示例项目里讲什么 |
|---|---|---|---|
| 1 背景 | 用户、规模、原流程、为什么要做 | 1 分钟 | 工单量、人工分派的等待时间、哪几类工单最多 |
| 2 约束 | 错误代价、延迟、权限、已有系统 | 1 分钟 | 开错权限是安全事故；接口是现有 IT 系统，不能直连数据库 |
| 3 方案演进 | 从最简单的版本讲起，每次加复杂度的理由 | 2 分钟 | V0 只做知识库问答；V1 加只读工具；V2 加写操作和二次确认 |
| 4 我负责的模块 | 设计、难点、你的取舍 | 3 分钟 | 工具描述怎么写、权限怎么校验、工具失败怎么降级 |
| 5 评测与结果 | 怎么评、数字和口径 | 1.5 分钟 | 离线评测集怎么建、灰度看什么指标 |
| 6 问题与反思 | 没做好的地方、下次怎么做 | 1.5 分钟 | 重复提问的问题；评测集早期覆盖不够 |

第 3 段的讲法和系统设计题一样，从最简单的方案开始。参考 [core/13 第 3.3 节](../core/13-system-design/README.md)。

第 4 段占时间最多。面试官要判断你的深度，主要看这里。

## 5 数字要能说出口径和来源

每个数字准备三个问题的答案：

| 问题 | 虚构示例的回答 |
|---|---|
| 分子分母是什么 | 分母是灰度部门提交的全部工单；分子是助手处理后关闭、七天内没重开的 |
| 和什么比 | 和同部门上线前一个月的人工首次解决比例比 |
| 数据从哪来 | 工单系统的状态记录，按周导出；不是用户问卷 |

常见的坑：

- 只说“提升了 30%”，说不清是绝对值还是相对值。
- 离线评测集上的数字当成线上效果讲。两者要分开说。
- 数字太精确，比如“提升了 31.47%”，反而让人怀疑。保留到合理精度。
- 记不清的数字不要临场编。说“大约”，或者说“具体数我回去确认”。

如果数字涉及前公司的未公开数据，可以只说相对变化和口径，不说绝对量。这也是在展示你守规矩。

## 6 个人贡献的边界

面试官会反复确认哪些是你做的。说清楚比说大好。

| 情况 | 说法（以下为虚构示例） |
|---|---|
| 完全自己做 | “工具层的权限校验是我设计和实现的。” |
| 主导、别人参与 | “评测集的标注规范是我定的，标注是我和两位同事一起做的。” |
| 参与讨论、别人决定 | “路由加 Agent 的架构是组长定的，我在评审里提过另一个方案，后面可以讲。” |
| 别人做的、你了解 | “检索部分是同事负责的，我知道大致做法，细节可能说不准。” |

一个检验方法：面试官问到任何一个模块，你都能马上说出它属于上表哪一行。

“我们”和“我”混用，面试官会默认是“我们”，你的贡献会被低估。说成“我”但追问接不住，会被判为夸大。

## 7 被问到没做好的地方

面试官问“项目里有什么做得不好的”，是在看你能不能客观评估自己的工作。

回答结构：问题是什么 → 为什么会这样 → 现在怎么处理或下次怎么做。

以下为虚构示例：

> 评测集早期只有 200 条，全是从历史工单里抽的单轮问题。上线后发现多轮场景的问题多，比如重复提问，评测集根本测不到。原因是我们建集时按工单类型分层抽样，没按对话轮数分层。后来补了一批从灰度日志里挑的多轮对话。如果重做，我会在建集时就把轮数作为一个分层维度。

不要做的：

- “没什么做得不好的。”
- 把优点包装成缺点，比如“我太追求完美”。
- 把问题都推给别人或资源不足。
- 说一个你根本没打算改的问题。

## 8 常见项目追问清单

准备时逐条写出自己项目的答案。答不上的，就是要补的地方。

| 追问 | 在看什么 |
|---|---|
| 为什么用 Agent，不用固定流程 | 有没有想过更简单的方案 |
| 最难的一个问题是什么，怎么解决的 | 深度，以及是不是你解决的 |
| 这个数字怎么算的 | 口径意识 |
| 离线评测和线上效果一致吗 | 有没有发现过两者的差距 |
| 模型选型怎么定的，换过模型吗 | 有没有对比依据 |
| 工具调用失败了怎么办 | 失败处理是否设计过 |
| 怎么防止 Agent 做危险操作 | 权限和安全意识，参考 [core/10](../core/10-safety-reliability/README.md) |
| 成本多少，怎么降 | 有没有成本意识 |
| 出过最严重的一次问题是什么 | 线上经验，排查方法 |
| 如果重做，你会改什么 | 反思能力 |
| 你个人最大的贡献是什么 | 贡献边界 |
| 这个项目还能怎么扩展 | 对问题空间的理解 |

## 9 自测清单

- [ ] 写出自己项目的 2 分钟稿，录音，检查是否在 2 分钟内讲完
- [ ] 稿里每个数字都能说出分子、分母、对比基线和数据来源
- [ ] 项目的每个模块都能归到第 6 节表格的某一行
- [ ] 准备好一个“没做好的地方”，按“问题 → 原因 → 改进”讲
- [ ] 第 8 节清单每一条都写了答案
- [ ] 稿子和答案存在本地，没有放进仓库
