# 题目：Agent Loop 与 Harness 的边界

> 对应知识章：[README.md](README.md)。先闭卷作答，再看答案。

## harness-loop-001 Agent Loop 和 Harness 的边界在哪
- level: 2
- tags: [harness, core]

**一句话答案**：Loop 只管“调模型 → 执行工具 → 写回”这件事本身；Harness 管 Loop 外面的预算、终止、权限、上下文、日志、恢复和校验，也就是模型能看到什么、能做什么、做到哪停、出事怎么接着做。

**要点**：
- 最小 Loop 十来行就能写完，缺的是预算、错误写回、权限、上下文控制、持久化、取消和完成判定。
- Loop 的逻辑对谁都一样，适合交给成熟 SDK；Harness 的规则和业务绑定，大部分要自己定。
- 用了 SDK 之后，约束只能从外面加：工具白名单、hooks、权限回调、上下文装配、结果校验。

**追问链**：
1. 工具报错了，是 Loop 的事还是 Harness 的事？→ 把错误写回上下文是 Loop 的事；决定重试几次、要不要换工具、要不要终止是 Harness 的事。
2. 为什么不把业务校验写进 Loop 里？→ 换 SDK 就要重写一遍，而且校验逻辑没法单独测试。放在 Loop 外，作为独立模块。
3. 模型变强以后 Harness 会变薄吗？→ 不一定。每个组件都编码了一个“模型做不到什么”的假设，要逐个去掉做对比；有的组件可以删，也可能有新组件变得可行。

**易错点**：
- 把 Harness 说成 prompt 模板。模板只是上下文装配的一部分。
- 说“用了框架就不用管 Harness”。框架给的是循环，完成标准和审批策略仍然要自己做。

## harness-loop-002 Task、Turn、Step 怎么区分，预算应该设在哪一层
- level: 2
- tags: [harness]

**一句话答案**：Task 是一个有完成标准的用户目标，Turn 是用户一条消息到系统一次回复，Step 是一次“调模型 → 执行 → 写回”；预算至少在 Task 和 Step 两层同时设。

**要点**：
- 每层失败的处理不同：Step 失败就重试或换工具；Turn 超时先给部分结果；Task 超预算就停下来问用户，或者交付已有结论。
- 只按 Turn 设预算，用户多追问几轮，Task 总花费就没有上限；只按 Step 设，又拦不住总量。
- 日志按 Step 记，带上 Task ID 和 Turn ID，回放时才能从中间某一步开始。

**追问链**：
1. SDK 里的 `max_turns` 是哪一层？→ 要看文档。OpenAI Agents SDK 按 LLM 调用次数计；Claude Agent SDK 的一个 turn 是模型输出一次加执行其中的工具调用。两者都更接近 Step。
2. 一个 Task 跨了多个 Session 怎么连起来？→ 用 Task ID 关联持久化的工作状态和进度记录，不靠上一个 Session 的上下文。
3. 用户在 Task 进行中发了新消息？→ 先判断是补充约束还是新目标。补充约束并入当前 Task；新目标就新开 Task，或者先问是否取消当前的。

**易错点**：
- 认为一个 Turn 就是一次模型调用。Agent 场景下一个 Turn 通常包含多次调用。

## harness-loop-003 Agent 什么时候该停，为什么不能只靠模型说“完成”
- level: 2
- tags: [harness, evaluation]

**一句话答案**：设一组彼此独立的终止条件：最终答案且校验通过、步数、token 或金额、墙钟时间、循环检测、连续被拒、用户取消，任一触发就停；模型判断完成只依据它自己的上下文，会误判。

**要点**：
- “独立”指每个条件由不同信息源判断：计数和计时在服务端，取消来自用户。不能让模型自己报告用了几步。
- 上限按评测集上正常任务的步数和 token 分布定，放在分布尾部之外；换模型、换工具后重测。
- 终止时返回已完成部分、当前进度和停下的原因，不能返回空。
- 完成标准写成可检查的清单，由系统或独立评分器判定。

**追问链**：
1. 模型为什么会误判完成？→ 它看不到上下文之外的事实。Anthropic 的长任务实验里，模型只跑了单元测试或 `curl` 就把功能标成完成，端到端其实不通。
2. 要不要把剩余预算告诉模型？→ 有助于收尾，但也可能让它提前交差。有的模型接近它以为的上下文上限时会提前收工。要用评测比较。
3. 循环检测怎么做？→ 先用确定的规则：同一工具加规范化参数的哈希重复、同一工具调用次数超限、连续多步没有新信息进入上下文。再考虑近似匹配。

**易错点**：
- 只设步数上限。一个工具返回超长内容，几步就能打满 token，步数上限还没到。
- 把终止当成失败。按预算截断并返回进度是一种正常结果。

## harness-loop-004 设了金额预算，为什么实际花费还会超
- level: 3
- tags: [harness, inference]

**一句话答案**：花费通常在模型响应返回后才能算出来，触发上限的那次调用已经发出并会完整计费；并行的子 Agent 也可能在停止前继续花钱。所以上限要留余量，或者调用前按最大输出预估。

**要点**：
- Claude Agent SDK 文档写明：花费在每次响应返回后比较，触发上限的响应仍会完成并计入，正在运行的子 Agent 在停下前的花费也会算进去。
- 两种做法：调用前预估，用“已花 + 本次最大可能花费”判断，偏保守；调用后检查，给上限留出一次调用的余量，偏宽松。
- 预算要覆盖子 Agent，否则主 Agent 把工作分出去就能绕过上限。

**追问链**：
1. 调用前怎么预估？→ 输入 token 可以先算出来，输出按 `max_tokens` 上限算，再乘单价；有缓存时按未命中计，偏保守。
2. 多个子 Agent 并行，预算怎么分？→ 先从 Task 预算里给每个子 Agent 预留一份，用完的退回；总量由一个服务端计数器扣减，不让子 Agent 各算各的。
3. 预算用完时有工具调用执行到一半怎么办？→ 等它结束并记下结果，或者取消并把“已取消”写回；有副作用的动作要在日志里记清状态，恢复时先查结果。

**易错点**：
- 以为设了上限就一分不会超。
- 只统计主 Agent，漏掉子 Agent 和压缩这类额外调用。

## harness-loop-005 人工审批时 Agent 要暂停几小时，Harness 怎么设计
- level: 3
- tags: [harness]

**一句话答案**：暂停时把当前状态写入 Checkpoint 并释放进程，人回复后用同一个任务 ID 加载状态继续；恢复时要防止暂停前的副作用被重复执行，并重新检查外部状态。

**要点**：
- 等待审批是状态机里的一个状态，必须能存盘。不能让 Loop 一直占着进程和连接。
- LangGraph 的 `interrupt()` 要求 checkpointer 和 `thread_id`，用 `Command(resume=...)` 恢复，恢复值就是 `interrupt()` 的返回值。
- LangGraph 恢复时整个节点从头重新执行，所以 `interrupt()` 之前的副作用要幂等，或者挪到之后或单独的节点里。
- 审批界面展示执行器从真实参数生成的内容；拒绝时把原因写回上下文。
- 审批要设超时，超时按“不执行”处理，状态保留。

**追问链**：
1. 为什么恢复时会重复执行？→ 很多实现按节点或步骤粒度存快照，恢复从这一步的开头重跑，不是从暂停的那一行继续。
2. 暂停了一天再恢复，要检查什么？→ 外部状态有没有变（文件、工单状态、库存）、工具和下游服务是否可用、prompt 和模型版本是否已升级。
3. 审批是外部系统做的呢？→ 把恢复值当成“审批已返回”的信号，再去那个系统查结果；不要在恢复时重新提交一次审批。

**易错点**：
- 用 `while True` 加 `sleep` 等审批，进程重启就丢了。
- 恢复后不核对外部状态，在过时的信息上继续操作。

## harness-loop-006 OpenAI Agents SDK 和 Claude Agent SDK 的 Agent 循环，各替你做了什么、没做什么
- level: 2
- tags: [harness, core]

**一句话答案**：OpenAI 的 Runner 管最终输出、Handoff、工具调用，限轮数；Claude Agent SDK 复用 Claude Code 循环，带工具、压缩、权限、花费上限。完成标准和审批自己定。

**要点**：
- OpenAI Agents SDK 的 `Runner` 循环：调模型 → 最终输出就返回 / Handoff 就换 Agent / 工具调用就执行并继续。
- OpenAI Agents SDK：最终输出指“期望类型的文本且没有工具调用”；超出 `max_turns` 抛 `MaxTurnsExceeded`，可注册处理函数给兜底输出；Guardrail 对输入、最终输出和单次工具调用做检查。
- Claude Agent SDK：`max_turns` 和 `max_budget_usd` 两种上限，结果消息的 `subtype` 区分成功和各类超限；接近上下文上限时自动压缩；权限按 hooks、deny、ask、权限模式、allow、`canUseTool` 的顺序判定。
- LangGraph 只管流程和状态持久化，循环由你画成图。

**追问链**：
1. 选哪个？→ 看哪个的默认值离任务最近。任务像“读写文件、跑命令”就用现成 Harness；要精细控制流程和断点就用图；多个专职 Agent 转交就看 Handoff。
2. 怎么降低换 SDK 的成本？→ 工具、校验、评测写成和 SDK 无关的模块，SDK 只负责串起来。
3. SDK 升级改变了行为怎么发现？→ 固定版本，升级前在同一评测集上对比通过率、步数和成本。

**易错点**：
- 背功能列表，说不出各自的默认值和抽象层次。
- 描述 SDK 内部实现时说不出出处。只讲文档写明的部分。

## harness-loop-007 预算 1 美元、单次调用最坏 0.12 美元、4 个子 Agent 共用预算且调用后记账，最多会花多少，怎么改成不超
- level: 3
- tags: [harness]

**一句话答案**：最后一次放行时已花小于 1 美元，之后最多 4 个调用在途、各花 0.12，所以最多接近 1.48 美元。不超有两种：共享计数器按 0.12 预留，或把内部阈值降到 0.52。

**要点**：
- 推导：设最后一次放行的时刻已花 < B，此后只有当时在途的最多 k 个调用会记账，所以超支 < k·c_max。这个界是紧的：k 个调用同时在“已花 = B − ε”时发出、都花满。
- c_max 的算法：输入 token 调用前可算，全按未命中缓存的价格；输出按 `max_tokens`。
- 预留：条件是“已花 + 已预留 + c_max ≤ B”，返回后按实际结算退差额。最后剩下不到一个 c_max 用不上，和 k 无关。
- 降阈值：阈值 B − k·c_max，要让出 k·c_max，这里是 48% 的预算。
- Claude Agent SDK 文档写明 `max_budget_usd` 在响应到达后比较，可能超出一次响应的花费，再加上仍在运行的子 Agent 停下前的花费。

**追问链**：
1. 预留为什么必须是一个共享计数器？→ 各子 Agent 各算各的，每个都只看到自己的花费，相当于每个子 Agent 单独超一份；检查和预留还要原子，否则两个 worker 同时通过检查。
2. 随机模拟里超支只有上界的九成，能按观察值留余量吗？→ 不能。最坏情况是可构造的，对外承诺上限要按 k·c_max 算。
3. 工具调用不花模型 token，也算并发吗？→ 调用付费 API 或派生子 Agent 的工具算，它们也是共用预算的在途花费。

**易错点**：
- 以为单线程最多超一个调用，并发时也一样。
- 只统计主 Agent，漏掉子 Agent；Claude Agent SDK 的 `usage` 只覆盖主循环，整棵树要看 `model_usage`。

## harness-loop-008 Agent Loop 只设了 max_steps 和重试上限，怎么证明它一定会停
- level: 3
- tags: [harness]

**一句话答案**：每条回到“装配上下文”的路径都经过一次成功的模型调用，步数加 1；唯一不加步数的自环是重试，受重试上限约束。二元组（剩余步数，剩余重试）按字典序严格下降，所以一定停。

**要点**：
- 前提是终止条件只在“装配上下文”检查，且“校验不通过”“无法解析”也都回到装配，不绕过步数计数。
- 最长一圈：装配、调用、重试 r 次、解析、权限、审批、执行、回到装配，共 r + 6 次转移，所以总转移数 ≤ max_steps·(r + 6) + 1。
- 会破坏终止性的改动：校验失败后直接再调模型而不计步；执行工具时无上限地自动重试；审批没有超时。
- 这只保证“会停”，不保证“停得快”：一次调用卡住时，墙钟检查要等它返回，所以每次调用还要有自己的超时。

**追问链**：
1. 设了墙钟上限 10 分钟，任务为什么跑了 40 分钟？→ 终止只在 Step 之间检查，一次工具调用卡了 30 分钟。能保证的上界是墙钟上限加一个 Step 的最长耗时。
2. 为什么不在每个状态都检查终止条件？→ 一个 Step 要么完整走完，要么不开始，日志里不会有半截 Step；代价由单次调用的超时来补。
3. 步数上限触发时还有工具调用没写结果怎么办？→ 终止发生在装配阶段，那时上一批调用都已有结果；在途调用的处理只出现在并发或取消时，要写“已取消”或“结果未知”。

**易错点**：
- 只说“有 max_steps 所以会停”，说不出哪些路径不计步、会绕过它。

## harness-loop-009 工具死循环、过早宣布完成、无限重规划，Harness 各用什么信号检测
- level: 2
- tags: [harness, evaluation]

**一句话答案**：死循环看同一调用加同一结果的重复、调用序列的周期、连续无新信息；过早完成看最后一次修改后有没有通过的测试和完成清单；重规划看计划变了但期间没有新工具结果。

**要点**：
- 三者都用 Harness 自己记的事件判断，不用模型的自述。
- 完全重复的键要带上结果：轮询任务状态时参数相同、结果在变，是正常的。
- 参数先规范化：键排序、去空白、Unicode 归一、路径去 `./`，否则改一个空格就绕过。
- 来回打转（A B A B）每次参数都不同于上一次，要检查序列末尾的周期 2 或 3。
- 过早完成：Anthropic 长任务文章观察到模型只跑了单元测试或 `curl` 就标完成；做法是 JSON 功能清单，只有测试通过才改 `passes`。
- 重规划要先让模型用固定格式或专用工具写计划，Harness 才能比较。

**追问链**：
1. 检测到之后马上终止吗？→ 先写回提示并附上上次结果，再限制该工具，最后才终止并返回原因和进度。
2. 阈值怎么定？→ 先只记录不拦截，看触发样本里真死循环的比例，再在评测集上定；换模型后重测。
3. OpenAI Agents SDK 内置了什么防循环机制？→ `reset_tool_choice` 默认开，工具调用后把 `tool_choice` 重置为 `auto`，避免强制工具调用导致无限循环。

**易错点**：
- 只按“工具名 + 参数”判重复，把轮询误杀。
- 用模型自己给的完成度打分做完成判定；自评偏宽松。

## harness-loop-010 审批暂停后进程重启，怎么保证恢复时不重复执行已完成的步骤
- level: 3
- tags: [harness]

**一句话答案**：状态只存在只追加的事件日志；副作用拆成发出前的 intent 和拿到后的 result，带 Task ID 加步骤的幂等键；恢复时有 intent 无 result 的先按键查外部状态，查不清转人工。

**要点**：
- 恢复的步骤：从日志重建状态 → 对账结果未知的步骤 → 核对外部状态和版本 → 继续 Loop。
- 已有 result 的步骤直接跳过；审批也写成事件，只接受“当前在等的那一步”，重复提交拒绝。
- LangGraph 恢复时整个节点从头重跑，`interrupt` 之前的副作用会再执行，要幂等或挪到之后、拆成单独节点。
- OpenAI Agents SDK 文档写明审批不保证只执行一次，从旧快照恢复可能再执行工具；建议稳定的幂等键，结果不确定时记为未知、不自动重放。
- 同一个 Task 同时只允许一个 Loop，用租约或乐观锁，防止同一快照被恢复两次。

**追问链**：
1. 崩在副作用生效之后、结果写盘之前，怎么办？→ 日志里有 intent 没 result，按幂等键查下游；查到就补记结果，查不到才重发，下游按键去重。
2. 下游不支持按键查询呢？→ 不自动重发，记为结果未知，交给人确认。
3. LangGraph 一个节点里有两个 `interrupt`，恢复值怎么对上？→ 按调用顺序的下标严格匹配，所以不能有条件地跳过 `interrupt`。

**易错点**：
- 恢复时把日志里的工具调用重新执行一遍，而不是只读回记录。
- 用内存里的变量记“做到哪一步”，进程重启就丢了。
