# 题目：上下文装配、压缩与断点续跑

> 对应知识章：[README.md](README.md)。先闭卷作答，再看答案。

## harness-ctx-001 窗口已经很大了，为什么还要做上下文压缩
- level: 2
- tags: [harness, inference]

**一句话答案**：窗口装得下不等于模型用得好，内容越多回忆越差（context rot）；每步都要重送整个历史，累计成本近似随步数平方增长；长任务的历史迟早超过任何窗口。

**要点**：
- context rot：Anthropic 引用“大海捞针”类研究，所有模型都有这个现象；原因是 n 个 token 有 n² 对注意力关系，以及训练数据里短序列更多。
- 成本：第 n 步要重送前 n−1 步的内容，求和是平方量级；首 token 延迟也随输入变长。
- 最先做的一步是工具结果清理，它压低的是增长最快的“每步新增”。

**追问链**：
1. 前缀缓存能消掉平方项吗？→ 只能消掉稳定前缀那部分。只追加的历史能吃到前几步的缓存，一旦压缩改写，压缩点之后就失效了。
2. 短任务要压缩吗？→ 几步就结束的任务收益很小，还多一次模型调用的延迟。
3. 除了压缩还有什么办法控制上下文？→ 按需加载（只放引用，用工具读）、外置笔记、子 Agent 隔离。

**易错点**：
- 回答“因为窗口不够”。很多任务窗口够用，问题在效果和成本。

## harness-ctx-002 上下文压缩有哪几级，哪些内容不能压掉
- level: 2
- tags: [harness]

**一句话答案**：按损失从小到大：裁剪、摘要、重置，外加贯穿全程的外置笔记；目标和硬约束、权限边界、失败过的路径、未完成步骤、未确认的副作用、已用的引用编号不能压掉。

**要点**：
- 裁剪是清掉用过的工具结果；摘要由同一 Agent 继续；重置是开新 Agent，用结构化交接文件接上。
- Anthropic 称工具结果清理是最安全、最轻的压缩形式。
- Claude Code 的压缩保留架构决策、未解决的 bug、实现细节，带着摘要和最近访问的五个文件继续。
- 调压缩 prompt：先做满召回，再提精确度，因为漏掉关键信息的代价远大于多留冗余。
- 摘要格式固定，例如目标、约束、已完成、失败过的、待办、产物引用，方便逐项检查。
- 压缩前原文要进 Event Log，压缩才敢做得激进。

**追问链**：
1. 压缩和重置怎么选？→ 同一阶段、需要连续性时压缩；进入新阶段、或模型接近上限时提前收工，就重置并写交接文件。哪种好取决于模型，要测。
2. 长期规则写在第一条消息里会怎样？→ 可能被压缩掉。要放在每次请求都会重新注入的位置，例如项目说明文件或系统提示。
3. 阈值怎么定？→ 软阈值触发摘要、硬阈值触发重置，按评测里质量开始下降的拐点定，硬阈值给本步输出留余量。

**易错点**：
- 说“压缩就是让模型写个摘要”，说不出分级和不可压缩清单。
- 摘要时把用户原话也改写了，约束被“优化”掉。

## harness-ctx-003 Event Log、Checkpoint、Resume 是什么关系
- level: 2
- tags: [harness]

**一句话答案**：Event Log 是只追加的事实记录，Checkpoint 是加速恢复的快照，Resume 用最近的 Checkpoint 加之后的日志重建状态；上下文只是从它们装配出来的视图。

**要点**：
- 只有快照没有日志：能恢复，但无法审计和复盘。只有日志没有快照：长任务恢复要从头重建，很慢。
- Checkpoint 打在阶段边界和有副作用的步骤之后，要记下哪些副作用已经完成。
- 日志在上下文之外，压缩就不再是永久丢失。Anthropic 的 Managed Agents 把会话做成上下文窗口外的只追加日志，Harness 崩了，新实例读回日志继续。
- 有完整日志不等于能精确重放模型行为，采样和外部数据都会让轨迹分叉。

**追问链**：
1. 大块工具返回也全记进日志吗？→ 存到对象存储或文件，日志里记摘要和引用。
2. 回放和重放的区别？→ 回放使用日志里记录的工具返回，只重跑模型；重放连工具也重新执行。排查模型问题用回放。
3. LangGraph 里对应什么？→ checkpointer 按 `thread_id` 存状态快照，用于人工介入、回到历史状态和故障恢复；生产要用持久化的 saver，并设快照保留策略。

**易错点**：
- 把对话轨迹当成工作状态。恢复时以结构化的工作状态和日志为准，不以模型上下文为准。

## harness-ctx-004 进程在第 7 步崩溃，第 7 步是一次写操作，怎么恢复才不重复副作用
- level: 3
- tags: [harness]

**一句话答案**：从第 6 步后的 Checkpoint 恢复，只读回日志、不重新执行；第 7 步结果未知，先用幂等键向下游查询，已完成就补记结果，没完成再带同一个幂等键重做，查不清交给人；最后核对环境再继续。

**要点**：
- 幂等键用 Task ID 加步骤编号生成，同一步重复提交时下游识别为同一次。
- 恢复时重新执行日志里的工具调用是错的：读操作只是浪费，写操作会重复副作用，而且外部数据已经变了。
- 核对环境：工作区和依赖还在不在、下游是否可用、prompt 和模型版本有没有升级、数据有没有过期。
- 长任务的会话开头先跑一次基本检查，发现上一次留下的坏状态先修。

**追问链**：
1. 下游不支持幂等键呢？→ 恢复时先查结果再决定；查不到就交给人工确认，不盲目重做。
2. 框架恢复时会从节点开头重跑，怎么办？→ 节点里副作用之前的代码会重新执行，要让副作用幂等，或者把副作用放到单独的节点里。
3. 用户已经看到了第 7 步之前的部分输出，恢复后要重新发吗？→ 日志里记下已经发给用户的内容，恢复后从后面接着发，避免重复。

**易错点**：
- 回答“重新跑一遍第 7 步”，没想到副作用。
- 只恢复上下文，不恢复“哪些副作用已完成”这份记录。

## harness-ctx-005 KV Cache 命中率突然下降怎么排查，压缩对缓存有什么影响
- level: 2
- tags: [harness, inference]

**一句话答案**：缓存只复用从开头起完全相同的前缀。先比对相邻两个请求，找第一个不同的 token，常见是时间戳、键顺序、工具顺序变了或超过有效期；压缩改写历史，压缩点之后的缓存全部失效。

**要点**：
- Anthropic API：前缀顺序是 tools、system、messages，某一层变了，这层和之后都失效；最多 4 个 `cache_control` 断点；短于最小长度不缓存且不报错；默认 5 分钟有效期，使用时免费刷新，可选 1 小时。
- vLLM：按“前缀哈希 + 本块 token”给每个 KV 块算哈希，只缓存满块，空闲块按 LRU 淘汰。
- 用响应里的 `cache_read_input_tokens`、`cache_creation_input_tokens` 按请求记录命中情况。

**追问链**：
1. 查到是系统提示里的时间戳导致的，怎么改？→ 把时间等动态内容移到稳定前缀之后，例如放进最新一条用户消息；系统提示和工具定义保持逐字不变。
2. 压缩太频繁对缓存有什么影响？→ 每次压缩后要重新写缓存；阈值太低时，省下的 token 可能被缓存失效抵消。
3. 多租户共用推理引擎，缓存有什么风险？→ 别人可能通过延迟差异推断缓存里有什么。vLLM 可以按请求加 `cache_salt`，只有同一个 salt 的请求才能复用。

**易错点**：
- 以为缓存只是性能优化、不影响效果。为了缓存调整内容顺序后，要用评测确认质量没变。
- 压缩阈值设得太低，省下的 token 被缓存失效抵消。

## harness-ctx-006 怎么证明你的压缩策略没有丢关键信息
- level: 3
- tags: [harness, evaluation]

**一句话答案**：三种方法一起用：关键事实保留率（对压缩后的上下文问目标、约束、失败路径）、同一断点的下一步动作一致率、开关压缩的端到端对比（通过率、步数、重复调用、成本），上线后再监控压缩后的重复调用。

**要点**：
- 只看通过率会漏问题：通过率不变，但步数和重复调用变多，说明丢了“已经试过什么”。
- 评测集要用和线上相似的长轨迹。用不相关内容填出来的长上下文，结论偏乐观。
- 同一题跑多次看分布，单次差几个点不下结论。
- 摘要格式固定，才能逐字段检查。

**追问链**：
1. 关键事实谁来抽？→ 先用规则抽结构化字段（约束、ID、数字、失败的工具调用），再人工抽查一部分；也可以用模型抽，但要人工校准。
2. 下一步动作不一致一定是坏事吗？→ 不一定，可能换了一条等价的路。要看最终结果和步数，再人工看分歧样本。
3. 压缩 prompt 改了一版，怎么上线？→ 在固定评测集上跑门禁，通过率不降、步数和重复调用不升才放量，并保留回滚开关。

**易错点**：
- 只讲压缩策略，不讲验证。面试里验证才是加分项。

## harness-ctx-007 什么时候该用子 Agent 隔离上下文，代价是什么
- level: 2
- tags: [harness, core]

**一句话答案**：子任务能独立完成、中间过程很长、主 Agent 只需要结论时才拆；子 Agent 用干净的上下文探索，只交回精简的结构化总结。代价是 token 成本成倍增加，以及交接中的信息丢失。

**要点**：
- Anthropic 的多 Agent 研究系统文章：Agent 约用掉聊天 4 倍的 token，多 Agent 约 15 倍。
- 减少走样：让子 Agent 把产物写到外部存储，只交回引用。
- 交接时显式传目标、约束和输出格式；交回结构化字段，方便主 Agent 用代码汇总。
- 来回对话多的任务适合压缩，有明确阶段目标的迭代开发适合结构化笔记，能并行探索的研究适合多 Agent。

**追问链**：
1. 子 Agent 误解任务怎么办？→ 交接时写清约束和完成标准，返回后由主 Agent 或规则检查格式和覆盖度。
2. 子 Agent 之间要共享信息呢？→ 通过主 Agent 中转，或写到共享文件，不直接互相读上下文。
3. 子 Agent 的权限和预算怎么算？→ 不能比主 Agent 更宽；花费计入 Task 总预算，否则拆出去就绕过了上限。

**易错点**：
- 说“子 Agent 越多越好”。每个子 Agent 都是一次独立装配加多步调用。
- 子 Agent 返回全部原文，隔离就没意义了。

## harness-ctx-008 现场估算：固定前缀 8,500 token，每步新增 2,800 token（工具结果占 2,500），窗口 200K，第几步超窗，80 步累计输入多少
- level: 2
- tags: [harness, inference]

**一句话答案**：C_k = 8,500 + (k−1)·2,800，第 70 步超窗；80 步累计 80×8,500 + 2,800×80×79/2 ≈ 953 万，平方项占九成；工具结果占新增的 89%，先压它。

**要点**：
- 累计输入 S_n = n(P+U) + g·n(n−1)/2，步数翻倍约涨四倍；超窗步数只看斜率 g，固定前缀只是平移。
- 只追加加缓存（写 1.25 倍、读 0.1 倍）：成本 = 1.25(P+U) + 0.1(S_n − C_n) + 1.25·g(n−1) ≈ 122 万，约为不开缓存的 12.8%。缓存降常数，平方项还在。
- 清理旧工具结果（保留最近 3 个、其余换成 20 token 占位符）后斜率从 2,800 降到 320。

**追问链**：
1. 开了缓存还需要压缩吗？→ 需要。缓存只把平方项乘了 0.1，撞窗口的步数不变，长上下文的回忆效果也不变。
2. 只用摘要（100K 触发、摘要 4K）呢？→ 第 33 次调用第一次摘要，之后每 32 次一次，曲线是锯齿形。
3. 为什么工具结果是主要增长源？→ 模型一次调用参数几十到几百 token，读回的文件、网页、日志常常上千；每步新增里它占大头。

**易错点**：
- 只算最后一步的上下文长度，漏掉每步都要重送整个历史的累计量。
- 以为固定前缀越大越容易超窗。超窗由斜率决定。

## harness-ctx-009 崩溃恢复时，为什么调用意图和模型输出都要先写进日志
- level: 3
- tags: [harness]

**一句话答案**：先写意图再调外部，崩在中间时才知道这一步结果未知，要先查再决定；模型输出不确定，写进日志后恢复直接用它，不重新采样，否则会换一条路、日志对不上。

**要点**：
- 进程可能死在三处：写意图前（外部没动，正常执行）、写意图后调外部前（没动）、外部生效后结果写回前（已生效）。后两种日志里一样，都按结果未知处理。
- 结果未知：有幂等键就带同一个键重做；能按 token 查就先查；都不行交给人。
- 先调外部后写日志，崩溃时日志里什么都没有，恢复后会再执行一遍，这和数据库的预写日志是同一个道理。
- 工作状态是日志的纯函数折叠；Checkpoint 只是加速，必须和从头折叠一致。

**追问链**：
1. 幂等键为什么不能用随机 UUID？→ 恢复后会生成新键，下游认为是新请求。用 Task ID 加步骤编号，恢复前后不变。
2. 读操作也要先查吗？→ 不用，直接重做，以新结果为准写进日志。
3. 怎么测这套恢复逻辑？→ 故障注入：在每个边界杀一次进程再恢复，assert 工作状态、日志、装配出的上下文和不崩溃的运行一致，副作用恰好一次。

**易错点**：
- 只记工具结果，不记意图，结果未知的调用无从发现。
- 恢复时重新调模型，觉得“反正它会做同样的决定”。

## harness-ctx-010 现场估算：上下文 100K、清理点之前稳定前缀 10K，清掉 50K 旧工具结果，缓存写 1.25 倍、读 0.1 倍，几次请求回本
- level: 3
- tags: [harness, inference]

**一句话答案**：清理那次多付 1.25×(100K−50K−10K) − 0.1×(100K−10K) = 41K，之后每次少读 50K、省 5K，约 8.2 次请求回本；清得越少越难回本，所以要批量清理。

**要点**：
- 公式：m* = [w(C−X−p) − ρ(C−p)] / (ρX)。只清 5K 要 194.5 次请求。
- 读价从 0.1 降到 0.05，同一次清理要 18.2 次才回本：缓存越便宜，改写历史越贵。
- Claude API 的 `clear_at_least`：一次清不掉指定量就不清，用来判断清理值不值得打破缓存。
- 摘要同理；在系统提示末尾单独加断点，压缩时系统提示的缓存仍有效。

**追问链**：
1. 每步清一点和攒够再清，哪个好？→ 只数 token 是逐步清理省；算上缓存，逐步清理每步都让后面的缓存失效，批量清理更便宜。
2. 怎么在线上发现压缩太频繁？→ 按请求画 `cache_creation_input_tokens`，看尖峰是否和压缩事件对齐，再按公式算回本请求数。
3. 任务剩下的请求数少于回本次数呢？→ 不清，除非快撞窗口或质量已经下降。

**易错点**：
- 只看上下文长度下降就认为压缩省钱。
- 忘了压缩点之前的稳定前缀仍能命中，把整段都按写价算。
