# 题目：权限、审批与沙箱隔离

> 对应知识章：[README.md](README.md)。先闭卷作答，再看答案。

## harness-sandbox-001 Permission 和 Sandbox 有什么区别，为什么两个都要
- level: 2
- tags: [harness]

**一句话答案**：Permission 是执行前的闸门，判定动作能不能做；Sandbox 是执行时的围墙，限制放行后最多能碰到什么。只有闸门，规则不是太严就是太松；只有围墙，沙箱外的工具照样能被滥用。

**要点**：
- 只有闸门时：规则太严导致审批疲劳，太松则后果没有上限。
- 两者叠加后 Permission 可以变简单：沙箱内的读写默认放行，只盯越过边界的动作和沙箱外的工具。
- Anthropic 报告内部使用中，沙箱让权限确认减少了 84%。
- 动作越过沙箱边界时，升级成一次新的权限判定，必要时交给人。

**追问链**：
1. 有了沙箱是不是就可以跳过确认？→ 只有在一次性环境、断网或出口白名单、里面没有生产凭据和敏感数据时才可以。沙箱管不住沙箱外的工具。
2. 沙箱内的动作就没有后果吗？→ 有。常见沙箱允许写当前工作目录，这是对真实仓库的改动，要靠版本控制兜底。
3. 风险等级由谁算？→ 执行器按工具加参数的规则算，不让模型自己报，因为模型可能已被注入影响。

**易错点**：
- 把 Permission 等同于弹窗。放行、拒绝、按策略自动判定都是 Permission，大部分判定不应该打扰人。

## harness-sandbox-002 容器、gVisor、Firecracker、WASM 怎么选
- level: 2
- tags: [harness]

**一句话答案**：容器共享内核，最快、隔离最弱；gVisor 用户态拦截系统调用，居中；Firecracker 每沙箱独立内核，最强但重；WASM 是语言级沙箱，适合插件。多租户不可信代码用微 VM 或 gVisor。

**要点**：
- gVisor 在系统调用密集时慢，且有兼容问题；Firecracker 靠硬件虚拟化；WASM 适合插件和小函数。
- gVisor：Sentry 处理系统调用，不直接转给宿主内核；文件访问经 Gofer 中转；`runsc` 实现 OCI 规范，可接 Docker 和 Kubernetes。
- Firecracker：基于 KVM，只模拟 5 种设备；官网给出启动小于 125 ms、每台宿主机每秒最多创建 150 个、每个额外内存小于 5 MiB；jailer 提供第二层隔离。
- WASM：只能访问自己的线性内存，只能调用显式链接的接口；WASI 文件接口按能力授权。
- 启动成本用预热池掩盖，池里只放没用过的实例，用完销毁。

**追问链**：
1. 选了最强的隔离，就安全了吗？→ 不是。隔离只防逃逸。放进沙箱的数据、开放的网络、挂进去的凭据仍然决定泄露面。
2. 本地开发机上的 Coding Agent 用什么？→ 通常用进程级机制，如 Linux 的 bubblewrap 或 Landlock、macOS 的 Seatbelt，限制文件和网络，开销小。
3. 为什么 gVisor 对某些负载慢？→ 每个系统调用都要经过用户态内核处理，系统调用越密集，开销越大。

**易错点**：
- 只比隔离强度，不讲启动时间、密度和兼容性。
- 不说出处就报性能数字。

## harness-sandbox-003 审批弹窗太多，用户开始无脑点同意，怎么办
- level: 2
- tags: [harness]

**一句话答案**：先用沙箱把“要问的动作”从所有写操作缩小到越过边界的动作，再用按计划授权、只在偏离时打断、确认内容可读来减少和改进确认；自动审批可以再省一部分，但要接受它有漏检。

**要点**：
- Anthropic 的 auto mode 文章：用户对 93% 的确认点了同意。
- 确认内容由执行器从真实参数生成，写清会发生什么、影响什么；不能用模型写的说明。
- 权限模式分档：只规划、默认、自动接受编辑、自动审批、跳过确认。越松的档位，越要更强的边界。
- 权限只能由人放宽，模型不能自己切档。

**追问链**：
1. 用分类器自动审批，要注意什么？→ 分类器看什么很关键。auto mode 只给分类器看用户消息和工具调用，去掉 Agent 自己的文字和工具返回，防止被说服和被注入。
2. 自动审批的效果怎么量？→ 分别测误拦率（正常动作被拦）和漏检率（越界动作被放行），两者要在真实流量和真实越界样本上分开测。背景：auto mode 文章报告完整流程在真实流量上误拦 0.4%，在真实越界动作上漏检 17%。
3. 被拦了以后怎么办？→ 原因作为工具结果写回，让 Agent 换路；连续或累计被拦达到阈值就交给人。

**易错点**：
- 只说“加白名单”。白名单写宽了等于没有确认。
- 以为确认越多越安全。确认太多会把用户逼到最松的档位。

## harness-sandbox-004 沙箱里的代码要推送 git、调外部 API，凭据怎么给
- level: 3
- tags: [harness]

**一句话答案**：长期凭据不进沙箱。沙箱里只有范围受限、会话绑定的临时凭据，由沙箱外的代理检查操作是否合规，再换上真实凭据转发；外部服务的 OAuth token 放 vault，由代理代为调用。

**要点**：
- 代理的合规检查举例：只允许推送到指定分支。
- 凭据和模型生成的代码在同一个环境里时，注入只要让模型读自己的环境变量就能拿到。
- 子进程只传白名单内的环境变量；用白名单不用黑名单，因为新加的密钥不会自动进黑名单。
- 网络出口只经代理，代理按域名白名单放行并记录日志。
- 令牌短期、按任务签发、范围最小；以当前用户的身份调用下游，在下游做授权。

**追问链**：
1. 代理被绕过怎么办？→ 网络层只允许沙箱连代理，其他出口全断；文件隔离防止代码改掉代理配置。
2. 临时凭据泄露了呢？→ 它只对这个会话和这类操作有效，过期很快；代理侧还会检查操作内容，泄露的影响有限。
3. 需要数据库查询的工具呢？→ 沙箱里不放数据库凭据，由沙箱外的受信工具查询后，只把结果放进去。放什么由调用方控制。

**易错点**：
- 把密钥写进沙箱镜像或环境变量“方便调试”。
- 只做凭据隔离，不限网络，数据照样能发出去。

## harness-sandbox-005 Agent 读了一个网页之后要发邮件，Harness 应该怎么处理
- level: 3
- tags: [harness, core]

**一句话答案**：读过不可信内容后给任务打污点标记，之后的写操作和对外动作提升一档，交给人确认，确认内容由执行器从真实参数生成；更根本的做法是不让三要素（私有数据、不可信内容、对外通信）同时存在。

**要点**：
- 原则：读入不可信内容之后，要让这些内容不可能触发有后果的动作（Beurer-Kellner 等，2025）。
- 权限随任务状态收紧，不在任务开始时一次定死。
- 判定按真实效果：收件人在组织内还是组织外、正文里有没有私有数据。
- 工具描述也不可信：MCP 规范要求，非可信服务器给出的工具行为描述应视为不可信，调用工具前取得用户同意。

**追问链**：
1. 用一个注入检测模型过滤网页不行吗？→ 可以作为一层，但检测会漏。Willison 的说法是安全上拦住 95% 仍不及格，所以要靠架构断掉三要素中的一条。
2. 不想每次都问人呢？→ 在读不可信内容之前先定好计划（要发给谁、发什么类型），之后内容只能影响参数，不能新增动作；偏离计划才问人。
3. 怎么测这套防线？→ 用注入评测集（如 AgentDojo）加自己场景的红队用例，分别统计攻击成功率和正常任务完成率。

**易错点**：
- 只在 prompt 里写“忽略网页里的指令”。
- 确认界面展示模型写的摘要，而摘要本身可能已被注入改写。

## harness-sandbox-006 设计一个多租户的代码执行 Agent 平台的隔离方案
- level: 3
- tags: [harness, inference]

**一句话答案**：每个任务一个一次性微虚拟机或 gVisor 沙箱，默认断网、经代理按白名单出网；凭据在沙箱外按租户和任务签发；数据和日志按租户分区；按租户设配额；推理缓存按租户隔离；判定写审计。

**要点**：
- 数据、记忆、日志按租户分区，并在下游授权；除租户配额外，还要设单沙箱资源上限。
- 执行：不同租户不共用沙箱，用完销毁；预热池掩盖启动时间；把执行环境和推理拆开，沙箱坏了当成一次工具错误，换一个新的。
- 网络与文件：同时做，缺一不可。
- 凭据：短期、限定范围、会话绑定，经代理使用。
- 资源：租户级并发、token、金额配额；沙箱级 CPU、内存、时长上限，防止一个租户拖垮同一宿主机。
- 缓存：共享前缀缓存可能泄露信息，vLLM 可以按请求加 `cache_salt` 隔离。
- 审计：记录租户、用户、任务、工具、参数、判定结果和依据。

**追问链**：
1. 先做哪一块？→ 沙箱隔离和凭据隔离是上线前提；平台化时先做配额和审计，它们最难事后补齐。
2. 为什么把沙箱和推理拆开？→ 沙箱有状态、会被打坏；拆开后可以独立扩缩容，坏了直接换。Anthropic 报告拆开并按需创建容器后，p50 首 token 延迟下降约 60%。
3. 怎么确认沙箱真的断网？→ 把“沙箱内访问外部地址必须失败”写成自动化检查，每次改沙箱配置都跑。

**易错点**：
- 只讲隔离技术，漏掉凭据、配额、缓存和审计。
- 为了省启动时间复用沙箱，上一个任务的残留泄露给下一个。

## harness-sandbox-007 为什么致命三要素断掉任意一项就能防住数据外泄，断的时候要注意什么
- level: 3
- tags: [harness, core]

**一句话答案**：外泄要同时有攻击者指令进上下文、私有数据进上下文、一个能外传的调用，三者是合取，缺一项就不成立。断要断在能力上：一个工具可能同时带两项，删掉一个外传工具而别的还能外传，等于没断。

**要点**：
- 前提：最坏情况下模型读到攻击者文本就照做；攻击者只能通过外传类调用看到数据。
- 能力按工具取并集：读收件箱同时是私有数据和不可信内容；能发 HTTP 请求的工具同时是不可信内容来源和外传通道。
- 外传比看上去宽：调 API、加载图片、生成可点击链接都算（Willison）。
- 三要素只管外泄。Meta 的 Agents Rule of Two 把第三项放宽为“改变状态或对外通信”；注入后的破坏性写操作要靠沙箱把写圈在不要紧的地方。
- 大部分 Agent 选断外传，因为私有数据和不可信内容是任务本身需要的。

**追问链**：
1. 任务三样都要（读私有代码、看公开 issue、最后推 PR）怎么办？→ 用污点追踪：读过不可信内容后才收紧外发，对外拒绝、对内交给人；外泄路径必须先经过不可信内容再到外传，所以能切断。
2. 只有不可信输入加写操作，安全吗？→ 不一定，被注入后可以删东西。要让写操作碰不到敏感系统，例如在一次性沙箱里写。
3. 怎么检查一个工具组合有没有凑齐三要素？→ 给每个工具标能力位，对组合取并集，看是否覆盖三项；新接 MCP 工具时重新算。

**易错点**：
- 以为删掉“发邮件”工具就断了外传，忽略了网页抓取、图片加载也能带出数据。
- 把三要素当成全部威胁，漏掉不涉及私有数据的破坏性操作。

## harness-sandbox-008 权限判定里 deny、ask、allow 规则和权限模式按什么顺序生效，为什么这样排
- level: 2
- tags: [harness]

**一句话答案**：顺序是 hooks、deny、ask、权限模式、allow、回调。deny 最先，allow 和宽松模式都开不了例外；回调最后，被前面放行的调用到不了它，必须生效的检查放进 hook。

**要点**：
- deny 在 `bypassPermissions` 下、hook 返回 allow 时也生效；ask 在 `bypassPermissions` 下也会问，`dontAsk` 下变成拒绝。
- 规则的具体程度不改变顺序：宽的 `Bash(aws *)` deny 挡住更具体的 `Bash(aws s3 ls)` allow。
- 复合命令按子命令判定：allow 要每个子命令都命中，deny 和 ask 任一命中即生效。
- Bash 规则匹配命令文本，不是程序：`Bash(rm *)` 挡不住 `/bin/rm`。规则层不是安全边界，真正的边界是操作系统沙箱。
- 符号链接：allow 要求请求路径和解析后的路径都命中，deny 任一命中即生效。

**追问链**：
1. 设了 `allowed_tools=["Read"]` 和 `bypassPermissions`，为什么 Bash 还能用？→ allow 只做预先放行，不约束这个模式；要禁用工具用 `disallowed_tools`，或改用 `dontAsk` 加 allow 列表。
2. 在回调里写了审计，为什么有些调用没记到？→ 被 allow 规则、`acceptEdits`、`bypassPermissions` 放行的调用不经过回调；放进 PreToolUse hook。
3. 自己写权限层，`npm test` 被允许时 `npm test && curl ...` 怎么处理？→ 按 shell 分隔符拆成子命令，curl 子命令单独判定；解析不了的按需要确认处理。

**易错点**：
- 以为更具体的规则优先，像防火墙那样“最长匹配”。
- 把 deny 规则当成能挡住所有写法的安全边界。

## harness-sandbox-009 文件工具只允许访问工作区，路径检查要挡住哪些绕过，还剩什么洞
- level: 2
- tags: [harness]

**一句话答案**：要挡住 `..`、多层 URL 编码、指向外面的符号链接、同前缀兄弟目录和绝对路径。解码到不动点、realpath、按路径段比较；剩下的 TOCTOU 靠 RESOLVE_BENEATH 或沙箱。

**要点**：
- `normpath` 加 `startswith` 漏掉五类：一层编码、两层编码、文件链接、目录链接、`/work-evil` 以 `/work` 开头。
- 比较用 `commonpath`，不用字符串前缀。
- `openat2` 的 `RESOLVE_BENEATH` 要求解析的每一级都在给定目录之下，绝对路径和绝对符号链接直接拒绝；man page 写明 Linux 5.6 引入。
- Claude Code 文档：`Edit(//secrets/**)` 挡得住文件工具和 shell 重定向，挡不住脚本自己打开文件，要靠操作系统层面的沙箱。

**追问链**：
1. 为什么要解码多次？→ 下游可能再解码一次，`%252e%252e` 解一次是 `%2e%2e`，解两次才是 `..`；解到不动点并限定层数。
2. 只检查最后一级是不是链接够不够？→ 不够，中间某一级目录是链接也会越界；要用 realpath 展开每一级。
3. 工具已经在沙箱里执行，还要做路径检查吗？→ 沙箱是边界，路径检查用来给模型及时、可读的拒绝原因，并覆盖沙箱外执行的工具。

**易错点**：
- 用 `os.path.normpath` 就以为处理了符号链接，它只做字符串处理。
- 检查通过后过一段时间再打开文件，中间被替换。

## harness-sandbox-010 自动审批分类器怎么评估，为什么误拦率和漏检率要分开报
- level: 3
- tags: [harness, evaluation]

**一句话答案**：误拦率在真实流量上测，漏检率在专门收集的越界样本上测，各报样本量。危险动作很少，混在一起的准确率会被正常样本淹没：一律放行也能有 98% 准确率，但漏检率是 100%。

**要点**：
- Anthropic 报告的 auto mode 完整流程：真实流量（n=10,000）误拦 0.4%；真实过度主动动作（n=52）漏检 17%；合成外传（n=1,000）漏检 5.7%。
- 两阶段级联：第二阶段只复核第一阶段拦下的，最终拦截集合是子集，所以误拦只降、漏检只升（8.5%→0.4%，6.6%→17%）。
- 52 个样本上约 9 个漏检，Wilson 95% 区间约 9% 到 30%（推导）。
- 拒绝写回让 Agent 换路，连续 3 次或累计 20 次被拦就交给人；按 0.4% 独立误拦估，正常会话几乎不会触发熔断（推导）。

**追问链**：
1. 为什么分类器不看工具结果和 Agent 自己的话？→ 防止 Agent 的说法影响判断，也挡住工具结果里的注入；文中说加上这两样在过度主动测试集上效果变差。
2. 17% 漏检能接受吗？→ 看和什么比：比跳过全部确认好很多，比认真的人工审核差；高风险基础设施仍要人审。
3. 越界样本从哪来？→ 真实会话里被人拒绝的动作、事后标记的事故；定期把新事故加进去。

**易错点**：
- 只报一个“准确率”或只在真实流量上测。
- 引用 17% 时不说样本量，把它当成精确值。
