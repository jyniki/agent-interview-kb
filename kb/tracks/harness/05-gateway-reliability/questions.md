# 题目：模型网关、流式、缓存与熔断降级

> 对应知识章：[README.md](README.md)。先闭卷作答，再看答案。

## harness-gw-001 为什么 Agent 系统需要一层模型网关，它负责什么
- level: 2
- tags: [harness, inference]

**一句话答案**：把多模型接入、配额、限流、路由、重试、熔断降级、缓存和 token 计量集中到一处，故障时行为一致，账能对上；但网关只看到单次调用，剩余 deadline 和任务 ID 要由 Runtime 传进来。

**要点**：
- 请求路径：鉴权与配额 → 限流 → 缓存查询 → 路由 → 熔断检查 → 调用并流式转发 → 计量。
- 计量按租户、任务、模型记未缓存输入、缓存写、缓存读、输出四个数，计费和容量规划都依赖它。
- 带服务端工具（如服务端执行代码）的模型调用不在网关自动重试，网关不知道下游是否已经生效。
- 重试只放一层：网关负责模型调用的重试，就要关掉 SDK 的自动重试。

**追问链**：
1. 为什么剩余 deadline 要从上游传？→ 网关不知道整个任务还剩多少时间。Google SRE 书主张整棵调用树共用一个绝对截止时间，每层只用剩下的部分。
2. 网关和推理引擎的职责怎么分？→ 引擎负责前缀缓存、调度和解码；网关负责跨模型、跨租户的策略。网关能做的是保持前缀稳定、会话粘滞，让引擎的缓存命中。
3. 自研还是用开源？→ 先用开源网关跑通路由和 fallback，例如 LiteLLM 的 Router；租户配额、计量对账、和 Runtime 的 deadline 协议通常要自己补。

**易错点**：
- 把网关说成“反向代理加个 API Key”，不讲 token 维度的配额和计量。
- 在网关重试所有失败，包括有副作用的调用。

## harness-gw-002 按 token 限流怎么实现，和按请求限流有什么区别
- level: 2
- tags: [harness, inference]

**一句话答案**：每个租户、每个模型各维护请求桶和 token 桶两个令牌桶；请求进来时按“未缓存输入估计 + max_tokens”预扣 token，结束后按实际用量退还；计数放在共享存储里原子扣减。

**要点**：
- 只按请求数限，大请求和小请求算一样，配额失效。
- Anthropic API 按 RPM、ITPM、OTPM 三个维度，用令牌桶，容量连续补充；ITPM 默认只计未命中缓存的输入。
- 预扣按 `max_tokens` 偏保守，但并发长请求不会一起冲破配额。
- 被拒绝时返回 429 和 `Retry-After`，客户端按它退避。

**追问链**：
1. Redis 挂了怎么办？→ 事先定好策略：降级到实例本地限流，按实例数平分配额，宁可稍严也不失控；或者对关键租户放行。
2. 都是 429，处理一样吗？→ 不一样。Anthropic 的速率限流带 `retry-after` 可退避；爬坡限制的 `error_code` 是 `ramp_limit_exceeded`，要放慢流量增长；花费上限的 429 没有 `retry-after`，重试没用，要告警。
3. 为什么提高缓存命中率能提高吞吐？→ 缓存读取不计入 ITPM。命中率 80% 时，同样的 ITPM 能处理约 5 倍的总输入。

**易错点**：
- 预扣后忘了按实际用量退还，配额越用越少。
- 每个实例各自在内存里限流，全局总量随实例数变化。

## harness-gw-003 主模型不稳定，降级链和熔断怎么设计
- level: 3
- tags: [harness, core]

**一句话答案**：按部署做熔断，失败过多就冷却或摘除，熔断期间直接跳到下一跳；降级链短，通常一跳，只在首个用户可见内容之前切换，终点是明确报错或固定流程；重试用预算和抖动限住总量。

**要点**：
- 断路器三状态：关闭时正常调用，失败到阈值打开；打开时直接返回错误；等待后半开放一个试探，成功关闭，失败重新计时。
- Envoy 的异常实例摘除：连续 5xx 或成功率显著低于同组就摘除，连续被摘除时时间按次数倍增，有上限。
- 超时分首字超时和总超时，首字前超时就切备用。
- 备用模型的 prompt 和评测要单独做，切换后质量会变。

**追问链**：
1. 为什么链不能长？→ 每一跳都加尾部延迟；多家同时出问题时往往共享依赖，换了也没用。
2. 熔断有什么缺点？→ Brooker 指出熔断的模态行为难测试，可能拉长恢复时间。Amazon 用本地令牌桶限制重试。两者可以配合：熔断挡坏部署，重试令牌桶挡重试放大。
3. 重试次数怎么定？→ Google SRE 书：每个请求最多三次，客户端重试占比低于 10% 才允许重试；退避用指数加抖动，Full Jitter 在 Brooker 的模拟里做的工作最少。
4. 流式输出到一半上游断了呢？→ 不能静默换模型重来。保存已发出的内容，交给 Runtime 决定续写还是报错。Anthropic 文档的续写做法是把部分回复放进新请求并要求从断处继续，工具调用块不能部分恢复。

**易错点**：
- 把降级等同于“换便宜模型”。那是成本路由，降级是可用性手段。
- 熔断按整个模型组做，一个部署坏了把整组都停了。

## harness-gw-004 Agent 的流式输出用 SSE 还是 WebSocket，断线和取消怎么处理
- level: 2
- tags: [harness]

**一句话答案**：文本流式多用 SSE：单向、走普通 HTTP、自带事件 id 和 `Last-Event-ID` 续传；连接和任务分开，断线后按最后事件编号补推；断开不等于取消，取消走单独接口并传到上游。

**要点**：
- 取消要一直传到上游的模型调用和工具。
- SSE 规范建议约每 15 秒发一条注释行保活，防止代理断开空闲连接。
- 生产和推送解耦：事件写进可回放、有上限的流，接入层按客户端速度读，慢客户端不阻塞模型调用。
- 缓冲超限时，进度类事件可以合并，正文不能丢，只能断开让客户端重连。
- 已发出的写操作取消不了，只能记录并走补偿。

**追问链**：
1. 什么时候必须用 WebSocket？→ 客户端要高频上行，例如语音打断、协同编辑。浏览器 WebSocket 没有内置背压，只能看 `bufferedAmount` 自己控速。
2. 流式“变成一次性返回”怎么排查？→ 先看中间代理是否开着响应缓冲。
3. HTTP 已经返回 200 了，上游出错怎么告诉客户端？→ 只能用流内事件。Anthropic 的流里会出现 `error` 事件，例如过载时的 `overloaded_error`。网关要把它转成自己的错误事件，带上是否可重试。

**易错点**：
- 客户端断开就立即取消任务，网络一抖用户的长任务就没了。
- 续传依赖的流过期被裁剪后，不给明确错误，客户端一直重连。

## harness-gw-005 语义缓存能不能用在 Agent 里，有什么风险
- level: 3
- tags: [harness, inference, evaluation]

**一句话答案**：适用面很窄，只适合无状态、事实稳定、不含实体参数和工具调用的单轮问答；主要风险是相似但不同导致答错、跨租户泄露、数据过期和缓存污染。Agent 里更值得做的是保住前缀缓存。

**要点**：
- 前缀缓存只复用计算，不会答错；语义缓存直接返回历史回答，相似不等于相同。
- 缓存键带租户和权限范围；含工具调用或有副作用的轮次不缓存。
- 设 TTL，源数据变更时按标签失效；只缓存通过校验的回答，并能按条删除。
- GPTCache 的 README 承认会有误报和漏报，给出命中率、延迟、召回三个指标。

**追问链**：
1. 相似度阈值怎么定？→ 在真实流量样本上标注“该命中 / 不该命中”，按误报率定阈值，不按命中率。
2. “取消订单 A”和“取消订单 B”怎么防？→ 把实体抽出来作为精确匹配的一部分；带写操作的意图干脆不缓存。
3. 前缀缓存网关能做什么？→ 不往前缀插时间戳和请求 ID，工具定义保持顺序不变，同一会话路由到同一部署。Anthropic 的前缀按 tools、system、messages 顺序构建，改前面一层后面全部失效。

**易错点**：
- 只报命中率不报误报率。
- 把前缀缓存和语义缓存混为一谈。

## harness-gw-006 现场估算：高峰每秒 5 个任务、每任务 12 次模型调用、每次 8 秒、输入 20K token（缓存命中 80%）、输出 500 token，需要多少在途并发和每分钟 token 配额
- level: 2
- tags: [harness, inference]

**一句话答案**：Little 定律：每秒 60 次调用乘 8 秒，在途 480 个；每分钟未缓存输入 60×20K×20%×60 = 1,440 万 token，输出 60×500×60 = 180 万 token。

**要点**：
- 算出每分钟 token 需求后，去对配额或集群容量。
- 在途数 = 到达率 × 停留时间：在途调用 = 5 × 12 × 8 = 480。
- 每次输入 20K token、缓存命中 80%：未缓存输入 = 60 × 20K × 0.2 = 每秒 240K，约每分钟 1,440 万。
- 每次输出 500 token：每分钟 60 × 500 × 60 = 180 万。
- 缓存命中率从 80% 掉到 50%，未缓存输入变成 2.5 倍，所以命中率要当容量指标监控。

**追问链**：
1. 成本怎么估？→ 按四项分别乘单价：未缓存输入、缓存写、缓存读、输出，再加重试和降级的额外调用。
2. 非实时任务怎么省？→ 走批处理接口。Anthropic 的 Message Batches 降价 50%，多数批次 1 小时内完成，24 小时没完成就过期。
3. 估出来超了配额怎么办？→ 先提高缓存命中、压缩上下文、简单步骤换小模型；再按租户优先级做准入，低优先级任务排队或走批处理。

**易错点**：
- 用聊天场景的“一个请求一次调用”去估 Agent。
- 只估输入不估输出，或者忘了缓存命中率的影响。

## harness-gw-007 设计一个多租户办公助手的模型网关
- level: 3
- tags: [harness, inference]

**一句话答案**：按请求路径设计：租户鉴权和预算 → 请求数加 token 限流 → 按难度和敏感度路由 → 按部署熔断、一跳降级 → 可续传流式 → 计量对账；deadline 和任务 ID 由上游传入。

**要点**：
- 流式转发用 SSE。
- 预算按月；计量按四项 token 对账；Runtime 传入的是剩余 deadline。
- 隔离：每个租户独立的预算和令牌桶，一个租户的批量任务不挤占其他租户；可按租户等级预留容量。
- 路由：简单的分类、改写走小模型，规划和长文档推理走大模型；含敏感数据的请求只发到满足合规要求的部署。
- 可靠性：首字超时切备用一次；熔断按部署；模型调用只在网关一层重试，用重试预算限总量；工具调用的重试在执行器（见 [04](../04-tool-orchestration/README.md)）。
- 缓存：保前缀缓存，会话粘滞；语义缓存只开给 FAQ 类无状态问答，缓存键带租户。
- 可观测：每次调用记租户、任务、模型、四项 token、首字延迟、是否降级、是否命中缓存。

**追问链**：
1. 一个租户突然把流量拉高十倍怎么办？→ 租户自己的令牌桶先挡住，返回 429 加 `Retry-After`；同时保证网关对上游的总增长平滑，避免触发上游的爬坡限制。
2. 怎么验证降级链真的能用？→ 定期故障演练：人为让主部署失败，看切换延迟、切换后的质量评测、报警是否触发。
3. 用户关掉网页，后台任务要不要停？→ 看产品约定。长任务可以继续，但断开超过重连窗口且用户没有选择“后台运行”时，视为取消，取消传到上游流和正在跑的工具。
4. 月底账单和计量对不上？→ 计量时记下单价版本和缓存读写的分项；失败、被取消的调用也要记下已产生的 token；上游是否计费以服务方文档为准。

**易错点**：
- 只讲路由，不讲租户隔离和计量。
- 把所有失败都在网关重试，和 Runtime、SDK 的重试叠在一起。

## harness-gw-008 网关的 RPM、ITPM、OTPM 三维令牌桶怎么做准入和结算
- level: 3
- tags: [harness, inference]

**一句话答案**：三个桶同时检查，都够才一起扣，否则都不扣并返回最长等待时间；输入扣未缓存输入加缓存写，输出按估计预扣；结束后按实际用量退还或记欠账；单请求超过桶容量直接拒绝。

**要点**：
- 令牌桶余额 b(t) = min(C, b(t₀) + r·(t − t₀))，不够时等待 (x − b)/r；容量 C 决定能容忍多大突发，C 只有一秒的量时 60 RPM 就是每秒 1 个。
- Anthropic 的 ITPM 只计 `input_tokens` 和 `cache_creation_input_tokens`，缓存读不计；文档例子：2M ITPM、命中 80% 时一分钟能处理 10M 输入。
- 上游 OTPM 按实际生成实时计算，不看 `max_tokens`；网关按 `max_tokens` 预扣会把上游没有的限制加回来。
- 欠账：实际超过预扣时余额变负，后面的请求等补充填上。

**追问链**：
1. 为什么不能分开扣？→ 请求桶扣了、token 桶不够被拒，请求桶白少一个；并发时还会出现部分扣成功的竞态，所以要原子执行（Redis 里用一段 Lua 脚本）。
2. 预扣按什么估？→ 按 `max_tokens` 最保守但占配额，OTPM 10 万、`max_tokens` 8192 同时只能放 12 个；常见折中按历史 P90 预扣，允许欠账。
3. 请求比桶容量还大怎么办？→ 返回不可重试的错误，提示压缩上下文；回 429 会让客户端无限重试。

**易错点**：
- 把缓存读也计入 ITPM，高估需要的配额。
- 准入时三个桶各扣各的，不保证原子。

## harness-gw-009 熔断的滑动窗口和失败阈值怎么定，窗口太小有什么问题
- level: 3
- tags: [harness, core]

**一句话答案**：在误跳闸率和检测延迟之间取舍：正常失败率 p₀ 下窗口误跳闸的概率按二项分布算，故障失败率 p₁ 下约 k/p₁ 个请求才跳闸；高流量时窗口按请求数取大，低流量时加最小请求数。

**要点**：
- P(误跳闸) = Σ_{i≥k} C(n,i)·p₀^i·(1−p₀)^(n−i)。
- 推导：p₀ = 2% 时，n = 5、k = 3 的窗口误跳闸概率约 7.8×10⁻⁵，每秒 100 个请求一天约 670 次；n = 20、k = 10 时约 1.6×10⁻¹²。
- 检测延迟：p₁ = 60% 时大窗口约 17 个请求，每秒 100 个时不到 0.2 秒。
- 只计服务端错误：400、413 计入会让一个租户的坏请求熔断整个部署；冷却时间不短于 `retry-after`；半开只放一个试探。

**追问链**：
1. 主部署挂起不报错，熔断还有用吗？→ 有，前提是把首字超时计入失败。模拟里没有熔断时 2,000 个请求都白等 10 秒，有熔断时只有 29 个打到坏部署。
2. 缩短首字超时能代替熔断吗？→ 不能。首字超时决定每个请求白等多久，熔断决定多少请求白等；只缩短超时，坏部署照样吃满流量。
3. 模型组里大部分部署同时失败怎么办？→ 多半是上游整体过载或网关自身问题，限制摘除比例（Envoy 的 `max_ejection_percent`），避免把剩下的一个压垮。

**易错点**：
- 只说“失败率超过 50% 就熔断”，不讲窗口大小和最小请求数。
- 把所有 4xx 都计入熔断。

## harness-gw-010 模型的流式输出中途断了，网关怎么处理已经生成的部分
- level: 3
- tags: [harness, inference]

**一句话答案**：没收到 `message_stop` 就算不完整；已结束的块保留，未结束的文本块保留已收到的文字，半截工具调用和思考块丢掉；交给 Runtime 选续写或重来，不静默重发。

**要点**：
- SSE 解析按 WHATWG 规则：CRLF、LF、CR 都能分行，空行分发，`:` 开头是注释，多行 data 用换行拼接，末尾没空行的半个事件不分发。
- Anthropic 流：`message_start` → 每个块 start、delta、stop → `message_delta`（usage 是累计值）→ `message_stop`，中间可夹 `ping` 和 `error`。
- 续写：Claude 4.5 及以前把部分回复放进 assistant 消息开头；4.6 及以后改为 user 消息带上部分回复并要求继续。
- 计费：断流前的输出已产生；从头重来要把已生成部分再付一遍。

**追问链**：
1. 为什么不能静默重发整条请求？→ 已推给用户的文字收不回，重发会出现重复开头，前后内容也可能不一致。
2. 网络包把 CRLF 切成两半会怎样？→ 前一包末尾的 CR 已结束一行，后一包开头的 LF 若再算成空行，会提前分发事件；解析器要记住上一包以 CR 结尾。
3. 200 之后上游过载怎么表现？→ 只能以 `error` 事件出现，例如 `overloaded_error`，状态码已经是 200，网关要看事件而不是状态码。

**易错点**：
- 把 `message_delta` 的 usage 相加，输出 token 记多。
- 把半截工具参数当成完整 JSON 去执行。

## harness-gw-011 语义缓存的相似度阈值怎么定，为什么不能按命中率定
- level: 3
- tags: [harness, core]

**一句话答案**：按期望成本定：查找开销加未命中的调用加错误命中乘错误代价；错误代价超过盈亏点时语义缓存不如精确缓存。命中率最高的阈值往往错误命中也最多。

**要点**：
- 成本(τ) = ℓ + (1 − g − b)·1 + b·c_w，g 是正确命中率，b 是错误命中率，c_w 是错一次折合的调用数。
- 盈亏点 c_w* = 1 + ((g − g₀) − Δℓ)/b，b 在分母，降一点错误命中率就能大幅提高可容忍的代价。
- 数值例子（假设分布）：τ = 0.90 时正确命中约 54%、错误命中约 4.7%；c_w = 50 时每请求成本约 2.76，比不缓存还贵。
- 实体不同的请求（“取消订单 A”和“取消订单 B”）相似度和换说法很近，阈值分不干净；做法是把实体纳入精确匹配。

**追问链**：
1. 错误命中率怎么估？→ 在真实流量样本上标注“该命中 / 不该命中”，按阈值扫描算误报率。
2. 阈值调到很高是不是就安全了？→ 错误少了，但多出的正确命中也很少，查找开销占大头，可能不如只用精确缓存。
3. Agent 的多轮请求能用语义缓存吗？→ 基本不能：上下文每轮都不同，还可能带工具调用和副作用；只给无状态、事实稳定的单轮问答。

**易错点**：
- 用命中率作为上线指标。
- 缓存键不带租户和权限范围。
