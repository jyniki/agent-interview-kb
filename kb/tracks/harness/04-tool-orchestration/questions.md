# 题目：工具注册、路由、并发与错误恢复

> 对应知识章：[README.md](README.md)。先闭卷作答，再看答案。

## harness-tool-001 工具注册表里要存哪些字段，为什么不能只存给模型看的定义
- level: 2
- tags: [harness, core]

**一句话答案**：除了名称、描述、输入 schema，还要存只给执行器用的字段：输出 schema、副作用类别、是否幂等、超时与并发上限、来源和版本、结果长度上限；这些决定能否并行、能否重试、要不要审批。

**要点**：
- 模型只用名称、描述和参数 schema 选工具；执行、限流、重试、审批都要额外信息。
- 副作用类别分只读、可逆写、不可逆写，同时供并发闸门和权限层使用。
- 记录工具版本，回放时才知道当时调用的是哪一版。
- 第三方 MCP 工具的 `readOnlyHint`、`idempotentHint` 等注解只是提示，规范说不能依据不可信服务端的注解做决策，要自己标注，默认按最危险处理。

**追问链**：
1. MCP 注解的默认值是什么？→ `readOnlyHint` 默认 false，`destructiveHint` 默认 true，`idempotentHint` 默认 false，`openWorldHint` 默认 true，也就是默认假设有破坏性。
2. 多个 MCP 服务都有 `search` 工具怎么办？→ 工具名只在单个服务端内唯一，聚合时加服务端前缀；规范提醒 `serverInfo` 里的名字不保证唯一，不能拿它区分。
3. 工具列表在 Task 中途变了怎么办？→ 常见做法是 Task 开始时冻结快照，变更下一个 Task 生效。改工具定义会让 prompt 缓存整体失效。

**易错点**：
- 把注册表等同于发给模型的 tools 数组。
- 相信第三方工具自己声明的“只读”，就让它并行或自动重试。

## harness-tool-002 工具有几百个，怎么决定每轮给模型看哪些
- level: 2
- tags: [harness, core]

**一句话答案**：常驻一小组高频工具，其余按需加载：可以先分类路由、或用请求检索工具描述取 top-k、或给模型一个工具搜索工具让它自己找；权限过滤放在检索之后，并保留搜索入口兜底漏召回。

**要点**：
- 全量加载最简单、前缀最稳定，但工具多时占满上下文，相似工具容易选错。
- 检索式选择：RAG-MCP 先对工具描述做语义检索，报告 prompt token 减少一半以上，选择准确率也高于全量放入的基线。
- 模型侧工具搜索：Anthropic 的 `defer_loading` 让工具不进初始上下文，文章报告 token 减少 85%，建议常驻三到五个最常用工具。
- 代价：每次搜索多一步延迟；检索漏召回时模型根本看不到正确工具。

**追问链**：
1. 怎么评测检索式选择？→ 单独测检索召回率，再测端到端成功率。只看端到端，分不清是没召回还是召回了没选对。
2. 动态加载工具会不会破坏 prompt 缓存？→ 会有影响。OpenAI 的工具搜索把加载的工具放在上下文末尾以保住前缀；Anthropic 文档说延迟工具不在初始 prompt 里，缓存仍可用。自己实现时把新工具追加在后面，不改前面的定义。
3. 无权限的工具要不要让模型检索到？→ 不要。检索后先按租户和用户过滤，模型看不到就不会去调，也少一次被拒。

**易错点**：
- 只说“用 RAG 选工具”，不说漏召回的兜底。
- 把工具数量上限当成硬规则。OpenAI 的“少于 20 个”是软性建议，要实测。

## harness-tool-003 模型一轮发了五个工具调用，执行器怎么跑
- level: 2
- tags: [harness]

**一句话答案**：模型决定发几个，执行器决定怎么跑：只读调用并行，写操作按给出顺序串行；每个调用过按工具和按租户的并发限制，各自超时；部分失败不影响其他调用，所有结果按调用 ID 对上，一起写回。

**要点**：
- Anthropic 文档说 API 不规定执行顺序；独立只读操作通常可并行，有副作用、共享状态或顺序要求的更适合串行。
- Claude Agent SDK 的做法：只读工具并发，`Edit`、`Write`、`Bash` 这类修改状态的工具串行，自定义工具设了 `readOnlyHint` 才并行。
- 写回格式：Anthropic 要求一轮的所有 `tool_result` 放在同一条 user 消息里且排在最前；拆成多条消息会让模型以后更少并行。
- 慢调用到超时就写回超时错误，不让整批一直等。

**追问链**：
1. 两个写操作改同一个文件呢？→ 按资源加锁，同一路径的写互斥；做不到就整体串行。
2. 模型把有依赖的两个调用并行发了怎么办？→ 执行器不替模型推断依赖；第二个调用会因参数错误失败，错误写回后模型会改成分步调用。
3. 什么时候要关掉并行？→ 下游要求严格顺序，或者模型容易重复调用同一工具时。Anthropic 在 `tool_choice` 里设 `disable_parallel_tool_use: true`，OpenAI 设 `parallel_tool_calls: false`。

**易错点**：
- 一个调用失败就把整批取消，或者少写回一个结果。少回结果在 Anthropic API 上会直接报错。
- 只限总并发，不按工具限，结果某个下游被打满。

## harness-tool-004 工具调用超时了，能不能直接重试
- level: 3
- tags: [harness, core]

**一句话答案**：不一定。超时不等于没执行：只读调用可以退避重试；有副作用的调用只有带幂等键才能重试，否则先查询是否已执行；重试只放在一层，并受 Task 剩余 deadline 约束。

**要点**：
- Brooker（AWS）的原话意思是：超时或失败不代表副作用没发生，有副作用的 API 不提供幂等就不能安全重试。
- 幂等键用 Task ID 加步骤编号生成，崩溃恢复后同一步重做也是同一个键。Stripe 的做法是保存第一次的响应，重试同一键直接返回，参数不同就报错。
- 重试只放一层：五层各试三次，底层负载可达 243 倍。常见做法是执行器负责重试，关掉工具 SDK 的自动重试，模型只处理语义错误。
- 超时值按下游延迟的高分位定，并受整个 Task 的截止时间约束。

**追问链**：
1. 超时后要不要通知下游？→ 要发取消。MCP 在 Streamable HTTP 下关闭响应流就是取消，stdio 下发 `notifications/cancelled`；取消可能晚到，两边都要处理竞态。
2. 工具一直发进度通知，超时怎么算？→ MCP 规范允许收到进度时重置计时，但建议（SHOULD）始终有一个最大超时。
3. 幂等键下游会存多久，恢复时间晚于这个窗口怎么办？→ Stripe（API v1）的键至少保留 24 小时；超出窗口就不能靠键去重，先查询执行状态再决定，查不清交给人。

**易错点**：
- 执行器、工具 SDK、模型三层都在重试，故障时把下游打垮。
- 以为“超时 = 失败 = 可以重来”，导致重复扣款或重复发消息。

## harness-tool-005 工具返回的结果五花八门，怎么做归一化和校验
- level: 2
- tags: [harness]

**一句话答案**：执行器把所有返回整理成统一结构：状态、错误类别、是否可重试、可操作的错误信息、截断后的内容和截断提示；按输出 schema 校验，不符合按错误处理；外部内容留在工具结果块里，不拼进系统提示。

**要点**：
- 错误分类决定谁处理：临时错误执行器重试；参数错误交模型改；权限拒绝写回原因；协议错误修注册表；致命错误降级或终止。
- MCP 区分协议错误（JSON-RPC error）和工具执行错误（结果里 `isError: true`），建议把执行错误交给模型自我纠正。
- 截断时告诉模型总量和缩小范围的办法，否则它以为结果就这么多。
- 工具版本、耗时等元数据进日志，不一定给模型看。

**追问链**：
1. schema 校验通过就够了吗？→ 不够。格式对不代表内容对，例如参数填错导致空结果，模型会以为没有数据。空结果也附提示。
2. 错误信息怎么写？→ 写清哪里错、应该怎么改。Anthropic 文档的例子是写“限流，60 秒后重试”，而不是只写“failed”。
3. 为什么外部内容不能放进系统提示？→ 工具结果可能带间接注入。Anthropic 文档建议不可信内容留在 `tool_result` 块里。防注入的完整设计见 [core/10](../../../core/10-safety-reliability/README.md)。

**易错点**：
- 把堆栈或原始 HTML 直接写回。
- 吞掉错误返回空字符串，模型以为成功了。

## harness-tool-006 模型反复调同一个工具，或者编造参数，Harness 怎么处理
- level: 3
- tags: [harness, evaluation]

**一句话答案**：死循环用确定规则检测：规范化参数的哈希重复、同一错误连续出现、单工具调用超限；触发后先提示，再犯就在本 Task 内禁用。参数幻觉靠严格模式、程序注入已知值、来源检查。

**要点**：
- 检测键是工具名加规范化参数的哈希；首次触发时返回已有结果并提示。
- 规范化参数要去掉顺序、空白、大小写差异，否则改一个空格就绕过检测。
- 严格模式（Anthropic 的 `strict: true`）用语法约束采样，只保证输入符合 schema、工具名有效，管不了“格式合法但编造”的值。
- 来源检查：ID 必须出现在本 Task 之前的工具结果里，否则执行前拒绝，并提示先调哪个查询工具。
- 输入示例对格式约定有效，Anthropic 报告复杂参数的处理准确率有提升。

**追问链**：
1. 重复调用一定是坏事吗？→ 不一定。轮询任务状态就是合法重复。注册表里标出可轮询的工具，并对它单独设间隔和次数上限。
2. 怎么证明你的检测规则没误伤？→ 在评测集上同时报两个数：被拦下的循环数和被误拦的正常任务数，后者要接近零。
3. 参数总填错，是加校验还是改描述？→ 先改描述和加示例。Anthropic 文档说调用无效通常意味着信息不够。校验是兜底，不能代替描述。

**易错点**：
- 只靠步数上限防死循环，等打满预算才停。
- 以为开了严格模式就不会有参数幻觉。

## harness-tool-007 设计一个编程助手的工具执行层
- level: 3
- tags: [harness, core]

**一句话答案**：按调用生命周期设计：注册表（标副作用和幂等）→ 工具选择 → 参数和来源校验 → 权限 → 并发闸门 → 带超时和幂等键执行 → 结果归一化 → 写回和日志；失败写回结构化错误，加循环检测和预算兜底。

**要点**：
- 工具分三类：只读（读文件、搜索、看 git 日志）并行；本地写（改文件）按路径加锁串行；对外写（推送、发评论、调外部 API）串行、带幂等键、需要审批。
- 选择：读写文件、搜索、运行测试常驻；第三方 MCP 工具延迟加载，靠检索或工具搜索。
- 执行：单步超时按下游高分位，受 Task 截止时间约束；只在执行器一层重试临时错误。
- 结果：测试输出、日志按长度截断，保留失败用例和末尾报错，附缩小范围的提示。
- 观测：每次调用记工具版本、参数哈希、耗时、错误类别，供回放和成本统计。

**追问链**：
1. `Bash` 既能读也能写，怎么归类？→ 默认按写处理、串行；可以按命令前缀做白名单，例如 `git status`、`ls` 视为只读。最终边界靠沙箱，见 [03 章](../03-sandbox-permissions/README.md)。
2. 运行测试要 10 分钟，怎么不卡住 Loop？→ 作为后台任务启动，立即返回任务 ID；模型用查询工具取进度，查询工具单独限频。最大超时仍然要有。
3. 怎么评测这一层？→ 构造故障注入用例：工具超时、返回超长、返回格式错、下游限流、模型编造 ID，看每类是否走到了预期分支，同时看正常任务的成功率和平均调用次数。
4. 第三方 MCP 服务突然变慢怎么办？→ 对这个工具单独熔断，熔断期间直接返回“暂不可用”的结构化错误，让模型换路。熔断的实现见 [05 章](../05-gateway-reliability/README.md)。

**易错点**：
- 只画“模型 → 工具 → 结果”三个框，不讲失败路径。
- 并发、重试、权限各讲各的，不说清它们在一次调用里的先后顺序。

## harness-tool-008 检索式选工具时，为什么召回率是端到端成功率的上界，top-k 怎么定
- level: 3
- tags: [harness, evaluation]

**一句话答案**：成功要求正确工具先进候选、再被选中，E(k) = R(k)·S(k) ≤ R(k)。k 越大召回越高，但候选越多越难选对，乘积在中间取最大；要分别测召回和条件选择准确率，再按实测定 k。

**要点**：
- R(k)：正确工具在 top-k 里的概率；S(k)：在候选里时模型选对的概率。
- 失败可拆成 (1 − R) + R·(1 − S)：没检索到，和检索到了没选对。
- 常驻一个搜索工具兜底，漏召回时还能找回一部分：E = R·S + (1 − R)·f·S。
- RAG-MCP 表 1 报告：prompt token 2133.84 → 1084，选择准确率 13.62% → 43.13%（对比全量放入）。

**追问链**：
1. 只看端到端成功率会怎样？→ 分不清该改检索（索引、描述、k）还是改描述和示例，两类失败混在一起。
2. k 取全部工具是不是最稳？→ 召回为 1，但 S(k) 最低、上下文最贵，端到端往往不是最好。
3. 权限过滤放在检索前还是后？→ 检索之后过滤，模型看不到无权工具；评测召回时用过滤前的候选，避免把权限当成漏召回。

**易错点**：
- 以为换更强的模型就能弥补检索漏召回。
- 不留搜索工具兜底，漏召回直接变成失败。

## harness-tool-009 一批有依赖的工具调用，已知总工作量 W、关键路径 C、并发上限 P，总耗时下界是多少
- level: 3
- tags: [harness]

**一句话答案**：T ≥ max(C, W/P)。关键路径上的调用只能顺序跑，P 个槽位在 T 内最多做 P·T 的工作。加速比上限是 W/C，P 超过 W/C 再加没用；同资源写的隐式依赖会拉长 C。

**要点**：
- 串行时 T = W；并行加速比不超过 W/C。
- 同一文件的写按模型给出的顺序加依赖边，所以按资源加锁比“所有写串行”好：只拉长同资源那条链。
- 贪心调度（依赖满足就派发）不保证达到下界；可以按到终点的最长剩余路径排优先级。
- 例子：W = 7、C = 4、P = 3，下界 4，加速比上限 1.75。

**追问链**：
1. 依赖关系谁给？→ 数据依赖一般由模型分轮发，或由规划器输出 DAG（LLMCompiler 用 `$1` 占位符）；资源冲突由执行器从参数解析；下游容量用按工具的信号量，不是依赖边。
2. 上游失败了下游怎么办？→ 不执行，写回 `dependency_failed`，其他独立调用照常完成。
3. 依赖有环呢？→ 执行前用拓扑排序（Kahn）检查，有环就一个都不执行，写回错误。

**易错点**：
- 以为并发上限越大越快，忽略关键路径。
- 一个调用失败就取消整批，或者跳过的调用不写结果。

## harness-tool-010 调用栈 n 层各自尝试 r 次，下游会被放大多少倍，重试预算怎么限住它
- level: 2
- tags: [harness, core]

**一句话答案**：最底层收到 r^n 倍请求，五层各三次是 243 倍。只在执行器一层重试；再加重试预算：重试占比低于 ρ 才重试，下游全挂时总流量不超过 1/(1 − ρ)，ρ = 10% 约 1.11 倍。

**要点**：
- Agent 里的层：模型重发、执行器、工具 SDK、下游服务。关掉 SDK 自动重试，模型只处理语义错误。
- 单请求上限（Google SRE：最多三次）挡不住大面积故障，全挂时仍是 3 倍。
- R/(F + R) < ρ 推出 R < F·ρ/(1 − ρ)。
- 退避用 Full Jitter：uniform(0, min(cap, base·2^n))；不加抖动最差。

**追问链**：
1. 预算怎么实现最省事？→ 令牌桶：每个首次请求存 ρ 个令牌，每次重试花 1 个，不够就不重试。
2. 重试会不会越过 Task 的截止时间？→ 等待前检查剩余 deadline，等完就超时就不重试，直接写回 `deadline_exceeded`。
3. 模型调用的重试也放在执行器吗？→ 不，放在模型网关，同样只在一层并受预算约束，见 harness/05。

**易错点**：
- 每层都“保守地重试三次”，以为互不影响。
- 用不带抖动的固定间隔或纯指数退避，客户端同时醒来再次打满下游。
