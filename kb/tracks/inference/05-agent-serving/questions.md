# 题目：面向 Agent 的推理

> 对应知识章：[README.md](README.md)。先闭卷作答，再看答案。

## infer-serve-001 Agent 请求和聊天请求在推理负载上有什么不同
- level: 1
- tags: [inference, harness]

**一句话答案**：Agent 一次任务调用模型很多轮，每轮输入是之前全部内容加新工具结果：输入长、输出短、前缀高度重复，中间还要等工具；成本集中在 Prefill，前缀复用是第一优化点，输出还要能被程序解析。

**要点**：
- 输入：系统提示、工具定义、全部历史、工具结果，越来越长。
- 输出：常常只是一次工具调用或一段 JSON。
- 前缀：第 k 轮的前缀就是第 k−1 轮的完整输入加输出。
- 停顿：等工具期间缓存可能被淘汰。
- 监控要把 TTFT（首 token 延迟）和 TPOT（每输出 token 延迟）分开看。

**追问链**：
1. 那 PD 分离对 Agent 有用吗？→ Prefill 占比高时有用，但要按命中前缀缓存后的实际 Prefill 量评估，见 [02 章](../02-batching-pd/README.md)。
2. 为什么输出短也重要？→ 输出短意味着 Decode 阶段时间少，单纯优化 Decode 吞吐的手段收益有限。

**易错点**：
- 用聊天场景的“输入短、输出长”假设去估 Agent 的成本。

## infer-serve-002 现场估算：系统提示加工具定义 6,000 token，每轮新增 1,500 token，共 10 轮，前缀缓存能省多少 Prefill
- level: 2
- tags: [inference, harness]

**一句话答案**：系统提示加工具 6,000 token、每轮新增 1,500 token、共 10 轮时，不复用要 Prefill 127,500 token，完美复用只要 19,500 token，约省 85%。

**要点**：
- 第 k 轮输入：6,000 + 1,500 × (k − 1)。
- 不复用总量：Σ_{k=1}^{10} = 10 × 6,000 + 1,500 × (0 + 1 + … + 9) = 60,000 + 67,500 = 127,500。
- 复用：每轮只算新增，总量等于最后一轮长度 6,000 + 13,500 = 19,500。
- 19,500 / 127,500 ≈ 15%。
- 轮数越多，不复用的成本按轮数平方增长，复用后按轮数线性增长。

**追问链**：
1. 实际达不到 85% 的原因？→ 前缀被改写（时间戳、重排工具、去掉思考内容）；等工具时缓存被淘汰；多副本路由到别的实例；块粒度下尾部不足一块要重算。
2. 换成托管 API 怎么算钱？→ 把命中部分按缓存读价、首次写入按缓存写价、其余按普通输入价分别计算。以 Anthropic 为例，读是 0.1 倍，5 分钟 TTL 写是 1.25 倍。
3. 这个会话最后占多少 KV？→ 按 Qwen3-8B 每 token 144 KiB，19,500 token 约 2.9 GB。

**易错点**：
- 以为复用后总量是“每轮 1,500 × 10”。第一轮的 6,000 也要算一次。

## infer-serve-003 vLLM 的前缀缓存和 SGLang 的 RadixAttention 有什么区别
- level: 2
- tags: [inference]

**一句话答案**：两者都复用最长公共前缀的 KV；vLLM 按块链式哈希，只缓存满块；RadixAttention 用基数树按 token 管理缓存前缀，LRU 淘汰叶子，配合按前缀长度排序的缓存感知调度。

**要点**：
- vLLM 块哈希 = f(前一块哈希, 本块 token id, 额外信息如 LoRA ID、多模态哈希、cache salt)。
- 请求结束后块进入空闲队列但保留哈希；从队头按 LRU 淘汰；一个请求的块逆序放入队尾，最长前缀的尾块最先被淘汰。
- RadixAttention：树放在 CPU，节点有引用计数，运行中使用的节点不可淘汰；先淘汰叶子，公共祖先保留更久。
- 缓存感知调度：等待队列按匹配前缀长度排序，最长共享前缀优先。

**追问链**：
1. 为什么块哈希要包含前一块的哈希？→ 同样的 token 在不同前缀后面 KV 不同；链式哈希让“哈希相同”等价于“从头到这里的前缀相同”。
2. 为什么哈希里要带 LoRA ID？→ 适配器改变了中间层输出，后续层的 K、V 不同，不能共用。
3. 最长前缀优先调度有什么风险？→ 前缀不常见的请求可能一直排在后面，需要防饥饿或限制重排范围。

**易错点**：
- 说“RadixAttention 比前缀缓存省显存”。它们省的是重复计算，KV 大小本身一样。

## infer-serve-004 多副本部署时怎么让多轮会话命中缓存
- level: 2
- tags: [inference, harness]

**一句话答案**：前缀缓存只在单实例有效，所以网关要做亲和路由：按会话 ID 粘滞，或维护各实例的前缀索引、把请求发给缓存了最长前缀的实例；同时和负载均衡做权衡，过载或故障时退回普通负载均衡，接受一次重算。

**要点**：
- 会话粘滞：实现简单，多轮必命中；热点会话会压垮单机，实例故障时缓存全失效。
- 前缀感知：不同会话共享系统提示也能命中；网关要分词、维护索引。
- SGLang 路由组件提供 `cache_aware`（默认至少匹配 1,024 token）和 `session_aware`，都在没有合适实例时退回负载均衡。
- Harness 配合：稳定内容放前面、动态内容放后面、历史只追加。

**追问链**：
1. 工具执行很慢，缓存被淘汰了怎么办？→ 设工具超时上限；引擎支持时把 KV 换出到 CPU 内存；托管 API 上评估更长的缓存 TTL。
2. 怎么知道亲和路由有没有效果？→ 监控前缀命中率（命中 token / prompt token）和 TTFT 分位数，按会话轮次分桶看。

**易错点**：
- 只做会话粘滞，不设退回策略，长会话把单个实例拖垮。

## infer-serve-005 流式输出里工具调用怎么解析
- level: 2
- tags: [inference, harness]

**一句话答案**：服务端用模型对应的解析器把工具调用标记抽成结构化增量；客户端按 index 聚合 id、name 和分片的 arguments，结束原因为 tool_calls 后再解析 JSON 并校验。

**要点**：
- 结束原因字段是 `finish_reason`。
- 标记例如 Hermes 格式的 `<tool_call>`；增量在 `delta.tool_calls[]` 里，每项带 `index`。
- 一次回复可能有多个并行工具调用，所以必须按 index 聚合。
- arguments 分片不是合法 JSON，不能逐片 `json.loads`。
- 服务端流式解析要扣住可能是半个起始标签的后缀，不能误当普通文本输出。
- 官方文档提醒参数可能不合法或带 schema 外字段，执行前要校验，失败时把错误作为工具结果返回模型。

**追问链**：
1. 想在参数还没生成完时就展示给用户怎么办？→ 用容错的增量 JSON 解析器展示，但执行工具一定等完整参数。
2. 模型在同一回复里先输出文本再调用工具，客户端怎么处理？→ content 增量和 tool_calls 增量分开累积，文本可以直接流给用户。

**易错点**：
- 收到第一个带 name 的分片就执行工具。

## infer-serve-006 约束解码怎么保证输出合法，代价是什么
- level: 3
- tags: [inference, harness]

**一句话答案**：每步解码前按语法算出合法 token 集合，其余 logits 置为负无穷；正则和简单 JSON 编译成有限状态机，嵌套结构用上下文无关文法；代价是合法不等于正确、首次编译有延迟、会扭曲模型分布。

**要点**：
- 上下文无关文法用下推自动机执行。
- Outlines：把正则编译成 FSM，并预建“状态 → 合法 token”的索引。
- SGLang 压缩 FSM：只有一条出路的连续边合并，确定的部分一步解码多个 token。
- XGrammar：词表分为可预处理缓存的上下文无关 token 和少量运行时检查的上下文相关 token；语法计算与 GPU 计算重叠；论文报告比已有方案最多快 100 倍。
- vLLM：`tool_choice` 为 required 或指定函数时用结构化输出约束；auto 模式默认只用解析器，除非工具声明 strict 或打开严格级别。

**追问链**：
1. 为什么说约束会伤质量？→ 它强行截断了模型的概率分布；如果 schema 和训练时见过的格式差很多，模型被迫走低概率路径。常见缓解是先让模型在约束外推理，再约束输出最终结构。
2. 为什么 JSON schema 不能都用 FSM？→ 任意深度嵌套需要栈，正则表达不了，要下推自动机；FSM 只能处理展开到有限深度的结构。
3. 约束解码和投机解码一起用要注意什么？→ 草稿 token 也要经过语法检查，验证和回退时语法状态要同步回滚。

**易错点**：
- 以为开了约束解码就不用做参数校验。它只保证语法合法，不保证值对、不保证调用了正确的工具。

## infer-serve-007 推导：系统提示 S 个 token、每轮新增 D 个 token、共 n 轮，不复用和完美前缀复用的 Prefill 总量各按什么阶增长
- level: 2
- tags: [inference, harness]

**一句话答案**：不复用是 nS + D·n(n−1)/2，按轮数平方增长；完美复用是 S + (n−1)D，即最后一轮的长度，按线性增长；比值趋近 2/n。注意力部分各高一阶：三次降到平方。

**要点**：
- 第 k 轮输入 P_k = S + (k−1)D，不复用是对 P_k 求和。
- 复用后每轮只算新增部分，总量等于 P_n。
- 上一轮的模型输出在 Decode 时已写进 KV，理想下限是 S + (n−1)·r，r 是工具结果长度。
- 注意力：位置 t 的查询看 t 个键。不复用时每轮约 P_k²/2，总量 ~n³；复用后总量等于一次 Prefill 完 P_n 的注意力，~n²。
- 复用后注意力占比上升，所以 FLOPs 省的比例略小于 token 省的比例。

**追问链**：
1. 为什么复用后注意力不是线性？→ 每个新 token 仍要看完整的长前缀，省掉的只是对旧 token 的重算。
2. 实际能达到理想下限吗？→ 块对齐每轮多算不到一块，可以忽略；模板去掉思考、等工具时被淘汰、路由到别的副本才是主要损耗。

**易错点**：
- 把复用后的总量算成 n·D，漏了第一轮的 S。
- 以为前缀复用后 Prefill 成本与上下文长度无关。

## infer-serve-008 vLLM 前缀缓存为什么整段 prompt 都命中也要重算一部分，块大小怎么影响命中
- level: 2
- tags: [inference]

**一句话答案**：要输出最后位置的 logits，至少现算一个 token，命中又按块对齐，所以可能重算最后一整块。共享 m 个 token 只命中 ⌊m/B⌋·B，改动所在的块及之后全部失效。

**要点**：
- 只缓存写满的块，尾块不进缓存。
- 链式哈希：第一次不命中就停，后面的块不可能再命中。
- RadixAttention 页大小默认 1，命中可以停在任意 token 上。
- 多轮 Agent 每轮新增远多于一块，块粒度的损失摊得很薄；大量短请求共享不对齐的前缀时差距才明显。

**追问链**：
1. 块大小设成 1 不就没损失了吗？→ 块表变长，kernel 读写不能充分并行，哈希和查表次数也变多；块大小是访存效率和共享粒度的取舍，见 inference/01。
2. 同一段内容会不会存两份？→ 会。V1 块表只能追加，请求自己算出的块即使和已缓存块哈希相同也不能替换，请求释放后才消除重复。

**易错点**：
- 以为两请求共享 10 个 token、块大小 4 时能命中 10 个，实际只命中 8 个。

## infer-serve-009 Agent 等工具的几十秒里，会话的 KV 是留在显存、换出到 CPU 还是丢掉重算
- level: 3
- tags: [inference, harness]

**一句话答案**：看上下文长度和工具耗时。长上下文、工具慢时换出最划算，换入比重算快一个数量级；短上下文直接让它被淘汰、重算即可；只有工具很快时才值得留在显存，否则显存被不干活的会话占满。

**要点**：
- 等工具期间块引用计数为 0，处在可淘汰状态。
- 以 Qwen3-8B、19,500 token（约 2.9 GB）为例：重算的理想下限约 436 ms，按 PCIe Gen5 单向约 64 GB/s 换入约 45 ms。
- 等工具占 5/6 时间时，钉在显存的会话平均只有 1/6 在用 GPU。
- vLLM 用 `--kv-offloading-size` 开 CPU 卸载；SGLang 用 `--enable-hierarchical-cache`。
- 托管 API 上对应的是缓存 TTL 的选择。

**追问链**：
1. 怎么发现缓存在等工具时被淘汰了？→ 按距上一轮的间隔分桶看命中率和 TTFT 的 P99，看是否随负载变化。
2. 换出有什么代价？→ 占 CPU 内存，换入延迟和 KV 大小成正比，拷贝和其他传输争 PCIe 带宽。

**易错点**：
- 以为请求结束后 KV 一定还在。前缀缓存只是“暂时不删”，负载高时很快被淘汰。

## infer-serve-010 XGrammar 为什么要把词表分成上下文无关和上下文相关 token
- level: 3
- tags: [inference]

**一句话答案**：压栈和规则内前进只看栈顶，这类 token 可按栈顶节点预计算并缓存；只有出栈返回父规则的 token 要看整个栈，运行时再查。后者很少，所以每步掩码生成很快。

**要点**：
- 嵌套 JSON 需要栈，FSM 状态有限，表达不了任意深度，要用 PDA 执行 CFG。
- 论文报告：Llama-3.1 词表、JSON 文法下上下文相关 token 不到 1%（128k 里 1,134 个），上下文扩展后再减 90%。
- 掩码生成只用 CPU，和 GPU 前向重叠，采样前同步。
- 持久化栈让回滚变成改指针，方便重新分词和投机解码回退。

**追问链**：
1. 举一个上下文相关 token 的例子？→ `},`：闭合一层之后，逗号合不合法要看再往上一层是对象还是数组；单独的 `}` 只看栈顶就够。
2. 约束解码开了，为什么还会解析失败？→ `max_tokens` 截断不归文法管；`auto` 模式下没设 `strict` 时根本没加约束。

**易错点**：
- 以为约束解码保证调用的工具和参数值正确，它只保证语法合法。
