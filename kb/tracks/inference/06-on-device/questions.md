# 题目：端侧部署：模型选型、运行时与端云协同

> 对应知识章：[README.md](README.md)。先闭卷作答，再看答案。

## infer-device-001 端侧部署模型受哪些约束
- level: 1
- tags: [inference]

**一句话答案**：内存（权重加 KV 要放进和系统共用的 DRAM）、延迟（batch=1 的 Decode 受内存带宽限制）、功耗（每 token 能耗随参数量增长）和发热（持续负载会降频）。

**要点**：
- MobileLLM 论文：iPhone 15 的 DRAM 6 GB，Pixel 8 Pro 12 GB；论文认为单个应用不应超过 DRAM 的 10%。
- 能耗粗估：每十亿参数每 token 约 0.1 J；7B 约 0.7 J/token，350M 的 8-bit 模型约 0.035 J/token。
- 端侧几乎都是 batch=1，Decode 速度上限 ≈ 内存带宽 / 权重字节。
- 发热降频要看持续负载下的速度，不能只看第一分钟。

**追问链**：
1. 假设每 token 约 0.7 J、满电约 50 kJ，7B 模型以 10 token/s 能连续生成多久？→ 50,000 / 0.7 ≈ 7 万 token，约 2 小时。
2. 为什么不能像服务器那样靠拼 batch 提速？→ 端侧只有一个用户，请求并发低，带宽瓶颈躲不掉，只能减小要读的字节。

**易错点**：
- 只算权重不算 KV。端侧小模型在几千 token 上下文时 KV 就能和 INT4 权重相当。

## infer-device-002 现场估算：Qwen3-1.7B（28 层、8 个 KV 头、head_dim 128）按 Q4_K 约 4.5 bit/权重量化，4K 上下文、BF16 KV，在 12 GB 手机上要多少内存，能否控制在 DRAM 的 10% 以内
- level: 2
- tags: [inference]

**一句话答案**：Q4_K 按 4.5 bit/权重算，权重约 0.96 GB；每 token KV 112 KiB，4K 上下文约 0.47 GB；合计约 1.43 GB，超过 12 GB 设备 10% 的预算。

**要点**：
- 12 GB 设备的 10% 即 1.2 GB。
- config：28 层，16 个 Q 头、8 个 KV 头，head_dim 128，词表 151,936，`tie_word_embeddings: true`。
- 计算过程：
  - 权重：1.7e9 × 4.5 / 8 ≈ 0.96 GB
  - 每 token KV：2 × 28 × 8 × 128 × 2 = 114,688 B
  - 4K：114,688 × 4,096 ≈ 0.47 GB
  - 合计 ≈ 1.43 GB
- 降下来的办法：KV 量化到 8 bit（≈ 1.19 GB），锁短上下文，或换 0.6B。

**追问链**：
1. 换 Qwen3-0.6B 呢？→ 层数、KV 头数、head_dim 相同，每 token KV 仍是 112 KiB；Q4 权重约 0.34 GB，4K 时合计约 0.81 GB，KV 比权重还大。
2. 嵌入层占多少？→ 151,936 × 2048 ≈ 0.31B 参数，约占 1.7B 的 18%；共享输入输出嵌入省掉同样大的一块。
3. 假设有效带宽 50 GB/s，Decode 多快？→ 0.96 GB / 50 GB/s ≈ 19 ms/步，上限约 50 token/s，未计 KV 读取。

**易错点**：
- 以为“模型小一半，KV 也小一半”。KV 只和层数、KV 头数、head_dim、上下文长度有关。

## infer-device-003 llama.cpp、MLC LLM、ExecuTorch 怎么选
- level: 2
- tags: [inference]

**一句话答案**：llama.cpp 用 GGUF 单文件、后端覆盖广，适合桌面和跨平台；MLC LLM 基于 TVM 编译，有移动和浏览器 SDK；ExecuTorch 从 PyTorch 导出，便于接 NPU。

**要点**：
- MLC LLM 提供 iOS、Android 和浏览器 SDK；ExecuTorch 导出 `.pte` 文件。
- ExecuTorch 按后端划分子图。
- llama.cpp 构建文档列有 CPU、Metal、CUDA、Vulkan、OpenCL（Adreno）、CANN、Hexagon 等后端，macOS 默认开 Metal。
- GGUF 同时存张量和标准化元数据；Q4_K 约 4.5 bit/权重。
- MLC LLM 的流程是转换权重、编译模型库、配置量化、打包。
- ExecuTorch 后端有 XNNPACK、Core ML、Vulkan、Qualcomm、MediaTek 等；不支持的算子回退 CPU。

**追问链**：
1. 选型先看什么？→ 目标设备和芯片、模型结构的算子是否都被目标后端支持、团队现有工具链（PyTorch 还是 GGUF 生态）。
2. 怎么验证？→ 在真机上测首 token 时间、每 token 速度、持续负载后的速度和耗电，不信桌面上的数字。

**易错点**：
- 背一套“哪个最快”的排名。性能和设备、模型、量化格式强相关，要实测。

## infer-device-004 NPU、GPU、CPU 怎么取舍
- level: 2
- tags: [inference]

**一句话答案**：NPU 能效最高但算子覆盖有限、工具链绑定厂商；GPU 通用、Prefill 快但更耗电发热；CPU 兼容性最好但 Prefill 慢。Decode 受带宽限制时三者差距变小，NPU 主要优势是省电。

**要点**：
- ExecuTorch 文档：后端不支持的算子回退 CPU，只能部分加速；不同后端算子支持不同，要在每台目标设备上测。
- 新的注意力结构常常没有 NPU kernel，一次回退可能抵消收益。
- Prefill 是算力瓶颈，硬件差异明显；Decode 是带宽瓶颈，三者共用同一块内存。

**追问链**：
1. 一个算子回退会有多大影响？→ 数据要在 NPU 和 CPU 之间来回搬，图被切开，可能比全跑 CPU 还慢。
2. 什么任务最适合放 NPU？→ 常驻、结构固定、算子都被支持的小模型，例如意图识别、唤醒后的短指令理解。

**易错点**：
- 默认“NPU 一定最快”。没核对算子支持和真机数据前不能下结论。

## infer-device-005 端侧小模型怎么得到：蒸馏和剪枝
- level: 2
- tags: [inference, training]

**一句话答案**：蒸馏让小模型匹配大模型在高温 softmax 下的软目标；剪枝从大模型裁掉层、宽度、头或 MLP 维度再蒸馏恢复，所需训练数据远少于从头训练。

**要点**：
- Hinton 等：提高温度 T 让教师输出更平滑，学生同温训练，推理时 T = 1。
- Minitron：从 Nemotron-4 15B 剪到 8B、4B；论文报告重训只用了不到 3% 的原始训练数据，训练 token 比从头训少最多 40 倍，MMLU 比从头训同尺寸模型最高高 16%。
- MobileLLM：1B 以下深而窄优于浅而宽，嵌入共享、GQA、相邻块权重共享。
- Agent 用途要专门蒸馏工具调用轨迹，测格式和参数正确率。

**追问链**：
1. 软目标为什么比硬标签有用？→ 错误答案之间的相对概率带有教师学到的相似性信息。
2. 剪深度还是剪宽度？→ Minitron 两种都实验了，要按目标尺寸和评测选；面试时说清“剪完必须蒸馏恢复，并在目标任务上评测”。

**易错点**：
- 只用 MMLU 评估端侧小模型。小模型的短板常在指令遵循和工具调用格式。

## infer-device-006 设计一个端侧 Agent 的端云路由
- level: 3
- tags: [inference, harness]

**一句话答案**：先在本地做敏感信息检测和难度判断：涉及本地隐私或离线时强制本地，简单单步任务留本地，复杂规划、长上下文、需要联网工具的送云端；端侧结果置信度低或校验失败再升级，上传前做最小化和脱敏。

**要点**：
- 路由依据：难度、隐私、网络、成本。
- 方法：规则分流；学习式路由（RouteLLM 用偏好数据训练路由器，论文报告部分设置下成本降到一半以下且质量不降）；级联升级。
- 隐私：只传任务需要的最小片段；本地存储加密并设保留期；日志只记元数据。
- 端云两个模型要统一工具协议和输出格式。

**追问链**：
1. 路由错了有什么代价？→ 难题留本地会答错；简单题送云端浪费钱、增加延迟、多一次数据外传。
2. 级联的代价？→ 被升级的请求多花一次端侧推理时间，所以端侧要能快速判断“不行”，例如用格式校验或置信度阈值。
3. 怎么评估路由器？→ 用真实请求回放，画出“云端调用比例—任务成功率”曲线，按目标成功率选阈值；单独统计敏感请求是否全部留在本地。
4. 弱网时云端超时怎么办？→ 设超时回退到本地，给用户降级提示，记录待网络恢复后重试的任务。

**易错点**：
- 只按难度路由，忘了隐私是硬约束，必须在路由前判断。

## infer-device-007 估算题：有效内存带宽 50 GB/s 的手机上，1.7B 模型按 4.5 bit/权重量化、每 token KV 112 KiB，batch=1 时 Decode 每秒最多几个 token，4K 上下文时呢
- level: 2
- tags: [inference]

**一句话答案**：每步读一遍权重和全部 KV，tokens/s ≈ 带宽 / 每步字节。只读 0.96 GB 权重约 52 token/s；4K 上下文加 0.47 GB KV，约 35 token/s。都是上限。

**要点**：
- 每步计算约 2N FLOPs，读取约 N·w/8 字节，INT4 时算术强度约 3.6 FLOP/B，远低于芯片的“算力/带宽”比值，所以受带宽限制。
- 每步字节 = N·w/8 + T × 每 token KV；50 / 0.956 ≈ 52，50 / (0.956 + 0.470) ≈ 35。
- 真机更慢：有效带宽低于标称，还有反量化、kernel 启动和调度开销。
- Prefill 相反，强度约等于 prompt 长度，受算力限制。

**追问链**：
1. 把位宽从 4.5 降到 2.25 会怎样？→ 权重字节减半，只读权重时上限翻倍；上下文长时 KV 不变，收益小于 2 倍。
2. 换到 NPU 会更快吗？→ 不一定。NPU、GPU、CPU 共用同一块 DRAM，Decode 看带宽；NPU 的主要好处是省电。
3. 为什么实测速度随上下文下降？→ 每步要读的 KV 随 T 线性增长，几千 token 后就和权重同量级。

**易错点**：
- 用算力（TOPS）估 Decode 速度。batch=1 的 Decode 由读取字节决定。

## infer-device-008 剪枝加蒸馏为什么比从头训练小模型省数据，Minitron 怎么做
- level: 2
- tags: [inference, training]

**一句话答案**：剪后的模型继承了大模型的大部分权重，重训只需让剩下的结构重新配合。Minitron 用前向激活给头、神经元、通道和层打分后剪枝，再只用 logits 的 KL 蒸馏重训。

**要点**：
- 重要性估计只用前向，在 1024 条校准样本上算激活，不需要反向传播。
- 论文报告：重训用了不到 3% 的原始训练数据（94B token），每个额外模型的训练 token 比从头训少最多 40 倍。
- 整个 15B、8B、4B 模型族的算力只省 1.8 倍：最大的模型仍要完整训一遍，(4.4+2.5+1.2)/(4.4+2.5/40+1.2/40) ≈ 1.8。
- 最佳实践：≤15B 时剪宽度优于剪深度；深度剪得多时蒸馏要加中间层状态；从最接近目标尺寸的模型剪起。

**追问链**：
1. 蒸馏温度怎么选？→ Hinton 的高温经验来自分类模型；Minitron 在 LLM 上试了 0.1 到 3.0，τ = 1.0 最好，因为 LLM 的 logits 分布本身熵就高。
2. 同时用硬标签和软目标时为什么乘 T²？→ 软目标梯度的量级按 1/T² 缩小，不乘的话换温度就改变了两项的相对权重。

**易错点**：
- 把“每个模型少 40 倍 token”说成“整个模型族省 40 倍算力”。

## infer-device-009 估算题：端侧延迟 0.6 s、云端延迟 1.2 s、端侧不计费，先本地试再上云的级联要求端侧成功率多高才比全部上云快
- level: 3
- tags: [inference, harness]

**一句话答案**：级联期望延迟 t_l + (1−p)·t_c，小于 t_c 要求 p > t_l / t_c = 0.5。成本上端侧不计费时省下的比例就是 p。前提是端侧错误能被校验出来。

**要点**：
- 校验器召回为 r 时：期望成本 c_l + (1−p)·r·c_c，期望延迟 t_l + (1−p)·r·t_c，漏给用户的错误 (1−p)(1−r)。
- p = 0.7、r = 1 时，成本降到全云端的 30%，延迟 0.96 s。
- 端侧变慢（如长 prompt 的 Prefill）会抬高门槛：t_l = 1.0 s 时 p 要超过约 0.83。
- 成功率低于门槛的请求类型应由规则或路由器直接送云端；RouteLLM 报告学习式路由让成本降到一半以下且质量不降。

**追问链**：
1. 校验器召回只有 0.8 会怎样？→ 钱和时间更省，但 p = 0.7 时有 6% 的请求拿到错误答案，省下的是用质量换的。
2. 哪些任务适合级联？→ 输出可校验的：结构化输出能用 Schema 检查，工具参数能用规则检查。开放式生成更适合提前路由。
3. 隐私放在代价模型的哪里？→ 放在前面作为硬约束，命中就留本地，不参与代价比较。

**易错点**：
- 只算成本不算延迟：端侧失败的请求多付了一次端侧时间。
