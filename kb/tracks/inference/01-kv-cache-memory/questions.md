# 题目：KV Cache 与显存估算

> 对应知识章：[README.md](README.md)。先闭卷作答，再看答案。

## infer-kv-001 Prefill 和 Decode 的瓶颈为什么不同
- level: 1
- tags: [inference, core]

**一句话答案**：Prefill 一次并行处理整段 prompt，矩阵乘很大，每读一字节权重做很多计算，受算力限制；Decode 每步只算一个 token，却要读全部权重和全部 KV，受显存带宽限制。

**要点**：
- Prefill：并行算出所有位置的 K、V，写入缓存，输出第一个 token。
- Decode：矩阵乘退化成矩阵乘向量，算得少、读得多，算力用不满。
- batch=1 时 Decode 单步时间下界 ≈ 权重字节 / 显存带宽；上下文越长，读 KV 的时间越多。
- 估算方法：Prefill 用 FLOPs / 算力估，Decode 用读取字节 / 带宽估。

**追问链**：
1. 那怎么提高 Decode 的吞吐？→ 把多个请求拼成 batch，权重读一次服务多个 token，见[连续批处理](../02-batching-pd/README.md)；或减少要读的字节，例如量化、GQA。
2. 两个阶段混在一个 batch 里会怎样？→ 长 Prefill 会拖慢同一步的 Decode，让正在输出的请求卡顿；分块 Prefill 和 PD 分离就是处理这个问题的。
3. 什么时候 Decode 会变成算力瓶颈？→ batch 足够大，使每读一字节权重做的计算超过硬件的算力带宽比时。

**易错点**：
- 说“KV Cache 减少了注意力的计算复杂度”。注意力本身仍要和全部历史做点积，省的是重算历史 K、V 的投影和前面各层的计算。
- 把两个阶段都按 FLOPs 估时间，算出的 Decode 速度远高于实际。

## infer-kv-002 现场估算：一个 36 层、8 个 KV 头、head_dim 128、参数 8.2B 的 BF16 模型，在一张 80 GB 卡上能放几条 32K 会话
- level: 2
- tags: [inference]

**一句话答案**：每 token KV = 2×36×8×128×2 B = 144 KiB，32K 约 4.8 GB；72 GB 可用扣掉 16.4 GB 权重和 4 GB 预留，剩约 51.6 GB，约 10 条。

**要点**：
- config：36 层，32 个 Q 头、8 个 KV 头，head_dim 128，BF16，参数 8.2B。
- 计算过程：
  - 每 token：2 × 36 × 8 × 128 × 2 = 147,456 B
  - 32K：147,456 × 32,768 ≈ 4.83 GB
  - 权重：8.2e9 × 2 ≈ 16.4 GB
  - KV 空间：80 × 0.9 − 16.4 − 4 ≈ 51.6 GB
  - 条数：51.6 / 4.83 ≈ 10.7，取 10 条
- 预留比例和激活预留是假设值，要明说。

**追问链**：
1. 如果是 MHA 呢？→ KV 头从 8 变 32，每 token 变成 4 倍，32K 一条约 19.3 GB，只能放 2 条。
2. KV 改用 FP8 呢？→ 每元素 1 字节，每 token 减半，约能放 21 条；精度影响见量化章。
3. 实际会话不都是满 32K，怎么估？→ 用平均长度而不是最大长度估并发；PagedAttention 按实际长度分配，所以平均长度才是对的口径。

**易错点**：
- 忘了 K 和 V 的 2 倍，或者用 Q 头数 32 代替 KV 头数 8。
- 把 GB 和 GiB 混着用，结果差 7% 左右。面试时说清用哪个即可。

## infer-kv-003 MHA、MQA、GQA、MLA 的 KV 大小怎么比
- level: 2
- tags: [inference, core]

**一句话答案**：每 token 每层缓存元素数：MHA 是 2·n_h·d_h，MQA 是 2·d_h，GQA 是 2·n_g·d_h，MLA 是 d_c + d_h^R。MLA 的缓存比 GQA 还小。

**要点**：
- MQA 所有 Q 头共享一组 K、V，KV 最小，论文报告质量有轻微下降。
- GQA 是两者之间的折中，n_g 可调；可以从 MHA 检查点均值池化合并 KV 头，再用约 5% 的预训练计算量上训练得到。
- MLA 缓存低秩潜向量 c^KV（DeepSeek-V2 中 d_c = 512）加解耦的 RoPE 键（d_h^R = 64）。
- DeepSeek-V2：60 层 × 576 × 2 B = 69,120 B/token，约为 MHA 口径的 1.8%，相当于 2.25 组的 GQA。

**追问链**：
1. MLA 推理时要把潜向量展开成多头 K、V 吗？→ 不用。W^UK 可以吸收进 W^Q，W^UV 可以吸收进 W^O，直接在潜空间算注意力。
2. 为什么要单独缓存 RoPE 键？→ RoPE 是位置相关的旋转，夹在中间会让 W^UK 无法吸收进 W^Q，所以用一小段独立维度承载位置信息。
3. MLA 有什么代价？→ 结构复杂，需要专门 kernel；KV 量化方案要按它的缓存布局重做，不能直接套 MHA 的实现。

**易错点**：
- 说“GQA 减少了注意力头数”。Q 头数不变，减少的是 KV 头数。

## infer-kv-004 PagedAttention 解决了什么问题，没解决什么
- level: 2
- tags: [inference]

**一句话答案**：它解决的是 KV 显存的预留、内部碎片和外部碎片三类浪费，以及跨序列共享 KV 的问题；它不减小每个 token 的 KV 大小。

**要点**：
- 论文测量：之前系统里真正存 token 状态的显存只占 20.4% 到 38.2%。
- 做法：KV 切成固定大小的块（vLLM 默认 16 token），每个请求一张块表映射逻辑块到物理块，物理块不必连续。
- 浪费只剩每个请求最后一个没写满的块。
- 引用计数加写时复制，支持并行采样、束搜索和共享前缀。
- 论文报告：相同延迟下吞吐是 FasterTransformer、Orca 的 2 到 4 倍。

**追问链**：
1. 块大小怎么选？→ 小块尾部浪费少但块表长、寻址多；大块读得高效但浪费多、共享粒度粗。论文实验里长序列（ShareGPT）16 到 128 都好，短序列（Alpaca）只有 16 和 32 好；默认取 16。
2. 它对 kernel 有什么要求？→ attention kernel 要按块表间接寻址读 KV，新的 attention 实现都要支持分页布局。
3. 写时复制什么时候触发？→ 某序列要往引用计数大于 1 的块里写新 token 时，先复制出一个新块再写。

**易错点**：
- 说“PagedAttention 压缩了 KV Cache”。要压缩得靠 GQA/MLA 或 KV 量化。

## infer-kv-005 用带宽估算 Decode 的速度上限：8B 模型 BF16、H100 SXM 显存带宽 3.35 TB/s，batch = 1
- level: 3
- tags: [inference]

**一句话答案**：batch=1 时每步至少读一遍全部权重，单步下界 ≈ 权重字节 / 带宽：16.4 GB / 3.35 TB/s ≈ 4.9 ms，上限约 200 token/s；长上下文还要加读 KV 的时间。

**要点**：
- 权重：8.2e9 参数 × 2 B ≈ 16.4 GB。
- 计算过程：16.4e9 / 3.35e12 ≈ 4.9e-3 s；1 / 4.9 ms ≈ 204 token/s。
- 32K 上下文时每步还要读约 4.83 GB 的 KV，单步下界变成 (16.4 + 4.83) / 3.35 ≈ 6.3 ms。
- 这是理论下界，实际还有 kernel 效率、调度、通信开销。
- 结论：Decode 速度由每步读多少字节决定，所以量化权重、减小 KV、组 batch 都有效。

**追问链**：
1. batch 从 1 加到 32，单步时间怎么变？→ 权重只读一次，单步时间增长远小于 32 倍，吞吐近似线性上升；但每个请求的 KV 都要读，KV 部分随 batch 线性增长，长上下文时它会成为新瓶颈。
2. 什么时候 Decode 会变成算力瓶颈？→ batch 足够大，使每读一字节权重做的计算超过硬件的算力带宽比时。
3. 为什么 Prefill 不这么算？→ Prefill 一次处理成百上千个 token，计算量大，瓶颈在算力，用 FLOPs / 算力估。

**易错点**：
- 用 NVIDIA 产品页上标注“with sparsity”的 TFLOPS 估 Decode 速度。Decode 首先看带宽，而且稀疏算力不是稠密模型能拿到的数。

## infer-kv-006 推理显存和训练显存差在哪
- level: 1
- tags: [inference, training]

**一句话答案**：推理只要权重、KV Cache 和少量临时激活；混合精度 Adam 训练每参数要存 FP16 权重和梯度加 FP32 的权重副本和两个动量，ZeRO 论文给出每参数 16 字节，还不含激活。

**要点**：
- 推理权重：BF16 每参数 2 字节。
- 训练模型状态：2（权重）+ 2（梯度）+ 12（FP32 权重、动量、方差）= 16 字节/参数。
- 推理的大头往往是 KV；训练的大头是优化器状态和激活。
- 推理激活不保留给反向传播，峰值由单次 Prefill 的 token 数决定，可用分块 Prefill 控制。

**追问链**：
1. 8B 模型全参训练，只算模型状态要多少？→ 8.2e9 × 16 ≈ 131 GB，一张 80 GB 卡放不下，需要 ZeRO 切分或 LoRA。
2. RL 训练里的 rollout 阶段算推理还是训练？→ 推理，要按本章的 KV 公式估，这是 Agentic RL 里显存紧张的原因之一。

**易错点**：
- 把推理显存也按“参数量 × 16”估，严重高估。
