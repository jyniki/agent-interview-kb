# 题目：轨迹与长程任务评测

> 对应知识章：[README.md](README.md)。先闭卷作答，再看答案。

## eval-traj-001 轨迹评测里哪些规则该写、哪些不该写，为什么不规定调用顺序
- level: 2
- tags: [evaluation, harness]

**一句话答案**：只写不依赖路径、对应真实失败代价的规则：禁用工具、写前确认、轮次和预算上限、重复调用次数。不规定调用顺序，因为正确路径不止一条，按顺序判会误杀，还会逼团队贴合标准轨迹；成败交给终态判。

**要点**：
- τ-bench：`r = r_action × r_output`，比对数据库终态和必须告知的信息，读操作和对话可以不同。
- τ-bench 论文承认 r = 1 只是必要条件：未经用户明确确认就执行退货，仍会判成功。
- Anthropic 的评测工程文章反对规定工具调用顺序，建议评产出而非路径。
- 每条轨迹规则都应对应真实失败代价。
- 终态为主、轨迹规则为辅：终态允许多条正确路径、判定客观，但漏掉过程违规和成本，轨迹规则补这一块。

**追问链**：
1. 只看终态会漏掉什么具体问题？→ 越权或违规的中间操作、成本十倍、碰巧做对。
2. 规则判不了的过程问题怎么办？→ 让校准过的评委看轨迹，或人工抽读，不直接写成固定路径。
3. 终态是“对话内容”而不是数据库时怎么办？→ 把必须包含的信息写成可检查项（τ-bench 用子串匹配），软项交给评委。

**易错点**：
- 拿一条标准轨迹逐步比对，把另一条正确路径判错，团队开始为贴合标准轨迹改提示。

## eval-traj-002 怎么评测 Agent 的工具调用
- level: 2
- tags: [evaluation, harness]

**一句话答案**：在固定上下文下做单步评测，查五件事：该不该调、选对工具没有、参数能否过 schema、参数值是否和上下文一致、报错后是否合理处理；可执行时直接执行看结果，不能执行时按 AST 比对。

**要点**：
- BFCL 的 AST 评测：函数名一致；必填参数齐全，文档外参数算幻觉；类型严格；取值在可接受集合内，字符串归一后比较。
- 多个调用顺序可不同，但一个期望调用没匹配上就整题错。
- 相关性检测：没有合适函数时，正确输出是不调用。
- 输入从线上轨迹里截取，固定下来做回归。

**追问链**：
1. 每一步都做单步评测吗？→ 不，只给最容易错、对下游影响大的步骤做，通常是路由和工具选择；流程一改就要重标，维护成本高。
2. 参数值“合法但不对”怎么判？→ 和上下文比对，例如订单号必须来自用户给出的那个；这类检查可以写成代码。
3. 单步全对，端到端还会错吗？→ 会。每步都对拼起来也可能绕路或前后矛盾，终态评测不能省。

**易错点**：
- 只测“该调时调了”，不测“不该调时没调”。

## eval-traj-003 长程 Agent 任务的评测只有成败 0/1 分，怎么设计部分得分
- level: 3
- tags: [evaluation, training]

**一句话答案**：拆成按依赖顺序排列、带权重的检查点，检查点查状态不查路径，按拿到的检查点给部分得分；完成整个任务单独给分，保证没完成的低于完成的，避免鼓励做一半就停。

**要点**：
- TheAgentCompany 用 `S_partial = 0.5 × 得分/总分 + 0.5 × S_full`。
- 检查点可以查动作是否完成、产出是否正确、是否完成必要沟通；多数用确定性函数，主观产出用带 rubric 的评委。
- 例：8 分拿 4 分没完成，得 0.25。
- 部分得分能做“卡点分布”：大多数试次停在哪个检查点。
- Anthropic 文章：核实了身份但没退款的 Agent，应高于一开始就失败的。
- 每个试次从干净环境开始，避免共享状态让分数虚高。

**追问链**：
1. 为什么后一半分数只给完成的？→ 保证没完成的永远低于完成的，防止 Agent 靠做大量简单步骤刷分。
2. 部分得分能直接当 RL 奖励吗？→ 可以缓解奖励稀疏，但检查点设计不好会被钻空子，要监控完成率是否同步上升。
3. 检查点权重怎么定？→ 按对最终目标的重要性和不可替代性定，由领域专家审；汇报时同时给完成率和部分得分。

**易错点**：
- 检查点写成“第 3 步必须调用某工具”，又回到了规定路径。

## eval-traj-004 Agent 评测通过率掉了 5 个点，怎么做失败归因
- level: 3
- tags: [evaluation, harness]

**一句话答案**：读失败轨迹，按“评分器或题目 → 环境 → 工具 → 上下文 → 模型决策”逐类排除；先找第一个决定性错误步骤，不是最后报错那步；环境失败不计入能力分；自动归因只当初筛。

**要点**：
- 评分器或题目错：输出合理却被判错；多个版本都在同一题失败。
- 环境：超时、限流、5xx、脏状态。
- 工具：返回错数据，或描述和行为不一致。
- 上下文：截断、检索没召回、长对话遗忘约束。
- 模型：信息都在，却选错工具或违反规则。
- Who&When：最好的自动方法找对责任 Agent 约 53.5%，找对错误步骤只有 14.2%。

**追问链**：
1. 为什么先排除评分器？→ 评分器误杀会伪装成能力退化；Anthropic 文章建议读过轨迹之前不按字面相信分数。
2. 怎么知道是上下文问题而不是模型问题？→ 把缺失的信息补回上下文重跑；补了就对，是上下文问题。
3. 自动归因三种方法怎么选？→ 一次性最便宜、找 Agent 好；逐步找步骤好但最贵；二分居中。可以先一次性定 Agent，再逐步查该 Agent 的步骤。

**易错点**：
- 把最后报错的步骤当根因。
- 把基础设施失败也算进模型能力分。

## eval-traj-005 多 Agent 系统的评测比单 Agent 多了什么
- level: 2
- tags: [evaluation, core]

**一句话答案**：除了端到端结果，还要给每个子 Agent 单独评测，评协作本身（交接、重复劳动、互相验证），并在同一评测集上和单 Agent 基线比成功率、成本和延迟；失败归因可用 MAST 三类。

**要点**：
- MAST：7 个框架的轨迹，14 种失败模式，分为系统设计问题、Agent 间未对齐、任务验证不足三类；标注者间 kappa 0.88。
- 每个 Agent 的输入输出要单独记录，否则无法归因。
- 多 Agent 收益要覆盖额外成本。

**追问链**：
1. 为什么一定要比单 Agent 基线？→ 多 Agent 增加了成本和失败点，没有基线就说不清它是不是值得。
2. “任务验证不足”类失败是什么？→ 没人检查结果，或检查流于形式，错误一路传到终态。
3. 怎么评交接质量？→ 检查下游 Agent 需要的关键信息是否出现在交接消息里，可写成检查点。

**易错点**：
- 只看端到端分数。整体掉分时不知道是哪个 Agent 的问题。

## eval-traj-006 给你一个编程助手 Agent，设计它的轨迹评测方案
- level: 3
- tags: [evaluation, harness]

**一句话答案**：终态用测试判，修复测试由失败变通过、回归测试保持通过；轨迹规则查危险命令、改动范围、步数和 token 预算；关键步骤做单步评测；长任务设检查点；隔离环境多次运行报 pass^k；失败按固定表归因。

**要点**：
- 终态参考 SWE-bench 的 FAIL_TO_PASS / PASS_TO_PASS。
- 单步评测的关键步骤：定位文件、工具调用。
- 终态：两组测试全过才算解决；测试覆盖不到的地方补人工或评委抽检。
- 轨迹规则：不执行危险命令，不改与任务无关的文件，不删测试，步数和 token 上限。
- 单步：是否找到正确文件；工具调用参数是否合法。
- 检查点：能复现问题、定位到正确模块、修复通过、回归通过。
- 环境：每个试次从干净仓库开始，避免读到之前试次留下的痕迹。
- 指标：解决率、pass^k、每任务 token 和耗时、违规操作数。
- 归因：评分器（测试是否会拒绝正确解）→ 环境（依赖安装失败）→ 工具 → 上下文 → 模型。

**追问链**：
1. Agent 改测试让它通过怎么办？→ 判定用的测试由评测方自己应用，不用 Agent 工作区里的版本（SWE-bench 的流程中测试补丁由评测框架应用）；同时把“修改测试文件”写成轨迹规则。
2. 测试本身会拒绝正确的另一种解法怎么办？→ 这是题目问题。SWE-bench Verified 专门剔除了这类题；自己的题集要人工核验并保留参考解。
3. 题从哪来？→ 真实 issue 和历史修复提交，脱敏后取修复前的代码和修复后的测试；先 20-50 题起步。

**易错点**：
- 只看测试通过率，不看改动范围和危险操作。
- 多个试次共用同一个工作目录。

## eval-traj-007 Agent 评测里终态分和过程分怎么组合成一个分数，为什么不用加权求和
- level: 3
- tags: [evaluation, harness]

**一句话答案**：用 O·G·(α + (1−α)P)：终态 O 和门控 G（违规、副作用）相乘，没做成或违规直接为 0；做成后过程分 P 只调整 1−α 的部分。加权求和会让没做成也有分，违规被别的高分抵消。

**要点**：
- 只看终态漏三类：过程违规、侥幸成功、副作用。
- 副作用检查：初始状态和终态做差，白名单之外的变化都算副作用，不用预先想到会改坏什么。
- 过程分可由关键步骤覆盖率（只查做没做，不查顺序）和无效步骤比例组成。
- Anthropic 文章列出加权、二元（全过才过）、混合三种组合。
- 没做成的试次另用检查点部分得分衡量，两个分数分开报。

**追问链**：
1. 评委对轨迹的判断该放进 G 还是 P？→ 放 P。评委有误判，放进门控会一票否决正确解；放进过程分只影响 1−α 的部分。
2. 侥幸成功 pass^k 能发现吗？→ 能发现不稳定的那部分，多跑几次会失败；发现不了稳定地违规，例如每次都不确认就写，只能靠过程规则。
3. α 怎么定？→ 看成本和步数在这个任务上多重要；只关心成没成就令 α = 1，退化成 O·G。

**易错点**：
- 规则写成“第 k 步必须调某工具”，换一条正确路径就被误杀。
- 归因只看 O = 0 的试次，漏掉被门控拦下的侥幸成功和副作用。

## eval-traj-008 每步成功率 p、任务 n 步时，成功率降到 50% 要多少步，纠错率 r 怎么改变它
- level: 2
- tags: [evaluation, core]

**一句话答案**：由 p^n = 0.5 得 n ≈ 0.693/(1−p)，和单步错误率成反比。纠错后等效错误率为 (1−p)(1−r)，半衰期约放大 1/(1−r) 倍；改错要花步数，预算上限会吃掉部分收益。

**要点**：
- p = 0.95 约 13.5 步，p = 0.99 约 69 步；错误率减半，半衰期约翻倍。
- p = 0.95、r = 0.6：等效 0.98，半衰期约 2.5 倍（精确 2.54）。
- 平均单步成功率相同时，难度集中在少数步骤的任务整体成功率更低：乘积是几何平均的 n 次方。
- 模型假设步与步独立，真实任务里不成立，只给方向。

**追问链**：
1. 这说明单步评测够不够？→ 不够。单步 95% 的 20 步任务只剩约 36%，且单步评测测不到纠错。
2. 步数上限怎么影响结果？→ 纠错要额外步数，上限太紧会截断本可纠正的试次；失败集中在上限附近时就是这个原因。
3. 换成连续时间是什么模型？→ 每分钟恒定失败率 λ，成功率 exp(−λt)，50% 时长 ln2/λ。

**易错点**：
- 把“平均单步正确率”直接取 n 次方当整体成功率，忽略难步集中的影响。

## eval-traj-009 METR 的 50% 任务时长怎么从 0/1 结果里拟合出来，80% 时长为什么短好几倍
- level: 3
- tags: [evaluation]

**一句话答案**：t 取人类成功时长的几何平均，对每个模型拟合 p = σ((log h − log t)β)，h 即 50% 时长。推出 h/t_0.8 = 4^(1/β)，短 4–6 倍对应 β≈0.8–1。

**要点**：
- 连续分数按代表人类水平的阈值二值化；每个模型每任务约 8 次。
- 同族任务结果相关，按 1/√族大小降权；论文称趋势对正则和加权选择不敏感。
- 借鉴 IRT 的 2PL，但难度直接用 log 人类时长，只拟合模型参数。
- 论文报告 50% 时长约每 7 个月翻倍；80% 时长翻倍时间相近，本身短 4 到 6 倍。4^(1/β) 是本章推导。
- 误差条来自任务族、任务、运行三层 bootstrap。

**追问链**：
1. 任务时长只覆盖很短的任务会怎样？→ 拟合不出 50% 点，h 和 β 很不稳，甚至完全可分；要补齐覆盖 h 两侧的任务。
2. 这个度量的局限？→ 依赖任务分布和人类基线的技能水平；人类时长只能部分预测成败；测高成功率时长要大量低噪声任务。
3. 和平均通过率比多了什么？→ 有单位的能力刻度，以及斜率 β 带来的可靠性信息。

**易错点**：
- 把 h 理解成 Agent 自己运行的时长，它是人类完成同类任务的时长。
- 把一个领域拟合出的 h 外推到其他领域。
