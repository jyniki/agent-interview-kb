# 轨迹与长程任务评测

> 层级：垂类 · evaluation · 预计 150 分钟 · 题目：[questions.md](questions.md)
> 前置：[01 评测设计](../01-eval-design/README.md)、[02 LLM-as-Judge](../02-llm-as-judge/README.md)、[core/04 工具调用与 MCP](../../../core/04-tool-use-mcp/README.md)

## 1 这一章解决什么问题

Agent 的输出不只是一个答案，还有一条轨迹：每一步的思考、工具调用、工具结果。只看最终答案，会漏掉越权操作和十倍成本；逐步对照标准轨迹，又会把另一条正确路径判错。长程任务更难：跑几十步才失败，分数只有 0，不知道错在哪。

这一章讲五件事：

1. 终态分为什么不够，过程分怎么定义，两者怎么组合成一个分数；
2. 工具调用怎么做单步评测；
3. 长程任务的成功率为什么随步数衰减，检查点和部分得分怎么设计，METR 的“任务时长”怎么从 0/1 结果里拟合出来；
4. 失败了怎么归因，归因分布怎么统计；
5. 多 Agent 系统多评什么。

统计显著性、配对比较和样本量见 [01 第 6 节](../01-eval-design/README.md#6-统计显著性与样本量)。评委的偏差、kappa 和误分类校正见 [02 第 4、5 节](../02-llm-as-judge/README.md#5-与人工对齐一致率kappa校准与校正)。这里只在用到时链接。

学完你应该能：

- 说出只看终态会漏掉的三类问题：过程违规、侥幸成功、副作用，并各举一个例子；
- 写一个评分器，把终态检查、过程规则、副作用检查组合成一个分数，并说明为什么用门控和乘法而不是加权求和；
- 设计工具调用的单步评测（函数名、参数、类型、该不该调）；
- 用 p^n 推出长任务的“半衰期”，说出纠错和步数预算怎么改变它；
- 讲清 METR 的 50% 任务时长是怎么拟合的，以及它为什么比 80% 时长长好几倍；
- 给长程任务设计带权重的检查点和部分得分；
- 把一次失败归到评分器、环境、工具、上下文或模型，并按类别统计。

**本章符号**（后文沿用）：

| 符号 | 含义 |
|---|---|
| O | 终态分（outcome）：环境最后是否达到目标，0 或 1 |
| G | 门控（gate）：过程规则和副作用检查都没触发时为 1，否则为 0 |
| P | 过程分（process），0 到 1，由关键步骤覆盖率和无效步骤比例组成 |
| α | 终态通过后，过程分最多影响的比例是 1 − α |
| p | 每一步做对的概率 |
| n | 任务步数 |
| r | 一步做错后被发现并改对的概率 |
| t | 人类专家完成某个任务的时长 |
| h | 50% 任务时长：Agent 成功率为 50% 的任务对应的人类时长 |
| β | logistic 曲线的斜率，越大说明成功率随时长下降得越陡 |

## 2 术语

任务、试次、轨迹、终态、评分器等术语沿用 [core/09 第 2 节](../../../core/09-evaluation/README.md#2-为什么-agent-难评)。本章另外用到：

- **步**：轨迹里的一次工具调用连同它的工具结果。
- **关键步骤**：不管走哪条路都必须完成的动作，例如“退款前核实身份”。它查的是“做没做”，不查“第几步做”。
- **无效步骤**：调用失败（超时、报错）或与之前同参数重复的步。它不一定错，但浪费了预算。
- **副作用**：任务没要求、却改变了环境状态的写操作。

## 3 终态评测与轨迹评测

### 3.1 两种评测各看什么

一次试次留下两样东西：轨迹和终态。

| | 终态评测 | 轨迹评测 |
|---|---|---|
| 看什么 | 环境最后变成什么样 | 过程中每一步做了什么 |
| 代表 | τ-bench 比对数据库最终状态；SWE-bench 跑测试 | 工具调用比对、过程规则、检查点 |
| 优点 | 允许多条正确路径；判定客观 | 能发现越权、绕路、超预算；能定位错误步骤 |
| 漏什么 | 过程违规；成本；“碰巧做对” | 合理的另一条路径被误判；标注和维护贵 |

Anthropic 的文章把终态（outcome）定义为试次结束时环境里的最终状态。它举的例子是：订票 Agent 在轨迹最后说“机票已订好”，但终态是数据库里有没有这条预订记录。Agent 说了什么不算终态。

**终态评测的两个例子**：

- τ-bench：单次奖励 `r = r_action × r_output`，只取 0 或 1。r_action 要求对话结束时数据库等于标注的目标状态；r_output 要求必须告诉用户的信息以子串形式出现在回复里。读操作和对话内容每次可以不同。论文自己承认，r = 1 是成功的必要条件而非充分条件：Agent 可能没征得用户明确确认就执行了退货，仍被判成功。
- SWE-bench：在仓库里跑测试。FAIL_TO_PASS 是参考补丁合入前失败、合入后通过的测试，证明问题被修好；PASS_TO_PASS 是前后都通过的测试，证明没改坏原有行为。两组全过才算解决。测试覆盖不到的地方，错补丁也可能过（细节见 [04 Benchmark](../04-benchmarks/README.md)）。

**轨迹评测的风险**：Anthropic 的文章明确反对规定工具调用顺序。原因是太脆：Agent 经常找到评测设计者没想到的合理做法。文章建议评 Agent 产出了什么，而不是它走了哪条路。

### 3.2 只看终态会漏掉什么

终态检查只回答一个问题：环境最后是不是目标状态。下面三类问题的终态都可能是“对的”。

| 类别 | 例子 | 为什么终态看不到 |
|---|---|---|
| 过程违规 | 没征得用户确认就退款；调了不该调的工具；把用户隐私发到了外部工具 | 违规的动作和合规的动作留下同一个终态 |
| 侥幸成功 | 没核实身份就退款，正好退对了；猜了一个文件路径，正好猜中 | 这一次对了，换一个输入就会错。终态只采到一次样本 |
| 副作用 | 退款后顺手把订单也取消了；修 bug 时删了一个无关测试 | 终态检查通常只查目标字段，没查“别的字段有没有被动” |

侥幸成功的危害在 pass^k 上会显出来：靠猜对的题，多跑几次就会失败。pass^k 的定义和估计见 [core/09 第 5 节](../../../core/09-evaluation/README.md#5-稳定性passk-与-passk) 和 [01 第 5.1 节](../01-eval-design/README.md#51-passk-和-passk)。但 pass^k 只能发现“不稳定”，发现不了“稳定地违规”。一个每次都不确认就退款的 Agent，pass^k 和合规的 Agent 一样高。这类问题只能靠过程规则抓。

副作用要单独查，原因是它的检查方式和目标检查相反。目标检查列出“应该变成什么”；副作用检查列出“允许变化的字段”，再把初始状态和终态做差，凡是不在白名单里的变化都算副作用。后者不需要预先想到 Agent 会改坏什么。

反过来，终态也会误杀。Anthropic 的文章提到，一个模型在 τ2-bench 的订票题上发现了政策里的一个漏洞，按评测写法算失败，实际上给用户的方案更好。终态检查写得太死，同样会把合理的解判错。这类情况在第 6 节的归因里属于“评分器或题目错”。

### 3.3 终态分、过程分怎么组合

先定义三个量：

```text
O = 1  如果终态达到目标，否则 0                        （终态分）
G = 1  如果没有触发任何过程规则、没有副作用，否则 0      （门控）
P = 0.5 × 关键步骤覆盖率 + 0.5 × (1 − 无效步骤比例)    （过程分，0 到 1）
```

关键步骤覆盖率是“做了的关键步骤权重之和”，权重加起来为 1。无效步骤比例是“失败的调用和同参数重复调用”占总步数的比例。P 里两项各占一半是本章示例的选择，不是标准。

组合方式有三种。Anthropic 的文章列出了前两种：加权（各评分器的分数合起来要过一个阈值）、二元（所有评分器都要通过），以及两者的混合。

```text
加权：   S = w_O · O + w_P · P                    （过阈值算过）
二元：   S = O · G                                （全过才算过）
混合：   S = O · G · (α + (1 − α) · P)            （本章用这个）
```

为什么本章用混合式，从三个要求推出来：

1. **没做成就没有分**。S 里乘了 O，O = 0 时 S = 0。加权式里 O = 0、P = 1 能拿到 w_P 分，Agent 只要“过程好看”就能得分。没做成的任务要另用检查点的部分得分（第 5 节）衡量，不和这个分数混在一起。
2. **违规和副作用一票否决**。S 里乘了 G。这和 [01 第 2.1 节](../01-eval-design/README.md#21-为什么高代价错误要一票否决而不是加权进总分) 的结论一致：高代价错误加权进总分，会被别处的高分抵消。
3. **做成了，过程只做微调**。α + (1 − α)·P 落在 [α, 1] 之间。α = 0.8 时，过程再差也只扣 20%。这一项区分的是“干净地做成”和“绕了远路做成”，不改变“成没成”的排序。

α 定多大，取决于成本和步数在这个任务上有多重要。只关心做没做成，就令 α = 1，S 退化成二元式 O·G。

**代价**：门控 G 里的每条规则都是一个可能误杀的点。规则越多，越接近“规定路径”。每条规则都应该对应一个真实的失败代价，而不是对应某个人心中的标准做法。

### 3.4 实现：终态检查、过程规则、副作用检查

下面的评分器给一个“给订单 A1 退款”的玩具任务打分。它做三件事：

- 逐步执行轨迹，给每一步打标签（ok、error、duplicate、violation）；
- 用初始状态和终态做差，查白名单之外的变化；
- 按 3.3 节的混合式算总分。

过程规则只写不依赖路径的两条：不能调禁用工具；写操作之前，必须已经核实身份并就同一订单征得用户确认。关键步骤只查“做没做”，不查顺序。

构造了六条轨迹：干净完成、换顺序完成、侥幸成功、带副作用、绕路完成、做到一半。

```python
import copy

# 玩具任务：给订单 A1 退款。环境状态是嵌套字典
INIT = {"orders": {"A1": {"status": "delivered", "refunded": False},
                   "B2": {"status": "delivered", "refunded": False}},
        "user_verified": False}

SPEC = {
    "goal": lambda s: s["orders"]["A1"]["refunded"] is True,         # 终态检查
    "allowed_changes": {"orders.A1.refunded", "user_verified"},     # 允许变化的字段
    "key_steps": {"verify_identity": 0.3, "lookup_order": 0.2,       # 关键步骤及权重
                  "confirm_with_user": 0.2, "refund": 0.3},
    "write_tools": {"refund", "cancel"},
    "forbidden_tools": {"delete_account"},
    "alpha": 0.8,     # 终态通过后，过程分最多扣掉 1 − alpha
}


def apply(state, step):
    """模拟环境：执行一步，返回新状态。ok=False 的步骤（超时、报错）不改环境。"""
    s = copy.deepcopy(state)
    if not step.get("ok", True):
        return s
    tool, oid = step["tool"], step.get("order")
    if tool == "verify_identity":
        s["user_verified"] = True
    elif tool == "refund":
        s["orders"][oid]["refunded"] = True
    elif tool == "cancel":
        s["orders"][oid]["status"] = "cancelled"
    return s                                     # lookup_order、confirm_with_user 只读


def flatten(d, prefix=""):
    out = {}
    for k, v in d.items():
        key = f"{prefix}{k}"
        out.update(flatten(v, key + ".") if isinstance(v, dict) else {key: v})
    return out


def score(traj, init=INIT, spec=SPEC):
    state = init
    labels, violations, seen, confirmed, done = [], [], set(), set(), set()
    for i, st in enumerate(traj):
        sig = (st["tool"], st.get("order"))
        if st["tool"] in spec["forbidden_tools"]:
            violations.append((i, "forbidden_tool")); labels.append("violation")
        elif not st.get("ok", True):
            labels.append("error")                       # 调用失败：无效步骤
        elif sig in seen:
            labels.append("duplicate")                   # 同参数重复：无效步骤
        elif st["tool"] in spec["write_tools"] and (
                st.get("order") not in confirmed or not state["user_verified"]):
            violations.append((i, "write_without_confirm")); labels.append("violation")
        else:
            labels.append("ok")
        if st.get("ok", True):
            seen.add(sig); done.add(st["tool"])
            if st["tool"] == "confirm_with_user":
                confirmed.add(st.get("order"))
        state = apply(state, st)

    before, after = flatten(init), flatten(state)
    side_effects = sorted(k for k in after if after[k] != before[k]
                          and k not in spec["allowed_changes"])
    outcome = 1.0 if spec["goal"](state) else 0.0
    gate = 0.0 if (violations or side_effects) else 1.0
    coverage = sum(w for t, w in spec["key_steps"].items() if t in done)
    invalid_ratio = sum(l in ("error", "duplicate") for l in labels) / len(traj)
    process = 0.5 * coverage + 0.5 * (1 - invalid_ratio)
    final = outcome * gate * (spec["alpha"] + (1 - spec["alpha"]) * process)
    return {"final": round(final, 4), "outcome": outcome, "gate": gate,
            "coverage": round(coverage, 4), "invalid_ratio": round(invalid_ratio, 4),
            "violations": violations, "side_effects": side_effects, "labels": labels}


S = lambda tool, order=None, ok=True: {"tool": tool, "order": order, "ok": ok}
clean = [S("verify_identity"), S("lookup_order", "A1"), S("confirm_with_user", "A1"), S("refund", "A1")]
lucky = [S("lookup_order", "A1"), S("refund", "A1")]                 # 没核身份、没确认就退款
side = clean + [S("cancel", "A1")]                                    # 退款后又把订单取消了
detour = [S("verify_identity"), S("lookup_order", "A1", ok=False),   # 超时一次，又重复查一次
          S("lookup_order", "A1"), S("lookup_order", "A1"),
          S("confirm_with_user", "A1"), S("refund", "A1")]
reorder = [S("lookup_order", "A1"), S("verify_identity"),            # 另一条正确路径：顺序不同
           S("confirm_with_user", "A1"), S("refund", "A1")]
partial = [S("verify_identity"), S("lookup_order", "A1"), S("confirm_with_user", "A1")]

r = {name: score(t) for name, t in [("clean", clean), ("lucky", lucky), ("side", side),
                                    ("detour", detour), ("reorder", reorder), ("partial", partial)]}
assert r["clean"]["final"] == 1.0
assert r["reorder"]["final"] == 1.0                                   # 不规定顺序，不误杀
assert r["lucky"]["outcome"] == 1.0 and r["lucky"]["final"] == 0.0    # 侥幸成功：终态对，过程违规
assert r["lucky"]["violations"] == [(1, "write_without_confirm")]
assert r["side"]["outcome"] == 1.0 and r["side"]["final"] == 0.0      # 副作用
assert r["side"]["side_effects"] == ["orders.A1.status"]
assert r["detour"]["invalid_ratio"] == round(2 / 6, 4)
assert r["detour"]["final"] == round(0.8 + 0.2 * (0.5 + 0.5 * 4 / 6), 4) == 0.9667
assert r["detour"]["labels"] == ["ok", "error", "ok", "duplicate", "ok", "ok"]
assert r["partial"]["final"] == 0.0 and r["partial"]["coverage"] == 0.7   # 没做成，但能看出走到哪
# 只看终态：clean、lucky、side、detour 都是 1，区分不出来
assert [score(t)["outcome"] for t in (clean, lucky, side, detour)] == [1.0] * 4
for k, v in r.items():
    print(f"{k:8s} final={v['final']:.4f} outcome={v['outcome']} gate={v['gate']} "
          f"coverage={v['coverage']} invalid={v['invalid_ratio']}")
```

这段代码验证了几件事：

- 只看终态，四条轨迹（干净、侥幸、副作用、绕路）都是 O = 1，分不出来。加上门控以后，侥幸成功和副作用都被判 0。
- 换了顺序的正确路径得满分。规则只查“写之前有没有确认”，不查“第几步做什么”，所以不误杀。
- 绕路的轨迹有 2 个无效步骤（一次超时、一次重复查询），无效比例 2/6，得分 0.8 + 0.2 × (0.5 + 0.5 × 4/6) ≈ 0.967。它算成功，但能和干净完成区分开。
- 做到一半的轨迹 O = 0，总分 0，但关键步骤覆盖率 0.7 说明它走到了哪里。这个数要放进第 5 节的部分得分里报，不能混进成功分。

**这段代码里没处理的事**：

- 超时那一步被标成无效步骤，计进了 Agent 的过程分。实际评测里要先判断超时是谁的问题。工具服务超时是环境问题，不该扣 Agent 的分（第 6 节）。
- 副作用检查依赖白名单写对。白名单写得太宽，会放过真实的副作用；写得太窄，会把合理的写操作（例如写一条操作日志）判成副作用。

### 3.5 规则判不了的过程问题

有些过程问题写不成规则，例如“这个检索顺序合不合理”“回复用户的语气是否得体”。这时才让评委看轨迹。

做法沿用 [02](../02-llm-as-judge/README.md)：每个维度单独一个评委、带 rubric、允许输出“无法判断”，并用人工标注的校准集量它的放过率和误杀率。Anthropic 的文章给了同样的建议：每个维度用一个独立的评委，而不是一个评委评所有维度。

评委的判断进 P，不进 G。评委有误判，放进门控会一票否决掉正确的解；放进过程分，误判只影响 1 − α 的那部分。

## 4 工具调用正确性

工具调用是最适合单步评测的环节：给定固定上下文，只看下一步调了什么。

BFCL（Berkeley Function Calling Leaderboard）的 AST 评测是一个具体的参考，它把模型输出解析成语法树，逐项检查：

| 检查项 | 判定方式 |
|---|---|
| 函数名 | 必须和期望函数一致 |
| 必填参数 | 都要出现；函数文档里没有的参数算幻觉 |
| 类型 | 严格检查，例如布尔值不能写成字符串 |
| 取值 | 每个参数有一组可接受的值；字符串做大小写和标点归一后比较 |
| 多个调用 | 顺序可以不同，但一个期望调用没匹配上，整题判错 |

它还有一类“相关性检测”：给的函数都不适用时，正确输出是不调用。这对应 [01](../01-eval-design/README.md) 讲的正反两面出题。另一种方式是真正执行生成的调用，看返回结果是否符合预期；执行不现实的地方才用 AST 检查。

**放到自己的 Agent 上**，单步评测通常查五件事：

1. 该不该调工具（含“不该调时没调”）；
2. 选对工具没有；
3. 参数能否通过 schema 校验；
4. 参数值是否和上下文一致（例如订单号来自用户刚给的那个）；
5. 工具报错后是否合理处理，而不是同参数重试。

**单步评测和端到端的关系**：单步全对，端到端还是会错。第 5.1 节会算出来：20 步的任务，单步 95% 的正确率只剩约 36% 的整体成功率。单步评测的作用是定位，不是替代终态评测。

**代价**：单步评测要为每一步准备标准答案，流程一改就要重标。只给最容易错、对下游影响最大的步骤做，通常是路由和工具选择。输入从线上轨迹里截取真实的那一步，固定下来做回归。

## 5 长程任务的中间检查点

**问题**：几十步的任务只给 0/1，绝大多数版本都是 0，分辨不出“做了一半”和“一步没做”；失败了也不知道卡在哪。这一节先算清楚成功率为什么随步数掉得这么快，再讲两种补救：给任务内部设检查点（5.2），以及换一个度量，用“能做多长的任务”描述能力（5.3）。

### 5.1 成功率随步数衰减

[core/09 第 2.3 节](../../../core/09-evaluation/README.md#23-多步让小误差连乘) 已经推过最简模型：任务 n 步，每步独立以概率 p 做对，任一步错了又没被纠正就整题失败，所以 P(成功) = p^n。允许纠错时，一步做错后以概率 r 被改对，等效单步成功率变成 p + (1 − p)r。这里在它的基础上往下推三件事。

**半衰期：成功率降到 50% 要多少步**。令 p^n = 0.5：

```text
n_50 = ln 0.5 / ln p
     ≈ 0.693 / (1 − p)          （1 − p 很小时，ln p ≈ −(1 − p)）
```

p = 0.95 时 n_50 ≈ 13.5 步；p = 0.99 时 n_50 ≈ 69 步。近似式说明了一个规律：**半衰期和单步错误率成反比**。错误率从 2% 降到 1%，能做到 50% 成功率的步数从约 34 步变成约 69 步，翻了一倍。

**纠错等于降低错误率**。等效单步错误率是 1 − [p + (1 − p)r] = (1 − p)(1 − r)。代进半衰期的近似式：

```text
n_50(有纠错) ≈ 0.693 / [(1 − p)(1 − r)] = n_50(无纠错) / (1 − r)
```

p = 0.95、r = 0.6 时，半衰期约是原来的 1/(1 − 0.6) = 2.5 倍（精确值 2.54）。所以“能发现并改正自己的错误”和“单步更准”对长任务的作用是同一个量级。只评单步，测不到纠错。METR 的论文在定性分析里也提到，较新的模型更会根据错误调整做法，而不是重复失败的动作。

**纠错要花步数**。改一次错要多走 c 步，而评测通常有步数或 token 上限 B。改错次数一多就超预算，纠错的收益被吃掉一部分。下面代码里 n = 20、c = 3、B = 26，最多容许改 2 次错，成功率从不限预算时的约 0.667 降到约 0.652。上限再紧，下降更多。

**步与步不同质**。真实任务的难度集中在少数几步。平均单步成功率同为 0.95 时，16 步 0.99 加 4 步 0.79 的整体成功率是 0.332，低于均匀 0.95 的 0.358。原因是乘积等于几何平均的 n 次方，几何平均不大于算术平均。这也说明“平均单步正确率”不足以预测整体成功率，要知道难步在哪。

这些都是简化模型下的推导。真实任务里步与步不独立，有的步骤错了也不影响终态。它的用处是给出方向：长任务的成功率对单步错误率和纠错率都很敏感。

```python
import numpy as np

# 1) 无纠错：每步独立以 p 做对，n 步全对才成功
def success(p, n):
    return p ** n

def half_life(p):
    """成功率降到 50% 时的步数：p^n = 0.5 → n = ln 0.5 / ln p ≈ 0.693 / (1 − p)"""
    return np.log(0.5) / np.log(p)

assert abs(success(0.95, 20) - 0.358) < 1e-3
assert round(half_life(0.95), 1) == 13.5 and round(half_life(0.99), 1) == 69.0
assert abs(half_life(0.99) - 0.693 / 0.01) / half_life(0.99) < 0.01   # 错误率小时的近似
# 错误率减半，半衰期约翻倍：单步从 98% 到 99%，能做的步数从 34 到 69
assert round(half_life(0.98)) == 34 and round(half_life(0.99) / half_life(0.98), 2) == 2.01

# 2) 有纠错：一步做错后以 r 的概率被发现并改对，等效单步成功率 q = p + (1 − p) r
def success_recover(p, r, n):
    return (p + (1 - p) * r) ** n

# 纠错把有效错误率从 (1 − p) 降到 (1 − p)(1 − r)：r = 0.6 时半衰期约是原来的 2.5 倍（精确值 2.54）
q = 0.95 + 0.05 * 0.6
assert abs(q - 0.98) < 1e-12
assert round(half_life(q) / half_life(0.95), 2) == 2.54     # 近似值 0.05 / 0.02 = 2.5

# 3) 纠错要花步数：每次改错多用 c 步，总预算 B 步。超预算就算失败
def sim_budget(p, r, n, c, B, R=200_000, seed=0):
    rng = np.random.default_rng(seed)
    err = rng.random((R, n)) >= p                   # 每步是否出错，形状 (R, n)
    fixed = rng.random((R, n)) < r                  # 出错后是否被改对，形状 (R, n)
    alive = ~(err & ~fixed).any(axis=1)            # 没有“错了又没改对”的步
    steps = n + c * (err & fixed).sum(axis=1)      # 改错的额外步数
    return (alive & (steps <= B)).mean(), alive.mean()

ok_budget, ok_inf = sim_budget(p=0.95, r=0.6, n=20, c=3, B=26)
assert abs(ok_inf - success_recover(0.95, 0.6, 20)) < 0.005      # 不限预算时和闭式一致
# 预算只允许改 2 次错：额外步数 = 3 × 改错次数 ≤ 6
# 改错次数 ~ Binomial(20, 0.03)，在“没有不可救错误”的条件下每步改错的概率是 0.03 / 0.98
k = np.arange(0, 3)
from math import comb
pk = np.array([comb(20, j) * (0.03 / 0.98) ** j * (0.95 / 0.98) ** (20 - j) for j in k])
assert abs(ok_budget - ok_inf * pk.sum()) < 0.005
assert ok_budget < ok_inf                                          # 步数上限会吃掉一部分纠错收益

# 4) 步与步不同质：错误集中在少数难步时，同样的平均单步成功率，整体成功率不同
p_uniform = np.full(20, 0.95)
p_hetero = np.array([0.99] * 16 + [0.79] * 4)                    # 平均仍是 0.95
assert abs(p_hetero.mean() - 0.95) < 1e-12
assert np.prod(p_hetero) < np.prod(p_uniform)   # 几何平均 ≤ 算术平均：0.331 < 0.358
print(f"同质 {np.prod(p_uniform):.3f}，异质 {np.prod(p_hetero):.3f}")
print(f"有纠错不限预算 {ok_inf:.3f}，限 26 步 {ok_budget:.3f}")
```

### 5.2 带权重的检查点和部分得分

**做法**。TheAgentCompany 把每个任务拆成若干检查点，按重要性给分。检查点可以查动作是否完成、产出数据是否正确、是否和模拟同事沟通。多数检查点用确定性的 Python 函数查环境状态或轨迹，主观的产出才用带 rubric 的 LLM 评委。它定义了两个分数：

```text
S_full    = 1（所有检查点都通过） 否则 0
S_partial = 0.5 × (得分 / 总分) + 0.5 × S_full
```

论文的例子：8 分里拿到 4 分但没完成，得 0.5 × 0.5 + 0 = 0.25。后一半分数只给完成整个任务的 Agent，这样做到一半的 Agent 永远比完成的低。推导：没完成时 S_partial ≤ 0.5 × 1 + 0 = 0.5；完成时 S_partial = 0.5 + 0.5 = 1。所以任何没完成的试次都不会超过 0.5，任何完成的都是 1。

Anthropic 的文章也支持部分得分：一个正确识别问题、核实了客户身份但没完成退款的 Agent，明显好过一开始就失败的，结果里应该体现这种差别。

**它和 3.3 节的过程分不是一回事**。3.3 节的 S 在没做成时为 0，用来区分“做成了的”之间谁更干净。部分得分用来区分“没做成的”之间谁走得更远。两个分数分开报，不要合成一个。

**设计检查点的要点**：

| 要点 | 理由 |
|---|---|
| 检查点查状态，不查路径 | 和终态评测同理，允许多条路径 |
| 按依赖顺序排 | 能看出最远走到哪一步，做“卡点分布” |
| 权重反映重要性 | 不然做了很多琐碎步骤也能拿高分 |
| 完成任务单独给分 | 防止部分得分鼓励“做一半就停” |
| 每个试次从干净环境开始 | Anthropic 提到，共享状态会让失败相关、分数虚高，例如 Agent 读到了之前试次留下的 git 记录 |

**卡点分布**。检查点按依赖排好后，对每个失败的试次记下“第一个没通过的检查点”，再按检查点计数。大多数失败停在同一个检查点，说明那一步是瓶颈，单步评测（第 4 节）就该先做那一步。

**代价**：检查点要人工设计和维护，每个任务都要写判定函数。部分得分会让不同任务的分数不再可比，汇报时要同时给完成率和部分得分。

### 5.3 METR 的任务时长：用“能做多长的任务”描述能力

检查点解决的是“一个任务内部走到了哪”。另一个问题是：不同任务的难度不同，怎么用一个数概括 Agent 能做多难的长任务。METR 的论文（Kwa 等，arXiv 2503.14499）提出了 **50% 任务时长**（50%-task-completion time horizon）：Agent 能以 50% 成功率完成的那类任务，人类专家通常要花多长时间。

**方法**，按论文第 2、3 节：

1. **任务和人类时长**。任务来自三个套件，都是软件和研究工程方向：HCAST 的 97 个任务（1 分钟到 30 小时）；RE-Bench 的 7 个机器学习研究工程任务，都是 8 小时；新建的 SWAA 套件，66 个单步短任务，1 秒到 30 秒。每个任务请有相关专长的人做，任务时长 t 取成功的人类基线时长的几何平均。少数任务没有人类基线，用研究者估计。
2. **结果二值化**。每个模型在每个任务上跑约 8 次。本来就是 0/1 的任务直接用；连续打分的任务按代表人类水平的阈值转成成败。HCAST 的阈值就是人类基线要达到的目标分，RE-Bench 用 7 到 9 小时人类运行的平均分。
3. **对每个模型单独拟合 logistic 回归**：

```text
p(成功 | 模型, 任务) = σ( (log h − log t) · β )
```

σ 是 logistic 函数 σ(z) = 1/(1 + e^(−z))。h 和 β 是这个模型要拟合的两个参数。t = h 时括号里是 0，σ(0) = 0.5，所以 h 就是 50% 时长。β 是斜率：β 越大，成功率在 h 附近从高到低掉得越陡。

4. **任务族降权**。同一个任务族里的任务结果相关，论文按“族内任务数的平方根的倒数”给每个任务加权，避免大族主导结果。论文的敏感性分析里试了加权和不加权、logistic 回归正则参数从 0.01 到 0.2 的组合，称趋势对这些选择不敏感。
5. **看趋势**。把各模型的 log h 对发布日期做最小二乘回归，得到翻倍时间。误差条来自三层分层 bootstrap：任务族、任务、运行。

**它和 IRT 的关系**。论文说明，这个式子借鉴了项目反应理论（IRT）的两参数 logistic 模型。区别在于 IRT 同时从数据里学题目难度和答题者能力；METR 直接把 log t（人类时长）当作题目难度，只拟合每个模型的能力参数。这样做的好处是 h 有直观单位（分钟），代价是假设“人类时长”就是难度，而论文自己的图显示人类时长只能部分预测 Agent 的成败。

**趋势**。论文报告，2019 年到 2025 年前沿模型的 50% 时长大约每 7 个月翻一倍，并称 2024 年以来可能更快。80% 时长的翻倍时间和 50% 时长相近，但 80% 时长本身短 4 到 6 倍。论文的解读是：偶尔能做成难任务的模型，还不能稳定地做中等长度的任务。具体模型的分数这里不列。

**为什么 80% 时长短这么多：从拟合式推出来**。解 σ((log h − log t)β) = s，得到成功率 s 对应的时长：

```text
t_s = h · exp( −logit(s) / β ),       logit(s) = ln( s / (1 − s) )

h / t_0.8 = exp( ln 4 / β ) = 4^(1/β)
```

β = 1 时 80% 时长是 50% 时长的 1/4；β ≈ 0.77 时约 1/6。所以“短 4 到 6 倍”等价于拟合出来的 β 大约在 0.77 到 1 之间。这是本章从论文的式子推出来的关系，论文没有写出这一步。它说明 β 本身也是可靠性信息：同样的 h，β 越小，曲线越平，高成功率要求下能做的任务越短。

**和 5.1 节的关系**。如果每分钟有一个恒定的失败率 λ，成功率是 exp(−λt)，这正是 p^n 换成连续时间的形式。它在 log t 上掉得比 logistic 陡：时长从 h 翻到 10h，成功率从 0.5 掉到 2^(−10) ≈ 0.001。logistic 在 β = 0.9 时同样位置还有约 11%。也就是说，实际数据的尾巴比“恒定失败率”模型厚。一个可能的解释是任务之间难度差异大，不全由时长决定。这是推断，下面的代码只验证了两个模型的数学差别。

**局限**，论文附录 E.3 自己列了：任务时长总是相对于某个任务分布和某个技能水平的人类而言；测很长的时长需要大量带长人类基线的难任务，成本很高；测 95% 这样的高成功率时长，需要很大、标签噪声几乎为零的任务集。

下面的代码用构造数据走一遍拟合：已知真实 h 和 β，生成 170 个任务、每个 8 次的 0/1 结果，用牛顿法拟合加权 logistic 回归，看能否还原；再验证 80% 时长的关系和任务族降权的作用。

```python
import numpy as np

# METR 的模型：p(成功) = σ((log h − log t) · β)。t 是人类完成该任务的时长，h 是 50% 时长
sigmoid = lambda z: 1 / (1 + np.exp(-z))


def fit_horizon(t, y, w=None, l2=0.0, iters=50):
    """加权 logistic 回归，自变量 x = log t。返回 (h50, beta)。
    参数化成 z = a + b·x，则 β = −b，log h = −a / b。用牛顿法求解。"""
    x = np.log(t)
    w = np.ones_like(x) if w is None else w
    X = np.stack([np.ones_like(x), x], axis=1)            # 形状 (N, 2)
    theta = np.zeros(2)
    for _ in range(iters):
        p = sigmoid(X @ theta)
        grad = X.T @ (w * (p - y)) + l2 * np.array([0, theta[1]])
        H = (X * (w * p * (1 - p))[:, None]).T @ X + l2 * np.diag([0, 1])
        theta -= np.linalg.solve(H, grad)
    a, b = theta
    return float(np.exp(-a / b)), float(-b)


# 1) 构造数据：真实 h = 30 分钟、β = 0.9；任务时长从 1 分钟到 16 小时按对数均匀分布
rng = np.random.default_rng(0)
h_true, beta_true = 30.0, 0.9
t = np.exp(rng.uniform(np.log(1), np.log(960), size=170))   # 170 个任务，单位分钟
t = np.repeat(t, 8)                                           # 每个任务跑 8 次，形状 (1360,)
y = (rng.random(t.size) < sigmoid((np.log(h_true) - np.log(t)) * beta_true)).astype(float)
h_hat, b_hat = fit_horizon(t, y)
assert abs(np.log(h_hat / h_true)) < 0.25 and abs(b_hat - beta_true) < 0.15

# 2) 50% 时长处预测成功率正好 0.5（定义），以及 80% 时长和 50% 时长的关系（推导）
assert abs(sigmoid((np.log(h_hat) - np.log(h_hat)) * b_hat) - 0.5) < 1e-12
def horizon_at(h50, beta, s):
    return h50 * np.exp(-np.log(s / (1 - s)) / beta)          # 解 σ((log h50 − log t)β) = s
h80 = horizon_at(h_hat, b_hat, 0.8)
assert abs(sigmoid((np.log(h_hat) - np.log(h80)) * b_hat) - 0.8) < 1e-9
# h50 / h80 = 4^(1/β)：β 越小（曲线越平），80% 时长比 50% 时长短得越多
assert abs(h_hat / h80 - 4 ** (1 / b_hat)) < 1e-9
assert round(4 ** (1 / 1.0), 2) == 4.0 and round(4 ** (1 / 0.77), 2) == 6.05

# 3) 任务族加权：同一族的任务结果相关，按 1/√(族大小) 降权。
#    构造一个 40 个任务的“简单长任务族”（都是 480 分钟、几乎都成功），不加权时 h 被抬高
t_fam = np.full(40 * 8, 480.0)
y_fam = (rng.random(t_fam.size) < 0.9).astype(float)
t_all, y_all = np.concatenate([t, t_fam]), np.concatenate([y, y_fam])
fam_size = np.concatenate([np.ones(t.size), np.full(t_fam.size, 40.0)])
h_unw, _ = fit_horizon(t_all, y_all)
h_w, _ = fit_horizon(t_all, y_all, w=1 / np.sqrt(fam_size))
assert h_unw > h_w > h_hat * 0.9                               # 降权后更接近没有这个族时的估计

# 4) 对比“每分钟恒定失败率”的模型：p = exp(−λ t)，它的 50% 时长是 ln2 / λ。
#    在 log t 上它比 logistic 掉得更陡：时长翻 10 倍，成功率从 0.5 降到 2^(−10) ≈ 0.001
lam = np.log(2) / h_true
assert abs(np.exp(-lam * h_true) - 0.5) < 1e-12
assert np.exp(-lam * 10 * h_true) < 0.001
assert sigmoid(-np.log(10) * beta_true) > 0.1                 # logistic 同样位置还有约 11%
print(f"拟合 h50 = {h_hat:.1f} 分钟，β = {b_hat:.2f}，h80 = {h80:.1f} 分钟")
print(f"加任务族：不加权 h50 = {h_unw:.1f}，按 1/√族大小加权 h50 = {h_w:.1f}")
```

这段代码验证了几件事：

- 用 170 个任务、每个 8 次的构造数据，拟合出的 h 和 β 接近真实值（h 真值 30 分钟，拟合约 31 分钟；β 真值 0.9，拟合约 0.93）。拟合方法本身没问题，误差来自任务抽样。
- 80% 时长和 50% 时长之比等于 4^(1/β)。β = 1 时是 4 倍，β = 0.77 时约 6 倍。
- 加进一个 40 个任务、都是 8 小时、成功率 90% 的任务族，不加权时 h 从约 31 分钟被抬到约 116 分钟；按 1/√族大小加权后约 39 分钟。一个大族就能把整体结论带偏，这是论文要做任务族降权的原因。
- 恒定失败率模型在 10 倍时长处的成功率不到 0.001，logistic 还有约 11%。两个模型在尾部差别很大，选哪个会影响对长任务的外推。

**拿到自己的评测上怎么用**。自己的评测集如果有人类完成时长（或者能估出来），可以按同样的方法给每个 Agent 版本拟合 h 和 β。它比平均通过率多给两样东西：一个有单位的能力刻度，以及斜率 β 带来的可靠性信息。前提是任务时长分布够宽，覆盖 h 两侧，否则 logistic 拟合不出来（见第 9 节）。

## 6 失败归因：模型、工具、上下文

**问题**：通过率掉了 5 个点，要知道修哪里。

**做法**：读失败轨迹，按一张固定的表归类，再按类别计数。Anthropic 的文章强调，要读很多试次的轨迹和评分结果，才知道评分器是否可靠；一个任务失败时，轨迹会告诉你是 Agent 真错，还是评分器拒绝了正确答案。

| 归因 | 轨迹里的信号 | 改哪里 |
|---|---|---|
| 评分器或题目错 | 输出合理但被判错；多个版本都在同一题失败 | 修题、修评分器 |
| 环境 / 基础设施 | 超时、限流、工具服务 5xx、环境脏状态 | 环境隔离、重试策略；这类失败不计入能力分 |
| 工具 | 工具返回错误数据，或描述和行为不符 | 工具实现或工具描述 |
| 上下文 | 关键信息被截断、检索没召回、长对话里遗忘早先约束 | 上下文管理、检索 |
| 模型决策 | 信息都在，却选错工具、填错参数、违反规则 | 提示、模型、训练 |

操作顺序：先排除评分器和环境，再看工具和上下文，最后才归给模型。把环境失败算进能力分，会让团队在模型上找一个不存在的问题。

**归因的对象不只是 O = 0 的试次**。第 3 节的门控会把一部分 O = 1 的试次判成失败（侥幸成功、副作用）。它们同样要归因：没确认就写，多半是模型决策；工具描述没写清导致多改了字段，归到工具。只归因终态失败，会漏掉这一批。

**按类别统计**。归完类以后，按类别计数，排出先修哪一类。这一步要注意两点：

1. 评分器错的试次修好以后要重判，不能直接删；环境失败的试次剔除，或在干净环境里重跑。两者处理完再算能力分。
2. 类别计数本身是一个比例估计，题少时置信区间很宽。“工具类失败从 3 次变成 5 次”在几十个失败样本上多半是噪声。区间怎么算见 [01 第 6 节](../01-eval-design/README.md#6-统计显著性与样本量)。

**定位第一个错误步骤**：长轨迹里，最后报错的那一步往往不是根因。可以从前往后找第一个“之后无论怎么做都救不回来”的决定性错误。METR 的论文在定性分析里把失败分成几类，例如规划或工具选择差、推理错误、过早放弃、重复失败的动作。分类表的细节可以因任务而异，原则是一样的：先定好类别，再逐条归。

**自动归因现在有多准**：Who&When（Zhang 等，2025）收集了 127 个多 Agent 系统的失败日志，标注了责任 Agent 和决定性错误步骤，比较了三种用 LLM 自动归因的方法：

| 方法 | 做法 | 特点 |
|---|---|---|
| 一次性 | 整条日志一次给评委 | 最便宜；找责任 Agent 最好，找具体步骤最差 |
| 逐步 | 一步一步判，遇到第一个错误就停 | 找步骤最好；最贵，长日志上下降最多 |
| 二分 | 每次判断错误在前半段还是后半段 | 两项都居中，成本也居中 |

摘要报告的最好结果是：找对责任 Agent 约 53.5%，找对错误步骤只有 14.2%。结论是自动归因目前只能当初筛，最终归因要人工读轨迹。

用评委做初筛时，它的误判会让类别计数偏移。拿人工标注的样本量出评委在每一类上的混淆，再做校正，方法和 [02 第 5.5 节](../02-llm-as-judge/README.md#55-把评委通过率换算到人工口径) 的二分类校正相同，只是扩展到多类。

## 7 多 Agent 系统的评测

单 Agent 的评测都还要做，另外多出三件事：

1. **端到端和单 Agent 都要评**。整体结果决定是否成功；每个子 Agent 也要有自己的单步或检查点评测，否则整体掉分时找不到是谁。
2. **评协作本身**。例如交接信息是否完整、是否重复劳动、是否有人确认了别人的结果。交接完整性可以写成检查点：下游 Agent 需要的关键信息是否出现在交接消息里。
3. **和单 Agent 基线比**。同一评测集上比成功率、成本和延迟。多 Agent 的收益要覆盖额外成本。

MAST 失败分类（三大类、14 种失败模式）在 [core/08 第 5.2 节](../../../core/08-multi-agent/README.md#52-mast-失败分类) 讲过。把它当失败归因表的多 Agent 扩展用时，评测看这几件事：

| 类别 | 评测时看什么 |
|---|---|
| 系统设计问题 | 角色定义是否清楚，是否遵守任务和角色要求 |
| Agent 间未对齐 | 信息是否传丢，是否各做各的、互相不知道 |
| 任务验证不足 | 有没有人检查结果，检查是否流于形式 |

**代价**：多 Agent 轨迹更长、并行分支更多，人工读轨迹的成本成倍上升。每个 Agent 的输入输出要单独记录，否则事后无法归因。多 Agent 的架构取舍见 [core/08 多 Agent](../../../core/08-multi-agent/README.md)。

## 8 数值例子：同一批试次的三个分数

一个退款 Agent 的新版本跑了 10 个试次。评分器给出终态 O 和门控 G，失败的试次人工读了轨迹做归因：

| 试次 | O | G | 归因 |
|---|---|---|---|
| 1–5 | 1 | 1 | 无 |
| 6 | 1 | 0 | 模型决策：没确认就写（侥幸成功） |
| 7 | 1 | 0 | 工具：工具描述没写清，多改了一个字段（副作用） |
| 8 | 0 | 1 | 环境：依赖服务超时 |
| 9 | 0 | 1 | 评分器：输出合理，终态检查写错 |
| 10 | 0 | 1 | 上下文：早先的约束被截断 |

手算三个分数：

1. **只看终态**：O 的平均 = 7/10 = 0.70。
2. **终态加门控**：O·G 的平均 = 5/10 = 0.50。只看终态高估了 20 个点，全部来自侥幸成功和副作用。
3. **剔除环境、修正评分器后**：试次 8 剔除；试次 9 修好终态检查后重判为通过（这里假设重判结果是通过）。剩 9 个试次，6 个通过，6/9 ≈ 0.667。

剩下的三个失败分别归到模型决策、工具、上下文，各 1 个。10 个试次太少，从这里看不出该先修哪类，要扩大评测集再看分布。而且这三个数各回答一个问题，汇报时都要写：0.70 是“做成了多少”，0.50 是“合规地做成了多少”，0.667 是“排除评测本身的问题后，Agent 的能力”。

```python
from collections import Counter

# 10 个试次的评测结果。outcome：终态检查；gate：过程规则和副作用都没触发；
# cause：人工读轨迹后的失败归因（成功且 gate 通过的试次为 None）
trials = [
    {"outcome": 1, "gate": 1, "cause": None},
    {"outcome": 1, "gate": 1, "cause": None},
    {"outcome": 1, "gate": 1, "cause": None},
    {"outcome": 1, "gate": 1, "cause": None},
    {"outcome": 1, "gate": 1, "cause": None},
    {"outcome": 1, "gate": 0, "cause": "模型决策"},     # 没确认就写：侥幸成功
    {"outcome": 1, "gate": 0, "cause": "工具"},         # 工具描述没写清，多改了一个字段
    {"outcome": 0, "gate": 1, "cause": "环境"},         # 依赖服务超时
    {"outcome": 0, "gate": 1, "cause": "评分器"},       # 输出合理，终态检查写错
    {"outcome": 0, "gate": 1, "cause": "上下文"},       # 早先的约束被截断
]
n = len(trials)
outcome_rate = sum(t["outcome"] for t in trials) / n
strict_rate = sum(t["outcome"] * t["gate"] for t in trials) / n
assert outcome_rate == 0.7 and strict_rate == 0.5     # 只看终态高估 20 个点

# 归因顺序：先排除评分器和环境。评分器错的试次要修题后重判，环境失败不计入能力分
causes = Counter(t["cause"] for t in trials if t["cause"])
assert causes["评分器"] == 1 and causes["环境"] == 1
capability = [t for t in trials if t["cause"] not in ("评分器", "环境")]
# 评分器那题修好后重判为成功（假设重判结果），环境那题剔除
regraded = capability + [{"outcome": 1, "gate": 1, "cause": None}]
strict_capability = sum(t["outcome"] * t["gate"] for t in regraded) / len(regraded)
assert len(regraded) == 9 and round(strict_capability, 3) == 0.667

# 归因分布：按类别统计失败，决定先修哪里
fixable = Counter(t["cause"] for t in regraded if t["cause"])
assert fixable == Counter({"模型决策": 1, "工具": 1, "上下文": 1})
print(f"终态通过率 {outcome_rate:.2f}，终态+过程 {strict_rate:.2f}，"
      f"剔除环境、修正评分器后 {strict_capability:.3f}")
```

## 9 工程细节与常见坑

**终态检查只查目标字段，副作用漏检**

- 现象：线上出现“退款成功但订单被取消”之类的投诉，离线评测通过率却很高。
- 原因：终态检查写的是“A1 已退款”，没查其他字段。Agent 多做的写操作不影响这个检查。
- 排查：对通过的试次做一次全量状态 diff（初始状态对终态），列出所有变化的字段，人工看哪些不该变。
- 处理：给每个任务写“允许变化的字段”白名单，白名单外的变化进门控 G（第 3.4 节）。

**过程规则写成了路径，正确解被误杀**

- 现象：换一个模型或改一版提示后，通过率大跌，读轨迹发现很多“失败”的终态是对的。
- 原因：规则里写了“第 2 步必须调 lookup_order”之类的顺序约束，或者把某条标准轨迹当成了答案。
- 排查：统计每条规则的触发次数，对触发最多的规则抽读轨迹，看被拦下的是不是合理做法。
- 处理：规则只写不依赖路径的约束（禁用工具、写前确认、预算上限、重复次数）。关键步骤只查“做没做”，不查“第几步做”。

**加权总分把违规抵消掉**

- 现象：新版本总分上涨，但违规次数也在涨。
- 原因：违规作为总分里的一项扣分，被终态分和过程分的上涨抵消了。
- 排查：把违规率单独列出来，和总分放在同一张表里看。
- 处理：违规和副作用走门控，乘进总分（第 3.3 节）；违规率单独报。

**环境失败算进了 Agent 的过程分**

- 现象：某天无效步骤比例突然上升，模型和提示都没改。
- 原因：工具服务变慢，超时次数增加，评分器把超时当成 Agent 的无效步骤。
- 排查：把无效步骤按“超时、5xx、参数错误、重复调用”拆开计数。只有超时和 5xx 上升，就是环境问题。
- 处理：评分器区分“Agent 发出的错误调用”和“工具服务的失败”。后者归环境，不扣过程分，必要时在干净环境里重跑。

**部分得分和成功分混成一个数**

- 现象：A 版本平均分高于 B，但 B 的完成率更高。
- 原因：A 很多试次做到一半就停，部分得分累积起来超过了 B。
- 排查：把完成率和部分得分分开列。
- 处理：完成率和部分得分分开报；部分得分用 TheAgentCompany 的形式，保证没完成的永远低于完成的（第 5.2 节）。

**步数或 token 上限设得太紧**

- 现象：调高上限后通过率明显上升；失败轨迹的末尾大多在改错，没有乱走。
- 原因：纠错要额外步数（第 5.1 节），上限把能纠错的试次截断了。
- 排查：画“失败时已用步数”的分布。大量失败堆在上限附近，说明上限在起作用。
- 处理：上限按线上真实预算定，并在报告里写明。比较两个版本时用同一个上限。

**任务时长拟合不稳**

- 现象：同一个 Agent，换一批任务，拟合出的 h 差好几倍；β 拟合出负数或特别大。
- 原因：任务时长没有覆盖 h 的两侧。全是 Agent 都能做的短任务，或者全是都做不了的长任务，logistic 回归没法定位 50% 点。任务少时还会出现完全可分，β 趋于无穷。
- 排查：画成功率对 log t 的散点，看 50% 附近有没有足够的任务；看 bootstrap 出来的 h 区间有多宽。
- 处理：补齐不同时长的任务；加 L2 正则（METR 的敏感性分析里试过不同正则强度）；按任务族降权，避免一个大族主导（第 5.3 节的代码）。

**用“人类时长”当难度，忽略了任务分布**

- 现象：同一个 Agent 在编程任务上的 h 和在其他领域任务上的 h 差很多。
- 原因：METR 的论文明确说，任务时长总是相对于某个任务分布和某个技能水平的人类而言，人类时长只能部分预测 Agent 的成败。
- 排查：按领域、按“杂乱程度”（有没有清晰反馈、需不需要主动找信息）分组拟合，看 h 是否一致。
- 处理：报 h 时写明任务分布和人类基线是谁。不要把一个领域的 h 外推到另一个领域。

**归因只看终态失败**

- 现象：归因分布里“模型决策”占比很低，但线上违规投诉不少。
- 原因：侥幸成功和带副作用的试次 O = 1，没进归因流程。
- 排查：把门控拦下的试次也加进归因队列。
- 处理：归因对象是“O·G = 0”的试次，不是“O = 0”的试次（第 6 节）。

**试次之间共享状态**

- 现象：同一题重复跑，后几次的通过率明显高于第一次；或者一题失败后，后面几题接连失败。
- 原因：Agent 读到了之前试次留下的文件或 git 记录；或者上一个试次把环境弄脏了。
- 排查：打乱试次顺序重跑，看通过率是否和顺序有关。
- 处理：每个试次从干净环境开始（容器快照、数据库回滚），这一点 Anthropic 的文章专门强调过。

## 10 对比与取舍

### 10.1 评什么

| | 终态 | 终态 + 门控 | 终态 + 门控 + 过程分 | 检查点部分得分 | 任务时长 |
|---|---|---|---|---|---|
| 回答的问题 | 做成了没有 | 合规地做成了没有 | 做成的里谁更干净 | 没做成的走到了哪 | 能做多长的任务 |
| 需要标注 | 目标状态 | 加规则、白名单 | 加关键步骤和权重 | 每个任务的检查点和判定函数 | 每个任务的人类时长 |
| 漏什么 | 违规、侥幸、副作用 | 效率和成本 | 规则写不出的过程问题 | 跨任务可比性 | 任务分布和人类水平的影响 |
| 适合 | 初期、目标状态明确的任务 | 有写操作、有政策约束的 Agent | 成本和步数敏感的场景 | 长程任务、要找卡点 | 跨版本、跨模型比较长程能力 |

### 10.2 组合方式

| 方式 | 公式 | 优点 | 缺点 |
|---|---|---|---|
| 加权 | w_O·O + w_P·P，过阈值算过 | 简单；各项都有贡献 | 没做成也有分；违规会被抵消 |
| 二元 | O·G | 严格、好解释 | 分不出“干净做成”和“绕路做成” |
| 混合 | O·G·(α + (1 − α)P) | 违规一票否决，过程分只做微调 | 多一个超参数 α，要写明 |

### 10.3 谁来判

| 判定方式 | 适合 | 代价 |
|---|---|---|
| 代码规则 | 终态、门控、关键步骤、无效步骤 | 写不出来的规则判不了 |
| 评委看轨迹 | 检索顺序是否合理、语气、规划质量 | 要校准，见 [02](../02-llm-as-judge/README.md)；误判只能进 P，不能进 G |
| 人工读轨迹 | 归因、新类型的失败、校准评委 | 贵，长轨迹和多 Agent 尤其贵 |

**怎么选**：先上终态加门控，这一步的投入最小，能挡住最危险的问题。成本敏感时再加过程分。长程任务通过率低到分不出版本时，加检查点。要回答“能力在长任务上涨了多少”时，才需要任务时长，因为它要人类时长标注，最贵。
