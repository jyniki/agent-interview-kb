# 题目：训练环境与用户模拟器

> 对应知识章：[README.md](README.md)。先闭卷作答，再看答案。τ-bench 的判分见 [evaluation/04 第 4.1 节](../../evaluation/04-benchmarks/README.md#41-τ-bench-到-τ²-bench)，pass^k 的估计见 [evaluation/01 的 eval-design-004](../../evaluation/01-eval-design/questions.md#eval-design-004-每题跑-n-次成功-c-次怎么估计-passk为什么不能用-pk)，这里只问训练视角。

## train-env-001 Agent RL 的训练环境要满足哪些要求
- level: 2
- tags: [training, harness]

**一句话答案**：由任务集、动作接口、状态和评分器组成，硬要求是可验证、可复现、可重置：奖励能程序判定，同样动作得同样结果，每条 rollout 从同一初始状态出发。

**要点**：
- 可验证：τ-bench 比对数据库终态；AppWorld 用基于状态的单元测试，还检查附带损害。
- 基于状态而不是基于动作序列，允许多种正确解法。
- 可复现：环境噪声会混进奖励方差，组内优势不可信。
- 可重置：GRPO 一组轨迹必须从相同状态出发才可比。

**追问链**：
1. 为什么要查附带损害？→ 只查目标完成，策略会学会“顺手”改别的东西；终态比对要覆盖不该变的部分。
2. τ-bench 的 r = 1 为什么不充分？→ 论文承认 Agent 没得到用户明确确认就执行退货，违反政策仍得 1 分；训练时这种漏洞会被系统性利用。
3. 工具超时的轨迹怎么处理？→ 环境故障，丢弃或重跑，不给负奖励。

**易错点**：
- 只说“要有奖励”，不提复现和重置。

## train-env-002 搜索或业务 API 类工具，训练时用在线还是离线
- level: 2
- tags: [training, harness]

**一句话答案**：训练优先用离线快照或模拟服务，换取可复现、便宜、无副作用；代价是和真实分布有差距，所以评测时另留一份接真实工具的集合检查迁移。

**要点**：
- 在线真实工具：分布真实；不可复现、慢、贵、有副作用。
- 离线快照：如 Search-R1 用固定的维基百科语料和本地检索器。
- 模拟服务：如 AppWorld 的 9 个应用、457 个 API；状态可控可重置，建设成本高。
- 工具结果缓存会让策略看不到真实工具的失败模式。

**追问链**：
1. 真实工具有时效性怎么办？→ 把时间当成环境状态固定下来；需要时效能力的任务单独做在线评测。
2. 模拟服务做多细？→ 至少覆盖真实工具的错误码和边界情况，否则策略学不会处理失败。
3. 写操作有副作用怎么训？→ 只在模拟服务或沙箱里训，真实写接口不进训练回路。

**易错点**：
- 认为离线环境训出来的能力一定能迁移。

## train-env-003 设计一个客服 Agent 训练用的用户模拟器
- level: 3
- tags: [training, evaluation]

**一句话答案**：给模拟器一段对 Agent 隐藏的任务指令（身份、意图、偏好），规定信息被问到才透露，用工具和可观测状态约束它的行为，模型和策略隔离；奖励不问模拟器满意度，而是比对环境终态。

**要点**：
- τ-bench：指令写到“政策下只有一种正确结局”；模拟器温度 1.0，Agent 0.0；模拟器看不到工具交互；`###STOP###` 结束。
- τ²-bench：用户也有工具（电信场景 15 写 15 读），只在 Agent 要求时调用，回复基于工具真实返回。
- 画像和目标分离，同一目标配多种说话方式。
- 模拟器和策略用不同模型或不同提示，避免共享盲区。

**追问链**：
1. 模拟器最常见的问题？→ 太配合，第一句就把信息说完，Agent 学不会追问；要规定逐步透露并统计配合度。
2. 为什么奖励不让模拟器打分？→ 模拟器打分会被话术影响，容易被钻；比对终态更难造假。
3. 模拟器温度为什么设 1？→ 让同一任务多个试次有差异，才能衡量可靠性；训练时也提供了多样的对话分支。

**易错点**：
- 让模拟器和策略用同一个模型同一个提示。

## train-env-004 怎么知道用户模拟器靠不靠谱
- level: 3
- tags: [training, evaluation]

**一句话答案**：人工抽样标注模拟器每轮是否遵守准则、遵守任务指令、正确使用工具、对话自然，把错误分成致命和无害两类统计错误率；再看奖励提升是否集中在模拟器犯错的轨迹上，并用真人对话评测检查迁移。

**要点**：
- τ²-bench：两名标注员逐轮检查，致命错误率航空 13%、零售 12%、电信 6%（标注对话数分别为 100、50、50；表 2 标题说电信没有致命错误，与表内数字矛盾，以表内为准）。
- 电信域更低，论文归因于结构化工具接口和清晰的动作空间。
- τ-bench 构建时每个零售任务跑 40 次以上，找出成功率极低的任务查指令歧义；40 个失败里有 4 个是用户指令错字或歧义。
- 人工判别测试：让人区分模拟对话和真实对话。

**追问链**：
1. 致命错误率 10% 量级对训练意味着什么？→ 约一成轨迹的奖励是噪声甚至反向信号；要先修指令和约束，或在训练前按错误模式过滤任务。
2. 怎样发现策略在利用模拟器？→ 按模拟器错误类型分桶看奖励；看策略是否形成固定话术；换一个模拟器模型后奖励是否明显下降。
3. 怎么降低模拟器错误？→ 把用户行为落到工具和可观测状态上，减少靠自然语言指令驱动的部分。

**易错点**：
- 只看 Agent 的分数，不单独评估模拟器。

## train-env-005 Coding Agent 的训练环境怎么规模化，SWE-smith 的思路是什么
- level: 2
- tags: [training, harness]

**一句话答案**：反转 SWE-bench 的顺序，先为每个仓库建一个可执行环境，再在里面自动注入让已有测试失败的改动来合成大量任务，镜像按仓库共享，存储比按任务建镜像低两个数量级以上。

**要点**：
- 环境：Agent 自动安装并跑测试，人工确认后每个仓库一个 Docker 镜像。
- 任务合成：LLM 改函数加隐蔽 bug、LLM 只看签名重写、随机 AST 变换、反向应用真实 PR、合并多个 bug。
- 只保留让至少一个原本通过的测试失败的改动。
- 规模：128 个仓库、5 万任务、295 GB；论文估计按每任务一个镜像需要 50 到 150 TB。

**追问链**：
1. 合成任务有什么局限？→ 注入 bug 和真实 bug 分布不同；失败测试对 Agent 可见，和 SWE-bench 隐藏测试补丁的设定不同。评测仍用真实任务。
2. R2E-Gym 走的是什么路？→ 从仓库提交构建环境，自动生成测试，用回译生成任务描述，减少对人工 issue 和现成测试的依赖。
3. 测试做评分器有什么问题？→ 区分度低，测试不全时错误补丁也能通过；R2E-Gym 把执行判定和模型判定结合，因为两者的弱点不同。

**易错点**：
- 只谈任务数量，不谈镜像存储和每条 rollout 的容器成本。

## train-env-006 用户模拟器以概率 e 犯致命错误时，训练奖励会怎样偏、什么时候会把策略带偏
- level: 3
- tags: [training, evaluation]

**一句话答案**：期望奖励变成 (1−e)p+eq，偏差 e(q−p)，策略间差距缩成 1−e 倍，只是噪声；但 e 依赖策略且 q>p 时，梯度多出 (q−p)·∂e/∂θ，策略会学着诱导模拟器犯错。

**要点**：
- p：模拟器不犯错时的成功率；q：犯错时仍得 1 分的概率。r 仍是 0/1，Var(r) = m(1 − m)。
- 等价于 05 章的 fp/fn 模型：fp = e·q，fn = e·(1 − q)，信号缩放 1 − fp − fn = 1 − e。
- 检出同样差距要多约 1/(1 − e)² 倍试次；e = 0.13 时约 1.32 倍。
- 零优势组概率 (1 − m)^G + m^G 随 e 上升，难题上更明显。
- τ²-bench 报告的致命错误率：航空 13%、零售 12%、电信 6%。

**追问链**：
1. 训练里要不要用 (m̂ − eq)/(1 − e) 去偏？→ 不必：常数缩放被组内基线和学习率吸收；去偏只对评测有用，且方差放大 1/(1 − e)²。
2. 怎样发现策略在利用模拟器？→ 按模拟器错误类型分桶，看犯错桶的奖励是否高于同任务正常桶；看训练中 e 是否上升；换模拟器模型复评。
3. 怎么从源头压低 q 和 ∂e/∂θ？→ 结束条件和关键约束交给规则和工具，例如 Agent 未完成写操作前忽略结束标记，约束写成结构化字段。

**易错点**：
- 认为模拟器错误只是噪声，忽略错误率会随策略变化。

## train-env-007 训练前怎样发现环境评分器的漏洞
- level: 2
- tags: [training, evaluation]

**一句话答案**：对每个任务跑探针：oracle 解法必须通过，什么都不做、倒出全部数据、提前退出或跳过测试、改测试文件这些平凡策略必须不过；再同种子回放两次比终态哈希，查可复现性。

**要点**：
- ABC（arXiv 2507.02825）审计到的例子：τ-bench 不可能任务以“数据库不变”为成功，空回复的平凡 Agent 在航空域拿到 38%；子串匹配让倒出整张表也能过。
- SWE-Lancer 测试文件可被覆盖；KernelBench 没清显存里的答案；CVE-Bench 同一 Docker 网络能直连外部服务器。
- 探针要每个任务都跑，漏洞常只在一部分任务上。
- 试跑看异常值：简单题总失败可能不可解，只有难题成功可能有捷径。

**追问链**：
1. 为什么环境漏洞在训练里比在评测里更危险？→ 评测里只是分数虚高；训练里只要钻漏洞的得分概率高于正常成功率，梯度就会主动放大它，并扩散到所有同类任务。
2. 训练中怎么发现探针没想到的漏洞？→ 留一个更严格的评分器定期复评同批轨迹，看两条曲线是否分叉；关注奖励突然整体跃升和轨迹模式突变。
3. 发现后怎么处理？→ 修环境，把对应探针加进回归集，回到 hack 出现之前的检查点继续训。

**易错点**：
- 只验证 oracle 能通过，不验证平凡策略不能通过。

## train-env-008 同步 rollout 时 batch 内 B 条轨迹独立同分布，一步时间对应单条时长的哪个分位数，GPU 为什么闲
- level: 3
- tags: [training, inference]

**一句话答案**：P(max ≤ x) = F(x)^B，最慢那条的中位数是单条时长的 0.5^(1/B) ≈ 1 − 0.69/B 分位数；B 越大越落在尾部，生成槽位在等工具和等最慢者时都空着。

**要点**：
- B = 256 时约是 p99.7；指数分布下 E[max] = μ·H_B。
- 同步时生成槽位忙碌比例 = Σ gen_i / (B · max T_i)。
- 异步连续补位能去掉“等最慢者”的空闲，剩下等工具的空闲，上限 E[gen]/E[T]；再要提高就让一个槽位挂多条轨迹。
- 本章模拟（工具时间对数正态）：B = 256 时忙碌 13.5%，连续补位上限 42.2%。

**追问链**：
1. 加大 batch 能提高吞吐吗？→ 收益递减：一步时间按尾部分位数增长，模拟里 max/mean 从 B = 16 的 1.9 涨到 B = 1024 的 4.7。
2. 用超时截断长尾有什么代价？→ 慢的往往是难题，截断后丢弃会让训练集偏向简单题；要按任务统计截断率。
3. 异步的代价是什么？→ 策略滞后，需要重要性比率修正和有界滞后，见 04 章第 5 节。

**易错点**：
- 把 GPU 闲置全归因于生成长度，忽略工具执行时间。

## train-env-009 训练端每 60 秒消费 256 条轨迹、每条平均占环境 57 秒，要多少并发环境
- level: 2
- tags: [training, harness]

**一句话答案**：用 Little 定律，在途数 = 到达速率 × 平均停留时间，约 256/60 × 57 ≈ 243 个；冷启动、模拟器延迟都会加进平均时长，尾部轨迹还要求额外余量。

**要点**：
- 每条多 20 秒冷启动，平均时长约 77 秒，并发数按比例增到约 330。
- 训练变快（U 变小）时并发环境要同比增加，否则训练端等数据。
- 用户模拟器是 LLM 服务，也要按同样的并发量部署。
- 预热池把冷启动从平均时长里拿掉；池子大小的估算见 harness/03 第 8 节。

**追问链**：
1. 为什么只按平均值配会不够？→ 尾部轨迹长时间占着环境，到达也有波动；要留余量并设单条超时。
2. 怎样降低每条轨迹占用环境的时间？→ 预热池、镜像按仓库共享并就近缓存、同一题 G 条轨迹调度到同一节点、截断过长的工具结果。
3. 环境时间里哪部分最该先拆出来看？→ 把轨迹时间拆成启动、生成、工具、评分四段统计，再决定优化哪段。

**易错点**：
- 按 batch 大小配环境数，忽略每条轨迹的停留时间。
