# 题目：评测与 Benchmark

> 对应知识章：[README.md](README.md)。先闭卷作答，再看答案。

## core-eval-001 为什么 Agent 评测比单轮模型评测难
- level: 1
- tags: [core, evaluation]

**一句话答案**：Agent 输出不确定、正确做法不唯一、过程有副作用、常常要多轮交互，而且成本和延迟也是指标，所以不能只拿一个标准答案比一次输出。

**要点**：
- 不确定：同一任务每次路径不同，要跑多次看成功率和稳定性。
- 不唯一：修 bug、写报告有多种合理做法，要判终态或用 rubric。
- 副作用：会改数据库、发消息，要在隔离环境里跑，检查环境最终状态。
- 多轮：客服类任务要用模型模拟用户。
- 效率：同样做对，步数和 token 差很多，要一起报。

**追问链**：
1. “终态”具体指什么？→ 试次结束时环境的状态，例如数据库里是否真有那条预订，而不是 Agent 嘴上说“已订好”。
2. 模拟用户会带来什么问题？→ 模拟用户本身有随机性，可能不按剧本说话，结果噪声变大；要多跑几次，并抽查对话确认失败不是模拟用户造成的。

**易错点**：
- 用 BLEU、ROUGE 这类文本相似度评 Agent 任务。

## core-eval-002 终态评测和轨迹评测有什么区别，怎么配合
- level: 1
- tags: [core, evaluation]

**一句话答案**：终态评测看环境最终状态对不对，轨迹评测看过程调了什么、是否合规；一般用终态决定对错，用轨迹检查规则和定位失败。

**要点**：
- 终态：测试是否通过、数据库是否等于目标状态。客观，但看不出违规过程。
- 轨迹：工具选择、参数、违规动作、步数。能查合规，但合理路径不唯一，按固定路径打分会误伤。
- τ-bench 论文写明终态奖励为 1 是必要条件不是充分条件，例如未经用户确认就办退货。

**追问链**：
1. 轨迹评测怎么避免误伤合理的不同路径？→ 不比对完整路径，只检查必须满足的约束：必须调过某个确认步骤、不能调某个危险工具、步数不超预算。
2. 单步评测有什么用？→ 定位“哪一步选错了工具或参数”，也适合调工具调用能力；但单步都对不代表整体能完成。

**易错点**：
- 把轨迹评测理解成“和标准轨迹逐步比对”。

## core-eval-003 LLM-as-Judge 有哪些偏差，怎么缓解
- level: 2
- tags: [core, evaluation]

**一句话答案**：主要有位置偏差、冗长偏差和自我偏好；缓解办法是交换顺序各评一次、rubric 写明长度不加分、换不同系列或多个评委，并用人工标注校准。

**要点**：
- 出处：Zheng 等，arXiv 2306.05685（MT-Bench 与 Chatbot Arena），报告强评委和人类偏好一致率超过 80%，与人类之间相当。
- 位置：成对比较时偏好某个位置。
- 冗长：偏好更长的回答。
- 自我偏好：偏好自己或同系列模型的输出。
- 顺序：能用代码判的先用代码判，剩下的交给评委，评委再用人工抽检校准。

**追问链**：
1. 一致率 80% 够不够？→ 要看和人与人之间的一致率比，也要看错在哪类样本上。如果错误集中在关键类别，平均一致率高也不能用。
2. 打分还是成对比较？→ 成对比较更容易判、更稳定，适合比较两个版本；绝对打分便于跟踪趋势，但尺度容易漂移。
3. 评委换了模型怎么办？→ 重新在人工标注集上校准，不能直接拿新旧评委的分数比。

**易错点**：
- 默认评委分数就是真值，不做校准。

## core-eval-004 pass@k 和 pass^k 有什么区别，各自什么时候用
- level: 2
- tags: [core, evaluation, training]

**一句话答案**：pass@k 是 k 次里至少一次成功的概率，随 k 上升；pass^k 是 k 次全部成功的概率，随 k 下降；“有一次能用就行”看 pass@k，面向用户要求每次都对看 pass^k。

**要点**：
- pass^k 由 τ-bench 提出，衡量部署可靠性。
- 每题跑 n 次成功 c 次：pass^k 估计为对任务平均 C(c,k)/C(n,k)（τ-bench）；pass@k 为 1 − 平均 C(n−c,k)/C(n,k)（Codex 论文）。
- k = 1 时两者都等于平均成功率。
- 例：单次成功率 75% 且试次独立时，3 次全对约 42%。

**追问链**：
1. 为什么不直接用 c/n 的 k 次方？→ 每道题的成功率不同，先在每题上用组合数做无偏估计再平均，比用总体平均成功率求幂更准确。
2. 训练时哪个更有用？→ pass@k 高说明模型有能力采到正确解，强化学习可以把它“提上来”；pass^k 低说明不稳定，是上线前要解决的问题。

**易错点**：
- 把 pass^k 写成 pass@k 的别称。

## core-eval-005 SWE-bench、τ-bench、GAIA / BrowseComp 分别测什么、怎么判、有什么局限
- level: 2
- tags: [core, evaluation]

**一句话答案**：SWE-bench 用真实 issue 测修代码，跑测试判；τ-bench 测客服工具使用和政策遵守，看数据库终态；GAIA、BrowseComp 测检索和工具组合，比短答案；局限是测试不完善和污染。

**要点**：
- SWE-bench：2294 个任务、12 个 Python 仓库；FAIL_TO_PASS 和 PASS_TO_PASS 测试全通过才算解决。
- SWE-bench Verified：人工审核的 500 题子集。
- τ-bench：零售和航空，模拟用户多轮对话，数据库终态加必需输出。
- GAIA：466 题，答案短可比对，300 题答案不公开。
- BrowseComp：1266 题，考坚持找难找的信息，不覆盖长答案和需要澄清的查询。
- OSWorld：369 个真实操作系统任务，用执行脚本检查最终状态。

**追问链**：
1. 为什么 OpenAI 停报 SWE-bench Verified？→ 两个原因：部分题目的测试有缺陷，会拒绝功能正确的提交；前沿模型能复述部分标准补丁，说明有污染。（背景：OpenAI 审计的 138 道难题里，至少 59.4% 的测试有缺陷。）
2. 公开 Benchmark 分数高，能说明你的业务也会好吗？→ 不能。设置、工具、提示都不同，还可能有污染。公开 Benchmark 用于粗筛，决策看私有的业务评测集。

**易错点**：
- 背分数和排名，说不出判分方式和局限。

## core-eval-006 从零给一个企业客服 Agent 设计评测方案
- level: 3
- tags: [core, evaluation, harness]

**一句话答案**：先从真实对话里抽几十到几百个任务建离线集，在隔离环境里用模拟用户跑多次，终态用代码判、过程合规用规则加评委判，报 pass^k、成本和延迟；上线前走影子和灰度，线上失败样本回流进离线集。

**要点**：
- 任务来源：真实工单按意图分层抽样，补上应该拒绝、追问、转人工的题。
- 环境：mock 订单库和工具，每次从同一初始状态开始。
- 判分：数据库终态对比用代码；“是否先确认再执行写操作”用轨迹规则；回复语气和准确性用评委加 rubric，评委用人工标注校准。
- 指标：分层成功率、pass^k、平均步数和 token、违规率。
- 噪声：每题跑多次，新旧版本在同一批题上配对比较，差距小于波动就不下结论。
- 线上：影子流量 → 灰度 A/B，看任务完成率、转人工率、投诉等护栏指标。

**追问链**：
1. 为什么用 pass^k 而不只是平均成功率？→ 客服是面向用户的，同一类问题有时对有时错，用户体验很差；pass^k 直接暴露不稳定。
2. 离线涨了线上没涨怎么办？→ 先查离线集分布是否和线上一致，再看线上指标是否测到了改动影响的场景；把线上失败样本补进离线集。
3. 怎么防止对评测集过拟合？→ 留一部分不给开发看的测试集；定期补新题；同时看线上指标。

**易错点**：
- 只用一个评委模型打总分，没有代码判分和分层统计。
- 只看质量，忘了成本、延迟和违规率。

## core-eval-007 为什么 C(c,k)/C(n,k) 是 pass^k 的无偏估计，而 p̂^k 会估高
- level: 3
- tags: [core, evaluation]

**一句话答案**：C(c,k)/C(n,k) 是从 n 个试次无放回抽 k 个全成功的概率，这 k 个就是独立试次，期望恰为 p^k；p̂^k 相当于有放回抽，x^k 是凸函数，按 Jensen 不等式会估高。

**要点**：
- 每题跑 n 次成功 c 次，n ≥ k；先逐题估计，再对题平均，期望线性保证整体无偏。
- k = 2 时偏差有闭式：E[p̂²] − p² = Var(p̂) = p(1 − p)/n，随 n 增大而变小。
- pass@k 同理：1 − C(n−c,k)/C(n,k) 无偏；1 − (1 − p̂)^k 是凹函数，会估低。Codex 论文附录 A 指出这种低估在 n > 5k 时也没完全消失。
- 还有一种错法：先算全集平均成功率 p̄ 再求 p̄^k，抹掉了题与题的差异。

**追问链**：
1. 两个 Agent 的 pass^1 都是 75%，pass^3 可能不同吗？→ 可能。每题都是 75% 的 pass^3 约 0.42；三题必对一题必错的 pass^3 是 0.75。只有逐题估计才算得出来。
2. 每题只跑 2 次能报 pass^3 吗？→ 不能，组合估计要求 n ≥ k；退回用 p̂^k 会有偏。
3. 数值上怎么算才不溢出？→ 写成连乘：C(c,k)/C(n,k) = Π_{i=c+1..n}(1 − k/i)，Codex 论文图 3 对 pass@k 用了同样的写法。

**易错点**：
- 以为 n 足够大时 p̂^k 就没问题，于是不同 n 的结果直接比较。

## core-eval-008 让一个只读最终回复的模型评委判断“任务是否完成”，会出什么问题
- level: 2
- tags: [core, evaluation]

**一句话答案**：评委看不到环境终态，会放过“说了没做”和“做错但说得好”的试次，也会误杀“做对但回复简短”的试次；办没办成应交给代码评分器比对终态，评委只判它看得到的回复质量。

**要点**：
- 每个评分器只判它看得见的东西。
- 和代码评分器对比时，拆开看放过率和误杀率，比只看一致率更有用。
- kappa = (p_o − p_e)/(1 − p_e)；评委测的东西和终态无关时，kappa 可以接近 0 甚至为负。
- 组合方式：分工（各管一方面、都过才算过）、级联（先跑便宜的代码检查）、校准（人工抽检评委）。

**追问链**：
1. 怎么发现评委有这个问题？→ 抽一批评委判过的样本，用代码查终态，算放过率；再读放过样本的轨迹。
2. 如果没法写代码查终态怎么办？→ 把终态的关键信息（工具结果、数据库快照）放进评委的输入，再用人工标注校准，单独报放过率。

**易错点**：
- 只报评委和代码评分器的一致率，不看分歧落在哪类样本上。

## core-eval-009 50 道题每题跑一次，同一个版本跑两次分数差 5 个点，正常吗
- level: 2
- tags: [core, evaluation]

**一句话答案**：正常。单次评测的方差是 Σp_i(1−p_i)/N²，50 题时标准差约 5 个点，两次相差 5 个点以上很常见；每题多跑几次能压低试次噪声，但换题带来的噪声只能靠加题和配对比较。

**要点**：
- 最坏情况 p = 0.5 时，单次评测标准差 ≈ 0.5/√N，50 题约 7 个点。
- 每题跑 K 次取平均，试次噪声按 1/√K 缩小。
- 题目抽样的方差约为 Var(p)/N，多跑试次消不掉。
- 比较两个版本时在同一批题上配对，抵消题目难度的共同部分。
- 统计单位是题：先算每题平均分，再按题算标准误，不能把 K × N 次运行当独立样本。

**追问链**：
1. 怎么判断一次改动是真的变好？→ 同一批题、每题多跑几次，逐题配对比较，看差值的区间是否含 0；先测出同版本的波动作为基线。
2. 为什么不能把每题 10 次运行当成 10N 个独立样本？→ 同一题的多次运行高度相关，这样算会把标准误算小，区间过窄，结论在换题后翻转。

**易错点**：
- 改一次 prompt、跑一次评测，涨几个点就宣布有效。
