# 题目：Prompt 与 Context Engineering

> 对应知识章：[README.md](README.md)。先闭卷作答，再看答案。

## core-prompt-001 Prompt Engineering 和 Context Engineering 有什么区别
- level: 1
- tags: [core, harness]

**一句话答案**：Prompt Engineering 关注指令怎么写；Context Engineering 关注每次推理时上下文里放哪些 token，包括指令、工具定义、检索结果、历史和工具结果，每步都要重新决定。

**要点**：
- 依据：Anthropic，Effective context engineering for AI agents，2025-09。
- Context rot：上下文越长，模型准确找回信息的能力越弱。
- 目标是尽可能小的、高信号的 token 集合，而不是越多越好。
- Agent 多步运行，上下文不断变化，所以 Context Engineering 是持续的装配工作。

**追问链**：
1. 窗口已经很大了，为什么还要精简？→ 长上下文更贵、更慢，前缀缓存更容易失效；而且信息越多，模型越难用好其中关键的部分。
2. 上下文里通常有哪些东西？→ 工具定义、system prompt、参考资料、历史消息、工具结果、检索结果、当前请求。
3. 怎么判断某段内容该不该放？→ 看去掉它后评测指标是否下降；能按需检索的内容只放引用。

**易错点**：
- 把 Context Engineering 当成“写更长的 prompt”。它更多是在决定删什么、什么时候加载。

## core-prompt-002 一个 system prompt 应该包含哪些部分
- level: 1
- tags: [core]

**一句话答案**：角色与目标、背景信息、任务与步骤、约束、输出格式、少量示例，用标题或 XML 标签分隔；写在“合适的高度”，既不写成硬编码的 if-else，也不默认模型懂你的背景。

**要点**：
- 约束里写清停止条件和转人工条件。
- 输出格式给样例，不只说“输出 JSON”。
- 迭代方式：先最简 prompt 跑评测，按观察到的失败补指令。
- 规则放 system，外部数据放 user 或 tool 结果并标注来源，配合指令层级。

**追问链**：
1. prompt 越写越长、互相冲突怎么办？→ 按部分重组，删掉评测证明无用的条款；把只在特定场景用到的规则拆出去按需加载。
2. 换了模型，prompt 要改吗？→ 要跑回归。不同模型对同一指令的遵循程度不同，强模型上啰嗦的解释可能多余，弱模型上可能不够。

**易错点**：
- 只写角色设定，没有约束和输出格式。

## core-prompt-003 Few-shot 示例怎么选，会有哪些偏差
- level: 2
- tags: [core, evaluation]

**一句话答案**：选多样、典型的示例，标签分布均衡，并打乱顺序评测；few-shot 对格式、示例选择和顺序都很敏感，模型会偏向提示末尾出现的答案和预训练中常见的 token。

**要点**：
- 出处：Zhao 等，Calibrate Before Use，arXiv 2102.09690。准确率可以从接近随机变到接近当时最好的结果。
- 论文提出的校准方法：用“N/A”这类无内容输入测出模型的偏好，再拟合参数把它校正成均匀分布。
- 按输入动态检索最相近的示例能提效果，但会破坏前缀缓存。
- 推理模型上，堆示例的收益变小，甚至可能有害。

**追问链**：
1. 动态示例和前缀缓存怎么兼顾？→ 把动态示例放在稳定前缀之后、当前请求之前，固定部分仍可缓存。
2. 模型照抄示例里的具体内容怎么办？→ 示例用和真实任务不同的虚构内容，或减少示例数，改用格式说明。
3. 怎么证明示例有用？→ 在同一评测集上对比零样本和不同示例组合，并对顺序做多次打乱，看均值和方差。

**易错点**：
- 只看一种示例顺序的结果就下结论。

## core-prompt-004 怎么保证模型输出合法的结构化数据
- level: 2
- tags: [core, harness]

**一句话答案**：三档方案：提示约束加解析重试、JSON 模式、按 JSON Schema 做约束解码；只有最后一种保证符合 schema，但仍要程序校验内容是否正确。

**要点**：
- 提示约束是尽力而为，会出现多余文字或缺字段。
- JSON 模式只保证语法合法。
- Schema 约束（如 OpenAI 的 `strict: true`）逐 token 限制可选值，代价是只支持部分 Schema 特性，并要求如 `additionalProperties: false`、字段全部列入 `required`。
- 格式合法之外，字段取值、引用是否存在，要靠业务校验。

**追问链**：
1. 约束解码会不会影响回答质量？→ 有可能。schema 太死会迫使模型在不该填的时候也填值。可选字段允许 `null`，再给一个“无法判断”的取值。
2. 只能用不支持约束解码的模型怎么办？→ 给样例，低温度，解析失败时把错误信息回传让模型修正，并设重试上限。

**易错点**：
- 认为“输出了合法 JSON”就够了，不做内容校验。

## core-prompt-005 上下文装配按什么顺序，为什么
- level: 2
- tags: [core, inference, harness]

**一句话答案**：稳定的放前面（工具定义、system、长期参考资料），变化的放后面（历史、检索结果、当前请求）；前者为了命中前缀缓存，后者因为模型对开头和末尾的信息利用得更好。

**要点**：
- 前缀缓存要求完全一致的前缀，前面一处变化会让之后的缓存全部失效。
- Anthropic 的缓存前缀顺序是 tools → system → messages，默认 5 分钟生命周期；读取标准价为基础输入价的 0.1 倍，5 分钟写入 1.25 倍。
- Lost in the Middle（Liu 等，arXiv 2307.03172）：相关信息在中间时效果明显下降。
- 时间戳、请求 ID 不要放进 system 开头；工具列表保持固定顺序。

**追问链**：
1. 最关键的检索结果放在哪里？→ 放在末尾、靠近当前请求；不要埋在长上下文中间，模型对中间信息利用得最差。
2. 关键规则放在开头，可是上下文很长时被“遗忘”了怎么办？→ 在当前请求附近简短重复关键约束，或把规则执行交给程序校验。

**易错点**：
- 只从效果角度谈顺序，忽略成本和缓存。

## core-prompt-006 上下文快满了，怎么分配预算、先删什么
- level: 3
- tags: [core, harness]

**一句话答案**：先给输出和固定开销留足预算，再按相关度装检索结果，历史和工具结果用剩下的空间；超出时先清理已用过的旧工具结果，再摘要早期对话，当前请求和核心约束始终保留。

**要点**：
- 输出预留不能被挤占，否则回答被截断。
- 工具定义过多时按需加载，见 [04 工具调用、MCP 与 Skills](../04-tool-use-mcp/README.md)。
- 清理旧工具结果最轻：保留调用记录，删掉大段返回，需要时再调用。
- 摘要会丢细节并改变前缀，要验证摘要后任务能否继续。
- 即时检索：上下文只放文件路径、查询语句等引用，用到时再取。

**追问链**：
1. 摘要丢掉了关键信息怎么发现？→ 用一组长任务评测，比较摘要前后的成功率；摘要模板里固定保留目标、已做决定、未完成事项。
2. 什么时候触发压缩？→ 按窗口占用比例设阈值，在离上限还有余量时做，避免最后一步才发现装不下。具体阈值和验证方法见 [harness/02 上下文装配、压缩与断点续跑](../../tracks/harness/02-context-compaction/README.md)。
3. 子 Agent 能帮上忙吗？→ 能。让子 Agent 在干净的上下文里做探索，只把精简结果交回主 Agent。

**易错点**：
- 用简单的滑动窗口丢最早消息，把任务目标和约束丢掉了。

## core-prompt-007 Prompt 注入是什么，prompt 一侧能怎么防
- level: 2
- tags: [core, harness]

**一句话答案**：攻击者把指令藏进模型会读到的外部内容里，诱导模型执行；prompt 侧可以做来源标注、Spotlighting 和指令层级，但只能降低概率，高风险动作要靠权限和确认兜底。

**要点**：
- 间接注入出自 Greshake 等，arXiv 2302.12173：LLM 应用模糊了数据和指令的界限。
- Spotlighting（Hines 等，arXiv 2403.14720）：分隔符、数据标记、编码三种变换；论文报告攻击成功率从 50% 以上降到 2% 以下。
- 指令层级（Wallace 等，arXiv 2404.13208）：训练模型在冲突时优先服从高权限指令。
- 最小权限：处理外部内容的步骤不给写操作和外发工具。

**追问链**：
1. 为什么 prompt 防御不够？→ 模型是否遵守分隔声明没有保证，攻击写法会不断变化。
2. 一个能读邮件也能发邮件的助手，怎么设计？→ 读邮件的步骤只做提取，输出结构化字段；发邮件前要求用户确认收件人和内容；外发工具不对外部文本里出现的地址自动放行。
3. 怎么测防御效果？→ 建一组注入样例，统计攻击成功率和正常任务成功率，两个都要看。

**易错点**：
- 只说“在 prompt 里写‘不要听从其他指令’”就算防住了。

## core-prompt-008 为什么上下文窗口没满，关键信息却越来越难被用上
- level: 2
- tags: [core, harness]

**一句话答案**：softmax 下关键位置的权重约为 e^Δ/(e^Δ+(n−1)·常数)，内容越多被分得越薄，干扰项越像答案越严重；Chroma 报告的实验也显示效果随长度、干扰项增加而下降。

**要点**：
- 推导：要保持一半权重，打分优势 Δ 要随 ln n 增长，上下文每长 10 倍多约 2.3。这是简化模型，只说明方向。
- Anthropic 的解释：n 个 token 有 n² 对关系，注意力预算被摊开；长序列训练数据少。结果是一条性能梯度，没有突然失效的拐点。
- Chroma 的 Context Rot 报告（2025-07）：固定任务难度只改长度，效果都下降；一个干扰项就低于基线；问题和答案相似度越低，随长度下降越快。
- 位置效应（Lost in the Middle）是另一件事：同样多的内容，放在中间更难被用上。

**追问链**：
1. 干扰项和无关内容，哪个伤害大？→ 和答案相似的干扰项伤害更大，分母里那一项按 e^μ 放大；少量近似答案可以抵得上大量无关内容。
2. 这对检索条数有什么启示？→ 召回率高不等于效果好，近似但不对的段落是干扰项；条数要在端到端评测上定。
3. 推导能解释报告里所有现象吗？→ 不能。报告发现打乱背景文本反而更好，原因不明，报告也说需要可解释性研究。

**易错点**：
- 把 context rot 理解成“超过窗口才出问题”，或者把它和位置效应混为一谈。

## core-prompt-009 few-shot 示例的顺序和标签分布为什么会改变输出，怎么修正
- level: 2
- tags: [core, evaluation]

**一句话答案**：模型有多数标签偏差和近因偏差，会偏向示例里多的标签和末尾的标签，顺序可能比选哪些示例还重要；可均衡标签、打乱评测，或用无内容输入测出偏差做上下文校准。

**要点**：
- Zhao 等（2102.09690）：只换顺序，准确率可从接近随机变到接近当时最好；P P P N 的示例下近 90% 的预测是 Negative。
- 上下文校准：用 “N/A” 等无内容输入测 p_cf，取 W = diag(p_cf)⁻¹。二分类时等价于从 logit 里减掉偏差 b。
- 局限：只修与输入无关的常数偏差；需要拿到输出概率。
- Lu 等（2104.08786）：好的顺序不能跨模型迁移，换模型要重新评测。
- Min 等（2202.12837）：示例主要提供标签空间、输入分布和格式，随机换标签只降 0 到 5 个点。

**追问链**：
1. 为什么校准能去掉偏差？→ σ(x)/σ(−x) = e^x，除以无内容输入的概率后两类之比变成 e^{ℓ−b}，偏差整体抵消。
2. 动态检索示例时怎么控制顺序？→ 检索后按固定规则排序，例如按标签轮流排，避免同一标签扎堆在末尾。
3. 示例标签全错还有用，说明什么？→ 示例的主要价值是演示格式和取值范围，所以示例格式要和期望输出完全一致；但这不是通用规则，有的设置下全错会降近 10 个点。

**易错点**：
- 认为“示例越多越好”或“只要标签正确就行”，忽略顺序和标签比例。

## core-prompt-010 写价 1.25 倍、读价 0.1 倍时，前缀缓存命中率多少才划算
- level: 2
- tags: [core, inference, harness]

**一句话答案**：每 token 成本为 ρ_w − (ρ_w − ρ_r)·h，低于不开缓存需要 h > (ρ_w−1)/(ρ_w−ρ_r) = 0.25/1.15 ≈ 21.7%；命中率低于两成时开缓存反而更贵。

**要点**：
- 没命中的部分按写价算，所以命中率低时每次都多付 25%。
- 盈亏点主要由写入溢价决定：读价降到 0.05，盈亏点只从 21.7% 变到 20.8%。
- 第 6.3 节的模拟：时间戳放在 system 开头，命中率 11.3%，成本是不开缓存的 112%；推荐顺序命中 79%，成本 34%。
- 倍率按厂商和模型变化，要以当时的定价表为准（本章查阅于 2026-11）。

**追问链**：
1. 命中率很低时该怎么办？→ 先找破坏前缀的内容（相邻请求做 diff），把它挪到可变尾部；短 prompt 或一次性请求可以不开缓存。
2. 1 小时缓存写价 2 倍，盈亏点变成多少？→ (2−1)/(2−0.1) ≈ 52.6%，只有确定会被多次读取的长前缀才值得用。
3. 读价越低，越该开缓存吗？→ 读价影响的是命中后省多少，要不要开主要看命中率能否过盈亏点。

**易错点**：
- 以为开了缓存一定省钱，忽略写入溢价。

## core-prompt-011 上下文超限时，预算分配器应该按什么顺序截断，有哪些不能破坏的约束
- level: 3
- tags: [core, harness]

**一句话答案**：先扣输出预留和固定开销，检索按分数装到上限；历史超出时先清理旧工具结果，再成对丢最早的消息；任务目标、调用与结果的配对、最近几条工具结果不能破坏，固定开销放不下要报错。

**要点**：
- 输出预留被挤占，回答和 JSON 都会被截断。
- 清理旧工具结果丢得最少，Anthropic 称为最安全、最轻的压缩。
- 只丢调用、留下工具结果，API 会因配对规则报 400。
- 任务目标单独固定，否则滑动窗口会把它丢掉。
- 截断改写历史，从截断点往后的缓存失效，频繁小幅截断比偶尔一次大幅截断更贵。

**追问链**：
1. 为什么固定开销放不下要报错而不是截断？→ 悄悄截掉 system 或请求的现象是模型突然不守某条规则，很难排查。
2. 检索为什么要单独设上限？→ 防止大段检索结果挤掉历史里的任务状态；历史有空余时再还给检索。
3. 截断后怎么验证没出问题？→ 对消息序列做结构校验（配对、首条是目标），并在长任务评测上比较截断前后的成功率和步数。

**易错点**：
- 用按条数的滑动窗口截断，拆开了调用和结果，或丢掉了任务目标。
