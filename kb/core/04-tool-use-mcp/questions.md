# 题目：工具调用、MCP 与 Skills

> 对应知识章：[README.md](README.md)。先闭卷作答，再看答案。

## core-tool-001 一次 Function Calling 是怎么走完的
- level: 1
- tags: [core, harness]

**一句话答案**：应用把工具定义和消息发给模型，模型返回结构化的调用（名称和参数），应用执行后用调用 ID 把结果发回，模型再给出答案或继续调用。

**要点**：
- 模型不执行工具，只输出调用请求；执行、权限、校验都在应用侧。
- 结果和调用靠 ID 对应：OpenAI 用 `call_id`，Anthropic 用 `tool_use_id`。
- 一轮可能返回多个并行调用，代码要按多个处理。
- `tool_choice` 控制自动、必须调用、指定工具或禁止调用；`strict` 让参数严格符合 schema。

**追问链**：
1. 为什么说执行在应用侧很重要？→ 这是安全控制点：可以在执行前做参数校验、权限检查和人工确认，模型输出的只是一个请求。
2. 工具执行失败怎么办？→ 把可操作的错误信息作为结果返回，让模型决定改参数重试或换路径；超时、重试的通用策略在 Harness 里做。

**易错点**：
- 说“模型调用了 API”。准确说法是模型生成了调用请求，应用执行了 API。

## core-tool-002 模型的工具调用能力是怎么训练出来的
- level: 2
- tags: [core, training]

**一句话答案**：合成或自采样工具调用轨迹，执行验证后做 SFT（早期代表 Toolformer、Gorilla、ToolLLM），再用结果奖励做 RL 学何时调用、何时停止；工具结果不计 loss。

**要点**：
- Toolformer（Schick 等，arXiv 2302.04761）：每个 API 只给少量演示；调用加结果作为前缀时，若后续 token 的加权损失下降至少一个阈值就保留。
- Gorilla（Patil 等，arXiv 2305.15334）：微调 LLaMA，配合检索器适应测试时的文档变化，减少 API 幻觉。
- ToolLLM（Qin 等，arXiv 2307.16789）：从 RapidAPI 收集 16,464 个 API、49 个类别，用 ChatGPT 生成 ToolBench。
- 训练时按对话模板输出调用格式，工具返回的内容不是模型生成的，计算 loss 时要屏蔽。

**追问链**：
1. 合成数据的主要风险？→ 调用路径由强模型生成，可能有错误或捷径；需要执行验证，过滤掉调用失败或结果不支持答案的轨迹。
2. SFT 之后为什么还要 RL？→ SFT 学的是模仿格式和常见路径，多步任务里何时调用、何时停止、怎么从错误中恢复，需要用结果奖励来优化。见 [training/04 Agentic RL](../../tracks/training/04-agentic-rl/README.md)。

**易错点**：
- 把 Toolformer 说成“人工标注调用位置”。它的数据是模型自己采样、按损失过滤出来的。

## core-tool-003 一个好的工具定义应该怎么写
- level: 1
- tags: [core, harness]

**一句话答案**：按高频任务设计少而清晰的工具，名字带命名空间，描述写清做什么、何时用、何时不用和参数格式，参数用精确名称和枚举，程序已知的值不让模型填。

**要点**：
- 不要把每个 API 端点都包成工具；总是连着调用的合并。
- 检验方法：只给一个人模型能看到的信息，他能否正确使用（OpenAI 的“实习生测试”）。
- 返回值只给高信号信息，用可读名称代替内部 ID，支持分页和截断。
- 错误信息要可操作：说明错在哪、怎么改。

**追问链**：
1. 返回值太大怎么办？→ 分页、过滤、截断，设合理默认值，截断时提示模型缩小范围；也可以提供简洁和详细两种返回模式。
2. 怎么知道描述改好了？→ 用真实任务跑评测，看选择准确率、调用次数、token 消耗和工具报错，不只看最终正确率。

**易错点**：
- 只关注描述，忽视返回值。返回值同样占上下文、影响后续决策。

## core-tool-004 MCP 是什么，和 Function Calling 是什么关系
- level: 2
- tags: [core, harness]

**一句话答案**：MCP 是应用连接工具和数据源的开放协议，把 M×N 集成变成 M+N；它不替代 Function Calling：Host 把工具定义交给模型，模型发出调用，Host 路由到 Server 执行。

**要点**：
- 参与方：Host（AI 应用）、Client（Host 内部，每个 Server 一个）、Server（提供上下文和能力的程序）。
- 数据层基于 JSON-RPC 2.0；传输层有 stdio 和 Streamable HTTP。
- 服务端三类原语：Tools（模型调用的函数）、Resources（上下文数据）、Prompts（交互模板）。
- 2026-07-28 版本改为无状态：去掉 `initialize` 握手，每个请求在 `_meta` 里带版本和能力，新增 `server/discover`。

**追问链**：
1. Tools 和 Resources 有什么区别？→ Tools 是可执行的动作，由模型决定调用；Resources 是数据，由应用决定是否读入上下文。
2. 接了很多 MCP Server 后有什么问题？→ 工具定义一次性加载会占满上下文；大量中间结果要经过模型。可以按需检索工具，或让 Agent 写代码调用 MCP、在执行环境里过滤数据。
3. 第三方 MCP Server 安全吗？→ 工具描述和返回内容都可能带注入，要当作不可信输入；远程服务用 OAuth 授权，按最小权限开放工具。

**易错点**：
- 说“有了 MCP 就不需要 Function Calling 了”。两者在不同层。

## core-tool-005 A2A 和 MCP 有什么区别，什么时候用 A2A
- level: 2
- tags: [core]

**一句话答案**：MCP 连接 Agent 和工具，A2A 连接 Agent 和 Agent；对方是需要推理、多轮交互、有自己状态，并且由别的团队或组织维护的 Agent 时，才用 A2A。

**要点**：
- A2A 由 Google 在 2025-04 发布，规范已发布 1.0.0。
- Agent Card：JSON 文档，描述身份、技能、端点和认证方式，位置在 `/.well-known/agent-card.json`。
- Task 是有状态的工作单元，有 submitted、working、input-required、completed、failed 等状态；输出放在 Artifact 里。
- 官方说法：MCP 是纵向的，加深单个 Agent；A2A 是横向的，连接不同 Agent。A2A 服务端内部可以再用 MCP。

**追问链**：
1. 同一个系统里的子 Agent 要不要走 A2A？→ 通常不需要，函数调用或框架内的子 Agent 更简单；需要跨团队发现、认证和长时任务管理时才值得。
2. 为什么 Task 要有 input-required 状态？→ 被委派的 Agent 可能需要补充信息，任务暂停等调用方回复，而不是直接失败。

**易错点**：
- 把 A2A 说成 MCP 的替代品。两者解决的是不同连接。

## core-tool-006 Agent Skills 是什么，为什么要渐进式加载
- level: 2
- tags: [core, harness]

**一句话答案**：Skill 是以 `SKILL.md` 为核心的文件夹；启动只加载 `name` 和 `description`，相关时才读正文，附加文件和脚本用到才读或执行，所以装很多 Skill 也不撑爆上下文。

**要点**：
- 出处：Anthropic，Equipping agents for the real world with Agent Skills，2025-10。
- 三级：元数据 → `SKILL.md` 正文 → 附加文件；脚本执行时代码本身不进上下文。
- 编写约束：`name` 最多 64 字符、小写字母数字和连字符；`description` 最多 1,024 字符；正文建议 500 行以内。
- 和工具的区别：工具是一个动作，Skill 是一类事的做法，里面可以指导调用哪些工具。

**追问链**：
1. Skill 没被触发怎么办？→ 先查 `description`：有没有同时写清做什么和什么时候用，有没有包含用户会说的关键词。
2. Skill 有什么安全风险？→ 恶意 Skill 可能带有害指令或脚本，诱导数据外泄。只从可信来源安装，否则先审计里面的文件和依赖。

**易错点**：
- 以为 Skill 会在启动时全部读进上下文。

## core-tool-007 模型总是选错工具，你怎么排查和解决
- level: 3
- tags: [core, harness, evaluation]

**一句话答案**：先看轨迹确认模型看到的工具列表，再把错误分类（没调、调错、参数错、结果没用好），然后依次查描述重叠、工具数量和上下文干扰，用回归集验证每次修改，最后才考虑训练。

**要点**：
- 轨迹：工具定义有没有被截断或拼错。
- 描述：两个工具是否功能重叠，是否缺“什么时候不用”，参数格式是否清楚。
- 数量：按场景路由、按需检索工具、限定本轮可调用集合；OpenAI 的软性建议是一轮开始时少于 20 个函数，并要实测。
- 上下文：关键信息埋在中间或被旧工具结果淹没。
- 评测：把错例加进回归集，按选择准确率、调用次数和成功率对比修改前后。

**追问链**：
1. 有 200 个工具，怎么组织？→ 按服务做命名空间；先路由到场景再暴露子集，或给一个工具搜索工具按需加载定义；高频的少数工具常驻。
2. 动态加载工具和前缀缓存冲突吗？→ 会。工具定义在缓存前缀最前面，改动会让后面全部失效。可以保持工具列表不变、只用允许列表限制本轮可调用的工具，或把动态加载放在后面的消息里（看接口是否支持）。
3. 什么情况下要微调？→ 描述和结构都改过，评测仍显示某类选择稳定出错，并且有足够的正确轨迹做训练数据时。

**易错点**：
- 一上来就说“换更强的模型”或“微调”，没有先看轨迹和描述。

## core-tool-008 Function Calling 一轮并行调用时，tool_result 应该怎么回传
- level: 2
- tags: [core, harness]

**一句话答案**：原样放回 assistant 消息，再用一条 user 消息给每个调用回一个结果，按 ID 对应、结果块排最前；失败或没执行的也要回，标 is_error。

**要点**：
- Anthropic：`tool_result` 紧跟 `tool_use` 消息；结果块在 user 消息最前，文字放后面；少回一个直接 400。
- 每个结果有 `tool_use_id`、`content`、可选 `is_error`。OpenAI 用 `function_call_output` 和 `call_id`。
- 执行顺序由应用决定：独立只读可并行，有副作用或依赖的串行；串行时前一个失败、后面不跑的，也回一个错误结果。
- OpenAI 的 `arguments` 是 JSON 字符串，Anthropic 的 `input` 是对象。

**追问链**：
1. 为什么不把每个结果拆成单独的消息？→ Anthropic 文档说这样会“教会”模型少做并行调用；格式规则要求一轮结果放在同一条消息里。
2. 工具抛异常时怎么回？→ 写成 `is_error: true` 的结果，内容写清错在哪、怎么改；循环要限制重试次数，防止模型在同一个错误上打转。

**易错点**：
- 只把成功的结果写回，超时或被拒绝的调用没有结果，下一次请求报错。

## core-tool-009 strict 模式是怎么保证参数合法的，它保证不了什么
- level: 2
- tags: [core, inference]

**一句话答案**：用约束解码，每步只允许 schema 合法的 token，所以类型、必填、枚举一定对；但它不管语义和权限，不支持的约束也不是硬约束，应用侧仍要校验。

**要点**：
- Anthropic：`strict: true` 保证 `input` 符合 `input_schema`、工具名合法。
- OpenAI：底层是 Structured Outputs，要求每个 object `additionalProperties: false`、字段全列进 `required`，可选字段写成可为 null。
- 只支持 JSON Schema 子集；Anthropic SDK 会把 `minimum` 这类约束移进描述、在本地校验。
- schema 首次使用有处理开销，之后缓存。约束解码原理见 inference/05 第 7 节。

**追问链**：
1. 可选字段改成“必填但可为 null”有什么坑？→ 模型会给每个字段填值，没想填的填 null；执行前要把 null 当作没传、换成默认值。
2. 开了 strict 还会出什么参数错误？→ 值合法但不合理，例如城市不存在、日期在过去、越权的资源 ID，要靠语义校验和权限检查。

**易错点**：
- 以为开了 strict 就可以去掉应用侧的参数校验。

## core-tool-010 Toolformer 怎么判断一个自动插入的 API 调用值得保留
- level: 3
- tags: [core, training]

**一句话答案**：比较后续 token 的加权损失：给调用和结果的 L+，对比不调用和只给调用不给结果两者中较小的 L−；L− − L+ 至少达到阈值 τf 才保留。

**要点**：
- L_i(z) = −Σ w_{j−i} log p(x_j | z, x_{1:j−1})，权重 w̃_t = max(0, 1 − 0.2t) 归一化，只覆盖调用后 5 个 token。
- L− 取 min：只给调用就已经好预测，说明起作用的是问题本身，不是工具结果。
- 论文默认 τs = 0.05、τf = 1.0、k = 5、m = 5；计算器和翻译工具 τf 降到 0.5。
- 保留的调用插回原文，用普通语言模型目标微调；文本内容和原数据集相同。

**追问链**：
1. 权重为什么随距离衰减？→ 让调用出现在结果马上能用上的位置附近；离得远的收益不计分。
2. 今天训练工具调用时，工具结果的 token 怎么处理？→ loss mask 设 0，否则模型学着预测、编造工具结果；mask 要按段在 token 上做。

**易错点**：
- 把 L− 说成“不调用时的损失”，漏掉“只给调用不给结果”这一项。

## core-tool-011 MCP 2026-07-28 版为什么去掉 initialize 握手，新旧版本怎么共存
- level: 3
- tags: [core, harness]

**一句话答案**：改成无状态：每个请求在 _meta 里带版本和客户端能力，服务端不记连接状态，任何实例都能处理，便于横向扩展；兼容靠 server/discover 探测，失败退回 initialize。

**要点**：
- 旧版：`initialize` 协商版本和能力 → `notifications/initialized`；HTTP 有 `Mcp-Session-Id`。
- 新版：去掉握手和会话；新增服务端必须实现的 `server/discover`；版本不支持返回 -32022 并列出支持的版本。
- 订阅改为 `subscriptions/listen` 按类型订阅；服务端反向请求改成返回 `input_required` 结果。
- Roots、Sampling、Logging 标为弃用；跨调用状态用服务端生成的句柄当工具参数传。

**追问链**：
1. 去掉会话后，需要跨调用保存的状态放哪？→ 服务端自己生成句柄，作为普通工具参数在后续调用里传；过期时返回工具执行错误让模型重建。
2. MCP 的两类错误怎么区分处理？→ 未知工具、格式错误是 JSON-RPC error，进日志告警；执行失败放 result 的 isError: true，交给模型改参数重试。

**易错点**：
- 以为新版里能力协商没了。能力仍然要声明，只是从握手挪到了每个请求的 `_meta`。
