# 题目：Agent 架构与设计模式

> 对应知识章：[README.md](README.md)。先闭卷作答，再看答案。

## core-agent-001 什么是 Agent，和直接调用大模型有什么区别
- level: 1
- tags: [core, harness]

**一句话答案**：Agent 是模型加循环、工具和状态，步数和顺序由模型在运行时根据中间结果决定；直接调用时控制流由程序写死。

**要点**：
- 四个组成：模型做决策，循环重复“决定 → 执行 → 读工具结果”，工具获取外部事实或改变外部状态，状态记录每一步结果。
- 本质区别在于控制流由谁决定。
- 代价是不可预测：成本、延迟、正确性都要靠 Harness 管住。

**追问链**：
1. 单次 Function Calling 算不算 Agent？→ 不算。它只是一次结构化输出，没有循环；把它放进循环、让模型看到结果再决定下一步才是。
2. 状态放在哪？→ 短期状态在上下文里；需要持久化时写到外部的会话日志或存储，上下文是从日志装配出来的视图。
3. 一个 Agent 系统里哪些部分通常不是 Agent？→ 路由、校验、返回一般是固定流程。

**易错点**：
- 回答“能自主完成任务的 AI”。没有结构，接不住追问。
- 把“有工具”当成 Agent 的标志。决定性的是循环和运行时决策。

## core-agent-002 Agent 和 Workflow 怎么选
- level: 1
- tags: [core, harness]

**一句话答案**：步骤能提前枚举就用 Workflow，不能才用 Agent；真实系统通常是路由在前、两者混用。

**要点**：
- Anthropic 的区分：Workflow 按预先写好的代码路径编排模型和工具；Agent 由模型动态决定流程。
- 判断顺序：单次调用加检索 → Workflow → Orchestrator-Workers → Agent，能停在前面就停。
- 混合架构：简单请求走固定流程，复杂请求进 Agent，最后统一校验。

**追问链**：
1. 给一个必须用 Agent 的例子？→ 修一个陌生仓库里的 bug：要读哪些文件、改几处、跑什么测试，事先都不知道。
2. 用 Agent 后怎么控制成本？→ 步数和 token 上限、按难度路由、缓存重复的工具调用、失败时回退到固定流程。
3. 怎么判断当初选 Agent 是对的？→ 和 Workflow 基线在同一评测集上比成功率、成本和延迟，Agent 的收益要覆盖它的额外成本。

**易错点**：
- 默认所有任务都上 Agent，说不出 Workflow 的优势：可预测、便宜、好测试。

## core-agent-003 Anthropic 归纳的五种 Workflow 模式各适合什么场景
- level: 1
- tags: [core, harness]

**一句话答案**：按场景选：步骤固定用链式，输入类型差别大用路由，子任务独立或要投票用并行，子任务运行时才知道用 Orchestrator-Workers，有清晰评价标准用 Evaluator-Optimizer。

**要点**：
- 增强型 LLM（带检索、工具、记忆）是这些模式的基础构件；五种 Workflow 之上才是 Agent。
- Chaining（链式）：步骤固定的长任务，步骤之间可以加程序校验。
- Routing（路由）：输入类型差别大，例如客服里的退款、咨询、投诉分开处理。
- Parallelization（并行）：分段并行处理独立子任务，或同一任务跑多次投票提高置信度。
- Orchestrator-Workers：子任务事先不知道，由中心模型动态拆分。
- Evaluator-Optimizer：有清晰评价标准，一个生成、一个当评委，循环改进。

**追问链**：
1. Orchestrator-Workers 和 Parallelization 的区别？→ Parallelization 的子任务是事先写好的，Orchestrator-Workers 的子任务由模型运行时决定。
2. Evaluator-Optimizer 什么时候会失效？→ 评委模型和生成模型犯同类错误，或者评价标准模糊，循环只会在原地打转。要设最大轮数，并尽量用可执行的检查（测试、规则）代替模型评委。

**易错点**：
- 只会背名字，给不出场景和代价。

## core-agent-004 ReAct 的核心思想是什么，和今天的 Function Calling 是什么关系
- level: 1
- tags: [core, training]

**一句话答案**：ReAct 让模型交替输出推理和动作，再读取工具结果；Function Calling 把动作变成结构化输出，但“推理 → 行动 → 工具结果”的循环没变。

**要点**：
- 出处：Yao 等，arXiv 2210.03629，2022 年 10 月。
- 推理帮助模型规划和处理异常，动作从环境获取事实，减少只靠推理产生的幻觉。
- 早期靠 prompt 约定 Thought / Action / Observation 的文本格式，需要解析；原生 Function Calling 由模型直接输出结构化调用，解析错误少了很多。

**追问链**：
1. 推理部分还需要显式写出来吗？→ 推理模型会在内部或单独的推理段里思考，不一定要求 prompt 里写 Thought；但面向用户或日志时，保留每一步的理由有助于调试。
2. ReAct 的主要失败模式？→ 重复调用同一工具陷入循环、对错误的工具结果深信不疑、过早给出答案。对应的 Harness 手段是循环检测、结果校验和终止条件。

**易错点**：
- 把 ReAct 说成一个框架或一个库。它是一种 prompting 方法。

## core-agent-005 把控制流交给模型有哪些代价，怎么控制
- level: 2
- tags: [core, harness]

**一句话答案**：三类代价：成本和延迟不可预测、错误逐步累积、难以测试和复现；分别靠预算与路由、结果校验与回退、完整轨迹与分层评测来控制。

**要点**：
- 预算：最大步数、token 上限、单工具调用次数上限、总超时。
- 校验：工具返回做格式和合理性检查，关键步骤用确定性代码检查。
- 回退：Agent 失败或超预算时退到固定流程或转人工。
- 复现：记录每一步的输入、输出、工具调用和结果，评测时对轨迹和最终状态分别打分。

**追问链**：
1. 步数上限设多少？→ 先看评测集上成功轨迹的步数分布，取一个高分位数（例如 P95）再留余量，并对超限请求单独统计，不要拍脑袋。
2. 超过上限怎么办？→ 不要直接报错：返回当前已有的部分结果并说明，或交给固定流程或人工。
3. 怎么发现模型陷入循环？→ 检测连续相同的工具调用和参数，或相同的工具结果重复出现。

**易错点**：
- 只说“加个 max_steps”，没有说怎么定值、超限后怎么处理。

## core-agent-006 设计题热身：给一个企业知识库问答，你选什么架构
- level: 3
- tags: [core, harness]

**一句话答案**：先路由：能直接检索回答的走“检索加单次生成”的 Workflow；需要跨文档比较、多步查询的才进 Agent；最后统一做引用校验。

**要点**：
- 先估流量结构：大部分是单文档就能回答的问题，少数需要多步。
- 快档：查询改写 → 检索 → 重排 → 生成并附引用。
- 慢档：Agent 可调用检索、表格查询、计算工具，设步数和预算上限。
- 校验：答案里的每条结论都要能对上引用片段，否则降级为“未找到依据”。
- 评测：按快慢档分别建评测集，统计路由准确率。

**追问链**：
1. 路由用什么做？→ 先用规则加小模型分类；用线上日志里“快档回答被用户否定”的样本迭代路由。
2. 路由错了怎么办？→ 快档检索置信度低或校验失败时自动升级到慢档。
3. 怎么证明慢档值得？→ 在同一批难题上比较两档的正确率和成本。

**易错点**：
- 一上来就画多 Agent 架构，没有先分析请求分布。

## core-agent-007 加一个验证器并最多重试 R 次，成功率怎么算，上限由什么决定
- level: 2
- tags: [core, harness, evaluation]

**一句话答案**：每轮分三种结局：对且放行、错但放行、被拦下重来。成功率随 R 增大趋于“放行输出里正确的比例”，上限由验证器的漏检率决定，不由轮数决定。

**要点**：
- 记号：p 一次生成做对，α 放行正确输出的概率，v 拦下错误输出的概率。A = p·α，B = (1−p)(1−v)，C = 1−A−B。
- 前 R−1 轮被拦下就重来，第 R 轮直接交出：P = A(1 + C + … + C^{R−2}) + C^{R−1}·p。
- 完美验证器时 P = 1 − (1−p)^R；R → ∞ 时 P → A/(A+B)。
- 例：p = 0.6、α = 0.95、v = 0.8、R = 3 时约 0.843，上限 0.877。

**追问链**：
1. 什么情况下加验证器反而更差？→ 验证器拦不住错（v 低）又会误拦对的（α < 1）：被误拦的正确输出换来一次可能错的新生成，成功率低于 p。
2. 怎么在上线前估这个上限？→ 用一批有标准答案的样本单独测验证器的 α 和 v，代入公式；比盲目调大 R 更有用。
3. 为什么可执行检查优于模型评委？→ 单测、编译、schema 校验的 v 接近 1；同一个模型当评委和生成者犯同类错误，v 低。

**易错点**：
- 以为重试次数越多越好。漏过去的错误每轮都在漏，重试救不回来。

## core-agent-008 ReAct 循环的步数上限怎么定，定高了和定低了各有什么后果
- level: 2
- tags: [core, harness]

**一句话答案**：看评测集上成功轨迹的步数分布，取尾部再留余量，并配循环检测。定低了截掉能做对的长轨迹；定高了成功率不涨，卡住的试次把上限花满，成本上涨。

**要点**：
- 终止步 τ 只在模型输出 finish 时停的话可以是无穷大；步数上限是循环一定会停的唯一硬保证。
- 每个试次的期望步数 = 成功部分的 E[min(K, N)] + 卡住比例 × N，卡住的试次每个都花满 N 步。
- 循环检测让卡住的试次早停，上限就可以放宽而不增加成本。
- ReAct 论文按“再加步数也不涨”定上限：HotpotQA 7 步、FEVER 5 步。

**追问链**：
1. 只取成功轨迹步数的 P95 够不够？→ 不够，会截掉最长的 5%；要再留余量，并单独统计因超限失败的比例。
2. 换了模型还能用原来的上限吗？→ 不能，步数分布会变，要在评测集上重测。
3. 超限后返回什么？→ 已完成的部分、当前进度和停下的原因，由调用方决定追加预算、转人工或交付部分结果。

**易错点**：
- 直接用框架默认值。默认值反映框架定位，不反映你的任务。

## core-agent-009 ReAct 和 ReWOO 的输入 token 随工具步数怎么增长
- level: 2
- tags: [core, harness, inference]

**一句话答案**：ReAct 每个工具步都调一次模型并重读全部历史，输入 token 随步数二次增长；ReWOO 一次写出全部调用、最后汇总一次，只调 2 次模型，输入随步数线性增长。

**要点**：
- 记号：固定前缀 P 个 token，每步追加 g 个 token，n 个工具步。
- ReAct：Σ_{i=0}^{n}(P + i·g) = (n+1)P + g·n(n+1)/2。
- ReWOO：规划器读 P，求解器读 P + n·g，共 2P + n·g。
- ReWOO 论文摘要报告 HotpotQA 上 5 倍 token 效率；代价是中间结果出乎意料时不能调整。

**追问链**：
1. 前缀缓存能消掉 ReAct 的二次项吗？→ 能让重复读入的前缀更便宜、更快，但读入的 token 数不变，上下文仍会撞上窗口上限。
2. Plan-and-Execute 省在哪？→ 大模型只做规划和重规划，执行器只看问题和当前一步，可以用小模型；调用次数不一定少，贵的调用少了。
3. 什么时候还是选 ReAct？→ 每一步都要看工具结果再决定下一步、结果难以预测时。

**易错点**：
- 把论文报告的 5 倍当成通用常数。倍数取决于步数、前缀长度和每步追加的长度。
