# 题目：RAG、搜索与 Deep Research

> 对应知识章：[README.md](README.md)。先闭卷作答，再看答案。

## core-rag-001 讲一下 RAG 的完整流程，每一步可能出什么问题
- level: 1
- tags: [core]

**一句话答案**：离线是解析、切块、嵌入建索引；在线是查询改写、多路召回、融合、重排、带引用生成、校验；每一环都可能失败，排查时从前往后查。

**要点**：
- 解析：表格和 PDF 版面解析错，检索到了也读不懂。
- 切块：意思被切断，或块里缺主语、时间等上下文。
- 召回：用户问法和文档写法差别大；专有名词在向量里区分不开。
- 重排：好文档排在后面被截掉。
- 生成：模型不用资料或混入参数知识；引用的段落不支持该句话。
- 出处：Lewis 等，arXiv 2005.11401，2020-05，把生成模型和向量索引组合起来。

**追问链**：
1. 用户说答案错了，你怎么排查？→ 先看相关文档有没有进候选集，再看重排后是否还在，最后看生成是否用了它；三步分别对应召回、重排、生成的问题。
2. 什么时候不用 RAG？→ 知识库很小时可以直接全放进 prompt，不做检索。（背景：Anthropic 的 Contextual Retrieval 文章给的参考门槛是 20 万 token 以内。）
3. RAG 和微调怎么选？→ 知识会变、需要出处时用 RAG；要改的是输出风格、格式或特定任务能力时考虑微调。两者可以叠加。

**易错点**：
- 只讲“向量库 + top-k + 拼 prompt”，说不出解析、重排、引用校验。

## core-rag-002 为什么要做混合检索，两路结果怎么合并
- level: 1
- tags: [core]

**一句话答案**：向量检索擅长语义相近，对专有名词和编号不敏感；BM25 相反；两路互补。合并常用 RRF，只按排名打分，避免两路分数尺度不一致。

**要点**：
- RRF（Cormack 等，SIGIR 2009）：`RRF(d) = Σ 1 / (k + r(d))`，论文取 k = 60。
- 多路都排在前面的文档得分最高。
- 分数直接相加的问题：BM25 分数没有上限，余弦相似度在固定区间，尺度不同。
- 权限、时间等结构化条件在检索层过滤。

**追问链**：
1. k 的作用是什么？→ 平滑排名的影响：k 越大，第一名和第十名的差距越小。
2. 除了 RRF 还有什么融合方法？→ 分数归一化后加权求和；或者把两路候选合并后统一交给重排模型，此时融合方式就不那么重要了。
3. 为什么权限不能在生成阶段处理？→ 文档进了上下文，模型就可能泄露；必须在检索时就过滤掉无权限文档。

**易错点**：
- 说“向量检索已经包含关键词信息，不需要 BM25”。错误码、型号、人名这类查询上向量检索常常失败。

## core-rag-003 切块怎么做，块的大小怎么定
- level: 2
- tags: [core]

**一句话答案**：先按文档结构切，结构差时用固定长度加重叠或语义切块；需要完整上下文时用父子块或给块加上下文说明；大小没有通用最优，要在自己的检索评测集上试。

**要点**：
- 块太大检索不精确、占上下文；块太小丢上下文。
- 父子块：小块检索，返回所在大块。
- Contextual Retrieval（Anthropic，2024-09）：给每块生成 50-100 token 的上下文说明后再建向量和 BM25 索引；以 top-20 召回失败率衡量，只加上下文嵌入降 35%，加上下文 BM25 降 49%，再加重排降 67%。
- 代码按函数或类切，表格整表保留或按行加表头。

**追问链**：
1. Contextual Retrieval 的成本怎么控制？→ 文章用 prompt 缓存：整篇文档缓存一次，为每个块生成说明时复用。
2. 文档更新了怎么办？→ 按文档维护块的映射，只重建变更文档的块；删除时同步删向量和关键词索引里的条目。
3. 怎么评测切块效果？→ 固定其他环节，只换切块策略，在标注了相关段落的问题集上比 Recall@k。

**易错点**：
- 报一个固定数字当答案，例如“512 token 最好”，说不出评测依据。

## core-rag-004 重排模型有哪几类，为什么要两段式检索
- level: 2
- tags: [core, inference]

**一句话答案**：双塔快但粗，用于召回；晚交互居中；交叉编码器和 LLM 重排精但慢，只用于少量候选。两段式是先快速召回较多候选，再精排出少量放进上下文。

**要点**：
- 双塔：查询和文档分别编码，文档向量可预先算。
- 晚交互（ColBERT，arXiv 2004.12832）：分别编码但保留 token 级向量，最后做细粒度匹配；论文报告精度和 BERT 排序器相当，速度快两个数量级。
- 交叉编码器：查询和文档拼在一起打分，每对都要算一次。
- Contextual Retrieval 文章的设置：先取 150 条，重排后留 20 条。

**追问链**：
1. 重排的延迟怎么控制？→ 限制候选数；用小的交叉编码器；对热门查询缓存结果。
2. 重排后放几条进上下文？→ 在评测集上试；Contextual Retrieval 文章比较了 5、10、20 条，20 条最好，但这和数据与模型相关。
3. 用 LLM 重排有什么风险？→ 成本高、延迟高，还可能受文档顺序和长度影响。

**易错点**：
- 把重排模型和召回用的 embedding 模型混为一谈。

## core-rag-005 固定流程 RAG 和 Agentic RAG 怎么选
- level: 2
- tags: [core, harness, training]

**一句话答案**：问题类型集中、一次检索就够时用固定流程，便宜可预测；需要判断资料够不够、要多跳或开放探索时，把检索做成工具交给模型决定，并设好次数和预算上限。

**要点**：
- Self-RAG（arXiv 2310.11511）：训练模型输出反思 token，自己决定何时检索并评价结果。
- CRAG（arXiv 2401.15884）：轻量评估器给检索结果打分，按置信度决定直接用、改用网页搜索或两者结合。
- Search-o1（arXiv 2501.05366）：推理模型在不确定时发起搜索，先提炼长文档再放回推理链。
- Search-R1（arXiv 2503.09516）：用 RL 训练多轮搜索，检索 token 在 loss 中屏蔽，只用结果奖励。训练细节见 [Agentic RL](../../tracks/training/04-agentic-rl/README.md)。
- 编程助手常用 grep 和读文件代替向量检索，因为代码标识符精确、代码变化快。

**追问链**：
1. 多跳问题在固定流程里怎么做？→ 查询分解或 IRCoT 式交替检索，但跳数和流程要预先设计。
2. Agentic RAG 怎么防止无限检索？→ 设最大检索次数和 token 预算；连续几次没有新信息就停；重复查询检测。
3. 为什么 Search-R1 要屏蔽检索回来的 token？→ 这些 token 不是模型生成的，算进策略梯度会让训练不稳定。

**易错点**：
- 认为 Agentic RAG 总是更好。它的延迟和成本不可预测，调试也更难。

## core-rag-006 设计一个 Deep Research 系统
- level: 3
- tags: [core, harness, evaluation]

**一句话答案**：主 Agent 拆问题、派并行子 Agent；子 Agent 在独立上下文里搜索，交回压缩的发现；主 Agent 汇总并决定是否继续；引用环节把论断对到来源；用预算、覆盖条件和收益递减控制停止。

**要点**：
- 参考 Anthropic 公开的研究系统结构（2025-06）：主 Agent、并行子 Agent、引用 Agent；计划写入记忆，防止上下文超长时丢失。
- 投入按复杂度分配：简单事实 1 个 Agent、3-10 次工具调用；直接比较 2-4 个子 Agent；复杂研究 10 个以上。
- 成本：文章报告多 Agent 系统 token 约为普通对话的 15 倍；在 BrowseComp 上 token 用量单独解释了 80% 的性能差异（这是整体规律，不是多 Agent 与单 Agent 的对比）。
- 停止条件：预算上限、每个子问题都有可靠来源、连续几轮无新信息、来源冲突时查权威来源或在报告中写明分歧。

**追问链**：
1. 子 Agent 之间重复搜索怎么办？→ 主 Agent 派任务时写清边界和不要做什么；共享已访问来源列表。
2. 怎么评测？→ 短答案能力用 BrowseComp 这类可核对的题；长报告用评委模型按事实准确、引用准确、完整性、来源质量打分，加人工抽检。Anthropic 文章提到早期从约 20 条真实查询开始就能看出大的改动效果。
3. 怎么避免引用低质量来源？→ 来源质量打分或白名单；Anthropic 文章提到人工测试发现早期 Agent 偏好 SEO 内容农场。

**易错点**：
- 只画结构，不讲停止条件和成本。面试官最关心的是怎么不让它跑飞。

## core-rag-007 怎么评测一个 RAG 系统
- level: 3
- tags: [core, evaluation]

**一句话答案**：检索侧和生成侧分开测。检索看 Recall@k、MRR 等；生成看忠实度（论断能否从检索内容推出）和答案相关性；端到端看正确率、引用准确率和拒答是否恰当。

**要点**：
- 不分层就无法定位问题出在召回、重排还是生成。
- Ragas（arXiv 2309.15217）：一套不需要人工参考答案的指标，覆盖检索质量、忠实度、生成质量。
- 引用准确率：逐句检查引用段落是否支持这句话。
- 拒答用例：资料里没有答案时，应该说没有。
- 位置影响：Lost in the Middle（arXiv 2307.03172）发现相关信息在开头或结尾时效果最好，在长上下文中间时明显变差，评测时可以打乱顺序看稳定性。

**追问链**：
1. 评测集怎么来？→ 从线上真实问题抽样，人工标注相关文档和参考答案；补充模型生成的合成问题，但要人工抽检。
2. 用模型当评委可靠吗？→ 有位置偏差、冗长偏差、自我偏好等；要和人工标注对一致性，固定评委模型和 prompt。见 [LLM-as-Judge](../../tracks/evaluation/02-llm-as-judge/README.md)。
3. 线上怎么监控？→ 看无结果率、用户追问或纠正比例、引用点击率；定期抽样人工复核。

**易错点**：
- 只看端到端准确率，或者只看检索召回率，没有分层。

## core-rag-008 BM25 的 k1 和 b 分别控制什么，为什么词频要饱和
- level: 2
- tags: [core]

**一句话答案**：k1 控制词频饱和的速度，同一个词重复出现的增益越来越小，有上限；b 控制长度归一化强度，0 不归一化，1 完全按 dl/avgdl 缩放。饱和让各命中一个词的文档胜过堆砌一个词的文档。

**要点**：
- 打分：Σ IDF(t) · tf·(k1+1) / (tf + k1·((1−b) + b·dl/avgdl))。
- tf = k1·B 时到达上限的一半；k1 → 0 退化成二值权重，k1 → ∞ 退化成线性 tf·idf。
- 饱和来自精英性模型：词频是“文档是否在讲这个主题”的带噪证据，证据再多也不超过“确知是精英”的权重。
- 软归一化折中两个假设：啰嗦假设（应除以长度）和范围假设（长文档讲得更多，不该除）。
- 背景：Robertson 和 Zaragoza 的综述（2009）给的经验范围是 0.5 < b < 0.8、1.2 < k1 < 2；Lucene 默认 k1 = 1.2、b = 0.75。

**追问链**：
1. IDF 怎么来的，为什么有的实现会出现负值？→ 来自 RSJ 权重，无标注时取 p = 0.5、不相关文档近似全体文档，得 log((N−n+0.5)/(n+0.5))；n > N/2 时为负。Lucene 改成 log(1 + …)，恒为正。
2. b = 1 时把一篇文档复制拼接两遍，分数怎么变？→ 不变：tf 和 dl 同时翻倍，tf/B 不变。b = 0 时分数会上升。
3. 不同库的 BM25 分数能直接比吗？→ 不能。分子上的 (k1+1) 有的实现省掉，IDF 写法不同，分数还依赖语料统计，只有同一索引内的排序有意义。

**易错点**：
- 把 BM25 说成“tf·idf 加长度归一化”，漏掉饱和；或者把 BM25 分数当跨查询、跨语料的固定阈值用。

## core-rag-009 交叉编码器为什么比双塔准，150 个候选时贵多少（BERT-base 规模、查询 32 token、文档 180 token）
- level: 3
- tags: [core, inference]

**一句话答案**：交叉编码器每一层都让查询和文档互相注意，文档表示依赖查询；双塔为了能离线建索引，打分必须分解成两个独立向量的点积。代价约为 n·(Lq+Ld)/Lq，150 个候选时约是一次双塔查询的一千倍。

**要点**：
- 双塔：sim = E_q(q)ᵀE_d(d)，文档向量离线算好，在线只编码查询（DPR 论文明确为了可分解而选这种形式）。
- 交叉编码器：每个候选把“查询 + 文档”整段过一遍模型，约 2P·(Lq+Ld) FLOPs；双塔在线约 2P·Lq。
- 150 × 212 / 32 ≈ 994，所以只用在召回后的少量候选上。
- 晚交互（ColBERT）居中：保留 token 向量，MaxSim 打分；论文报告重排时比 BERT 排序模型快 170 倍以上，代价是每个 token 存一个向量。

**追问链**：
1. 单向量为什么会把“讲八个话题、其中一个能回答”的文档排低？→ 文档向量是各话题的平均，相关话题被稀释；MaxSim 让每个查询 token 单独找最像的文档 token，不受稀释影响。
2. 重排的延迟怎么控制？→ 限制候选数，用小模型，块长不超过模型输入上限，热门查询缓存。
3. 候选里的长块有什么问题？→ 交叉编码器有长度上限（monoBERT 是 512 token），超出部分被截掉，答案在后半段的块会被低估。

**易错点**：
- 说交叉编码器“模型更大所以更准”。关键是查询和文档之间的交互发生在每一层，而不是参数量。

## core-rag-010 RRF 里的 k = 60 起什么作用，为什么不能把 BM25 分数和余弦直接相加
- level: 2
- tags: [core]

**一句话答案**：RRF 只看名次，对分数尺度不敏感；直接相加时尺度大的 BM25 说了算，换语料分数一变排序就变。k 削弱单路第一名的影响：k 大于 8 时，两路都排第 10 胜过只在一路排第 1。

**要点**：
- RRF(d) = Σ_i 1/(k + r_i(d))，Cormack 等（SIGIR 2009）在试点实验里定下 k = 60，并说取值不关键。
- 推导：1/(k+1) = 2/(k+10) 解得 k = 8；k = 60 时第 1 名的贡献只比第 10 名多约 15%。
- BM25 没有上限，依赖 IDF、查询长度和实现；余弦在 [−1, 1]。名次在任何单调变换下不变。
- RRF 不保证总不低于较好的一路：一路很差又排了很多错误文档时，会把它们带进来，要在评测集上比。

**追问链**：
1. 想利用分数间距怎么办？→ 每个查询内做 min-max 或 z-score 归一化后加权求和，权重在评测集上调。
2. 两路候选合并后交给交叉编码器重排，还需要 RRF 吗？→ 融合方式影响变小，但 RRF 仍决定送进重排的候选截断在哪里。
3. 多查询改写后怎么合并？→ 同样用 RRF 把每个改写的结果融合。

**易错点**：
- 把 r(d) 写成分数，或从 0 开始计名次；某一路没返回该文档时也给它加一项。
