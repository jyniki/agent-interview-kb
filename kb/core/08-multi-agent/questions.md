# 题目：多 Agent 系统

> 对应知识章：[README.md](README.md)。先闭卷作答，再看答案。

## core-multi-001 什么时候该用多 Agent，什么时候不该用
- level: 1
- tags: [core, harness]

**一句话答案**：子任务依赖弱、可以并行、信息量超过一个上下文窗口、任务价值能付得起数倍 token 时才用；子任务强依赖、输出必须保持一致时用单 Agent。

**要点**：
- 收益：并行降低延迟；每个子 Agent 有独立上下文，总共能处理更多信息；角色专一，prompt 和工具更聚焦。
- 代价：token 成倍增加；交接时丢上下文；子 Agent 看不到彼此的决策，输出容易冲突；调试更难。
- Anthropic 研究系统的文章写明，需要共享同一份上下文、Agent 间依赖多的领域不适合，例如大多数编程任务。
- Cognition 的文章主张默认用单线程 Agent，理由是动作里隐含决策，冲突的决策带来坏结果。

**追问链**：
1. 给一个适合多 Agent 的场景？→ 调研类问题，例如“比较五个开源向量库的特性”：五个方向可以并行查，各自压缩结论后汇总。
2. 给一个不适合的？→ 在一个仓库里实现一个功能：多个文件的改动要互相一致，拆给多个并行 Agent 容易接口对不上。
3. 单 Agent 上下文装不下，又不想拆怎么办？→ 先做上下文压缩，把历史动作和决策总结成关键要点；或者用子 Agent 只回答窄问题，不让它并行改东西。

**易错点**：
- 把多 Agent 当成默认的“高级架构”，说不出单 Agent 的优势。
- 只讲收益，不讲 token 成本和交接损失。

## core-multi-002 常见的多 Agent 拓扑有哪些，各自的代价是什么
- level: 1
- tags: [core]

**一句话答案**：中心调度、流水线、交接、辩论与投票、黑板共享状态；代价分别是主 Agent 单点与汇总丢信息、错误向下游传递、接手方上下文不足、成本高且收益不稳定、并发写冲突。

**要点**：
- 中心调度：主 Agent（orchestrator）拆任务、并行派发、汇总，适合调研。
- 流水线：按角色顺序传产物，MetaGPT 把 SOP 写进 prompt，适合流程固定的任务。
- 交接：分诊 Agent 把对话交给专门 Agent，适合客服。
- 辩论：多个实例多轮互评后收敛，适合有标准答案的推理。
- 黑板：各 Agent 读写共享状态，适合异步补充一份结果。

**追问链**：
1. 交接（handoff）和把 Agent 当工具调用有什么区别？→ 交接把对话控制权交出去，接手方继续和用户对话；当工具调用时控制权留在调用方，专家只返回结果。
2. 中心调度里主 Agent 同步等待子 Agent 有什么问题？→ 一个慢的子 Agent 会卡住整批；主 Agent 也没法中途调整子 Agent。改成异步能提高并行度，但结果协调、状态一致和错误传播都更复杂。

**易错点**：
- 只会列框架名（AutoGen、MetaGPT、LangGraph），说不出拓扑本身的取舍。

## core-multi-003 多 Agent 之间怎么交接任务和共享状态
- level: 2
- tags: [core, harness]

**一句话答案**：交接内容要结构化，至少写清目标、输出格式、工具和资料范围、任务边界；关键决策要共享，共享状态要有归属或版本控制，并持久化以便续跑。

**要点**：
- 消息传递：上下文隔离，但任务描述写不清子 Agent 就会做错事。
- 完整轨迹共享：决策不丢，但上下文变长、成本上升，敏感数据也一起传出去。
- 共享状态：可持久化可恢复，要处理并发写和版本。
- 子 Agent 返回也要结构化：结论、依据、未完成部分。

**追问链**：
1. 两个子 Agent 同时改同一字段怎么办？→ 每个 Agent 只写自己负责的字段；或者写入带版本号，版本不匹配就拒绝并让后写者重读再改。
2. 交接时要不要把全部历史传过去？→ 看依赖强弱。接手方要基于之前的决策继续时要传，至少传关键决策的摘要；只做独立子任务时传任务描述即可。传之前过滤掉接手方不需要的工具结果和敏感字段。
3. 长任务进程重启怎么办？→ 计划和阶段结论写在外部存储，从检查点续跑，而不是从头再来。

**易错点**：
- 只传一句“帮我查一下 X”，没有输出格式和边界，子 Agent 重复劳动或做偏。

## core-multi-004 多 Agent 系统常见的失败模式有哪些，怎么防
- level: 2
- tags: [core, harness, evaluation]

**一句话答案**：MAST 分类把失败分成三类：系统设计问题、Agent 间未对齐、任务验证不足；对应的手段是写清角色和终止条件、结构化交接、用可执行检查做验证。

**要点**：
- 出处：Cemri 等，arXiv 2503.13657，2025-03，共 14 种失败模式。
- 系统设计问题：角色不清、不遵守约束、没有终止条件、步骤重复。
- 未对齐：交接丢信息、忽视其他 Agent 的输入、推理和行动不一致。
- 验证不足：过早结束、验证不完整或错误。
- 运行时问题：子 Agent 超时、互相委派成环、长任务中途出错，分别用超时加部分结果、委派深度和轮数上限、检查点续跑来处理。

**追问链**：
1. 为什么“再加一个审核 Agent”不一定有用？→ 审核 Agent 和生成 Agent 可能犯同类错误，或者只看表面就放行。能用测试、规则、数据库状态检查的，优先用可执行检查。
2. 怎么发现 Agent 互相踢皮球？→ 记录委派链，检测重复出现的任务描述和来回交接；超过委派深度或轮数直接终止并上报。
3. 新版本上线时正在跑的长任务怎么办？→ 新旧版本同时运行，流量逐步切换，不打断进行中的任务（Anthropic 称为彩虹部署）。

**易错点**：
- 把失败都归因于“模型不够强”，说不出结构上的原因。

## core-multi-005 辩论或投票类多 Agent 一定比单模型好吗
- level: 2
- tags: [core, evaluation]

**一句话答案**：不一定。辩论原论文报告推理和事实性有提升，但后续对比发现默认设置下它并不稳定地优于 self-consistency 这类单模型多次采样方法，而且对超参数敏感。

**要点**：
- Du 等（arXiv 2305.14325）：多个实例多轮互相评论答案，报告数学推理和事实性提升。
- Smit 等（arXiv 2311.17371）：比较成本、时间和准确率，默认设置的辩论不能稳定胜过 self-consistency；调整 Agent 之间“多容易同意对方”这类参数后才能超过。
- 公平比较要对齐采样次数或 token 预算。

**追问链**：
1. 为什么辩论可能变差？→ 多个实例相关性高，会一起附和错误答案；或者被一个自信但错的实例带偏。
2. 什么时候值得用？→ 有可验证的标准答案、单次错误代价高，且已经证明比同预算的多次采样更好时。

**易错点**：
- 引用“辩论提升准确率”时不提对照基线和成本。

## core-multi-006 怎么证明你的多 Agent 系统比单 Agent 好
- level: 3
- tags: [core, evaluation]

**一句话答案**：在同一题集上对比三组：多 Agent、单 Agent、同等 token 预算的单 Agent；同时报质量、成本和延迟，再用过程指标定位收益或损失来自拆分、交接还是汇总。

**要点**：
- 为什么要同预算基线：Anthropic 报告在 BrowseComp 上 token 用量单独解释了 80% 的表现差异，不控制预算就分不清收益来自结构还是来自多花钱。
- 量级：Anthropic 给出多 Agent 系统比聊天多用约 15 倍 token，收益必须覆盖这部分成本。
- 质量：终态正确性、引用准确、完整性，可以用 LLM 评委按 rubric 打分，并用人工抽检校准。
- 过程：子任务重复率、交接后做错事的比例、汇总时丢掉的关键事实数。
- 起步：用几十条代表真实使用的查询就能看出早期大改动的效果；效果变小后扩样本、做配对比较。

**追问链**：
1. 评委要不要检查 Agent 走了哪条路径？→ 主要评结果和过程是否合理，不要求固定步骤，因为不同的合理路径都可能成功。路径只用来定位问题。
2. 质量提升 3 个点、成本翻倍，值不值？→ 看任务价值和失败代价，换算成每多答对一题的额外成本，再和业务收益比；也可以只把难题路由到多 Agent。
3. 分解质量怎么评？→ 很难自动评。先看结果层指标，再人工抽查失败样本的分解计划，把“结果差且分解有问题”的样本积累成专门的测试集。

**易错点**：
- 只和一个弱的单 Agent 比，不控制 token 预算。
- 只报质量，不报成本和延迟。

## core-multi-007 主从结构的子 Agent 并行只读调研，为什么同样工具调用次数下输入 token 反而比单 Agent 少
- level: 2
- tags: [core, harness]

**一句话答案**：每步都要重读整个上下文，单 Agent 的工具结果全堆在一起，输入随总步数平方增长；子 Agent 只背自己那几步，二次项少了约 N 倍。实际总 token 更高，是因为子 Agent 被允许多搜。

**要点**：
- 一个上下文从 B₀ 开始、每步加 c、走 k 步，输入总量 B₀·k + c·k(k-1)/2。
- 单 Agent k = N·s，二次项约 c·N²s²/2；主从每个子 Agent k = s，合计约 N·c·s²/2。
- 主从多两次调用（规划、汇总），子 Agent 只看到任务描述。
- 前缀缓存会让单 Agent 重读的历史大多按命中价计费，差距明显缩小。
- Anthropic 报告多 Agent 系统比聊天多用约 15 倍 token，主要来自更多、并行的搜索。

**追问链**：
1. 计入前缀缓存后结论怎么变？→ 单 Agent 每步只有最新的工具结果是新 token，其余按缓存价，差距从几倍缩到两倍以内甚至更小。
2. 那为什么还说多 Agent 贵？→ 子 Agent 每个方向搜得更多、彼此重复搜索，步数一多总输入就反超单 Agent。
3. 要把完整轨迹传给每个子 Agent 呢？→ 相当于每个子 Agent 从主 Agent 的长上下文起步，隔离的省钱效果基本消失。

**易错点**：
- 把“多 Agent 多用 15 倍 token”理解成拆分结构本身贵。
- 算成本时忘了每步重读整个上下文。

## core-multi-008 主 Agent 同步等 10 个并行子 Agent，单个平均 60 秒且耗时服从指数分布，期望要等多久
- level: 2
- tags: [core, harness]

**一句话答案**：等的是最大值：E[max] = μ·H_N，H_10 ≈ 2.93，约 176 秒；长尾分布下更糟，所以要设截止时间，到点用已完成的结果继续并注明缺失。

**要点**：
- 最小值期望 μ/N；由无记忆性，下一个再等 μ/(N-1)，累加得 μ·(1 + 1/2 + … + 1/N)。
- H_N ≈ ln N + 0.577，随 N 对数增长，但一直在增长。
- 截止时间 D 时完成个数的期望是 N·P(T ≤ D)。
- Anthropic 文中把同步执行列为瓶颈：一个慢的子 Agent 会卡住整个系统。

**追问链**：
1. 截止时间设短有什么代价？→ 结果不完整，最终答案要注明缺失的方向，或者重派慢的子任务。
2. 改成异步能解决吗？→ 能提高并行度，但结果协调、状态一致和错误传播都更复杂。
3. 怎么从监控上发现这个问题？→ 平均延迟正常但 P90 很高，延迟随子 Agent 个数上升；看最慢者和中位数的比值。

**易错点**：
- 用单个子 Agent 的平均耗时估计并行后的延迟。

## core-multi-009 5 个 Agent 各自正确率 80%，错误独立和完全相关时，串联全对与多数投票的成功率各是多少
- level: 3
- tags: [core, evaluation]

**一句话答案**：独立时串联 0.8⁵ ≈ 0.33，投票约 0.94；完全相关时两者都是 0.8。投票收益和 1-ρ 成正比，靠多样性；串联靠一致性。

**要点**：
- 相关模型：以概率 ρ 所有 Agent 一起对或一起错，否则独立；单个正确率仍是 p。
- 串联 = ρ·p + (1-ρ)·pᴺ；投票 = ρ·p + (1-ρ)·P_独立(多数正确)。
- ρ = 0.5 时串联约 0.56，投票约 0.87。
- 同一模型的多个实例盲点相同，ρ 高，投票、辩论、审核 Agent 的收益都变小。

**追问链**：
1. 怎么降低相关性？→ 换不同模型、不同 prompt、不同资料来源；最好用测试、规则这类可执行检查，它和生成模型的错误不相关。
2. 流水线为什么要在中间产物上加检查？→ 串联成功率随阶段数指数下降，中间检查把错误挡在下游之前。

**易错点**：
- 默认多个实例的错误互相独立，高估投票和审核的效果。

## core-multi-010 多 Agent 辩论的一致率越来越高，能说明答案越来越可信吗
- level: 2
- tags: [core, evaluation]

**一句话答案**：不能。Du 等自己指出辩论通常收敛，但答案不一定对，错时模型仍自信地说与他人一致；实例越相关，辩论越接近把第一轮多数传播给所有人。

**要点**：
- 流程：N 个实例各自作答，每轮把其他人的回答拼进上下文，让每个实例参考后更新，重复多轮。
- 代价：调用 N·R 次，输入里其他人答案的部分随 N² 增长；实例多时论文先总结再给每个实例。
- 论文观察：模型比较“随和”；更鼓励坚持己见的 prompt 辩论更长、结果更好；长辩论时模型只关注最近几轮。
- 对照基线应是同等调用次数的多次采样取多数（Smit 等）。

**追问链**：
1. 评测辩论系统要报什么？→ 正确率和一致率分开报，再和同调用次数的 self-consistency 比，同时报 token 和延迟。
2. 怎么让辩论不只是跟随多数？→ 混用不同模型，用鼓励坚持的 prompt，有可验证答案时直接验证。

**易错点**：
- 把共识当成正确性的证据。
