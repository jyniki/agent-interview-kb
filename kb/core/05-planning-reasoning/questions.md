## core-plan-001 CoT 为什么有效，Self-Consistency 又改进了什么
- level: 1
- tags: [core]

**一句话答案**：CoT 让模型先写中间步骤再给答案，相当于给多步问题更多计算；Self-Consistency 采样多条推理路径，对最终答案投票，减少单条路径出错的影响。

**要点**：
- 出处：Wei 等，arXiv 2201.11903，2022-01；Self-Consistency 是 Wang 等，arXiv 2203.11171，2022-03。
- CoT 论文发现效果在模型足够大时才明显，小模型写出的步骤可能是错的。
- Self-Consistency 的前提是答案能比对，例如数字或选项；开放式输出没法直接投票。
- 推理模型把 CoT 变成训练出来的能力，调用时不必再要求“一步一步想”。

**追问链**：
1. Self-Consistency 和 Best-of-N 什么关系？→ Self-Consistency 是 Best-of-N 的特例，用多数投票代替打分器，所以不需要 verifier。
2. 采样数怎么定？→ 成本线性增长，收益递减；按题目难度分配，简单题少采或不采。Snell 等（2024-08）的结论是按难度分配算力比统一 Best-of-N 效率高。
3. 开放式任务想用多路径怎么办？→ 用打分器或评委模型选，或者让模型合并多份答案；但要清楚评委本身也会出错。

**易错点**：
- 说“CoT 让模型学会了推理”。CoT 是推理时的 prompting 方法，不改权重。
- 把 Self-Consistency 说成多次生成后取最长或最详细的。它按最终答案投票。

## core-plan-002 ReAct 和 Plan-and-Execute 怎么选
- level: 1
- tags: [core, harness]

**一句话答案**：步骤短、信息要边做边得到就用 ReAct；步骤多但结构清楚就先写计划再执行，并配好重规划。

**要点**：
- ReAct 每一步都看最新的工具结果再决定，适应性强，但长任务容易忘目标、走偏。
- Plan-and-Execute 有全局视角，计划可以校验、展示给用户、断点恢复；代价是计划可能和现实不符。
- ReWOO 是更极端的解耦：一次写出所有工具调用，执行完再汇总。论文报告在 HotpotQA 上省 5 倍 token，但中间结果出乎意料时无法调整。
- 实际常混用：高层用计划，每个步骤内部用 ReAct。

**追问链**：
1. 计划放在哪？→ 放进 Harness 的结构化状态，例如带状态字段的步骤列表；不要只留在对话历史里，否则无法校验和恢复。
2. 用推理模型还需要 Plan-and-Execute 吗？→ 单轮内的推理模型已经会自己规划；但跨很多轮、要人工确认或要断点恢复的任务，显式计划仍然有用，它解决的是可控性，不只是推理质量。
3. ReWOO 为什么省 token？→ ReAct 每一步都要把前面所有内容重新送进模型；ReWOO 只在规划和汇总时调用模型。

**易错点**：
- 认为 Plan-and-Execute 一定比 ReAct 好。环境变化快时，计划写完就过时。

## core-plan-003 Agent 按计划执行时，重规划机制怎么设计：什么时候触发、改哪些步骤、怎么防止无限重规划
- level: 2
- tags: [core, harness]

**一句话答案**：在工具失败、结果不符预期、用户改需求或预算过半时触发，保留已完成步骤，只重写剩余部分，并限制同一步的失败次数。

**要点**：
- 触发条件要明确；每步都重规划浪费 token，从不重规划会一条路走到黑。
- 只改剩余步骤，避免重复执行有副作用的操作，例如重复下单、重复发邮件。
- 同一步失败次数设上限，超限就换方案或交给人。
- 重规划时写下原因，防止后面又走回老路。

**追问链**：
1. 怎么判断“结果不符预期”？→ 计划里每一步带预期产出或检查条件，例如“返回至少一个可订航班”；执行后用程序或模型对照。
2. 有副作用的步骤怎么处理？→ 标记为不可重复，重规划时视为已完成；需要撤销时走显式的补偿步骤，例如取消订单。
3. 重规划本身失败了怎么办？→ 设总重规划次数上限，超限后输出当前进展和失败原因，请用户决定。

**易错点**：
- 重规划时推倒重来。已完成的步骤和结果要保留。
- 只说“出错就重新规划”，说不出触发条件和终止条件。

## core-plan-004 模型自我反思、自我纠错真的有用吗
- level: 2
- tags: [core, evaluation]

**一句话答案**：有外部反馈时有用，例如测试结果、编译错误、检索到的事实；只靠模型自评时，推理任务上的纠错并不可靠，有时改完更差。

**要点**：
- Huang 等（arXiv 2310.01798，2023-10）：没有外部反馈时，模型很难纠正自己的推理答案。
- Reflexion（arXiv 2303.11366）有效，是因为它用了环境信号判断成败，再把文字反思存进记忆；它不更新权重。
- Self-Refine（arXiv 2303.17651）在改写类任务上有收益，但评委和作者是同一个模型，会犯同类错误。
- 工程上的分级：可执行检查 > 外部事实对照 > 模型自评。

**追问链**：
1. 编程 Agent 里怎么用反思？→ 跑测试，把失败信息交给模型，模型分析原因再改；反馈来自测试，不是模型自己判断。
2. 只能靠模型当评委时怎么减少偏差？→ 用不同模型或不同 prompt 当评委，给明确的检查清单，设最大轮数。评委偏差的细节见 [evaluation/02 LLM-as-Judge](../../tracks/evaluation/02-llm-as-judge/README.md)。
3. Reflexion 的反思存在哪、存多久？→ 存在情景记忆里，在后续尝试时放进上下文；要控制条数，否则过时的反思会误导模型。

**易错点**：
- 把 Reflexion 当成“模型自己想想就变好”的证据。它依赖环境反馈。
- 认为反思轮数越多越好。没有新信息时，多轮反思只是原地打转。

## core-plan-005 ToT、MCTS、Best-of-N 有什么区别，什么时候值得用搜索
- level: 2
- tags: [core, inference]

**一句话答案**：Best-of-N 独立生成多个完整答案再选；ToT 在中间步骤展开多个候选并可回溯；MCTS 用树搜索平衡探索和利用。它们都依赖能可靠评估答案或中间状态，评估不了就不值得搜。

**要点**：
- ToT（arXiv 2305.10601）：论文报告，Game of 24 上同一模型从 CoT 的 4% 提到 ToT 的 74%。这个任务中间状态清楚、对错可验。
- RAP（arXiv 2305.14992）：同一个模型既提出下一步，又预测下一步的状态，用 MCTS 搜索。
- 过程奖励模型给每一步打分，可以引导搜索；Lightman 等在 MATH 上发现过程监督优于结果监督。
- 成本排序大致是 Best-of-N < ToT < MCTS，延迟也随之变高。

**追问链**：
1. 写营销文案适合用 ToT 吗？→ 不适合，中间状态没法可靠打分；生成几个版本让人挑更实际。
2. Best-of-N 的打分器不准会怎样？→ 会系统性地选出“打分器喜欢”而不是正确的答案，N 越大越容易选中钻空子的答案。
3. 在线服务里怎么控制搜索成本？→ 按难度路由，只对难题搜索；设节点数、token、时间上限，超限输出当前最优。

**易错点**：
- 只讲算法，不讲评估信号从哪来。没有可靠评估，搜索只是更贵的随机采样。

## core-plan-006 模型写出的推理过程可信吗，对 Agent 审计有什么影响
- level: 3
- tags: [core, evaluation]

**一句话答案**：不一定可信。实验表明模型会被 prompt 里的偏置影响答案，却在解释里不提这个原因；所以审计要以工具调用和输入为证据，CoT 只能作辅助信号。

**要点**：
- Turpin 等（arXiv 2305.04388，2023-05）：把 few-shot 示例的正确答案总放在 (A)，模型偏向选 (A)，但解释几乎从不提这一点（人工检查的 426 条解释里只有 1 条提到）；在 BIG-Bench Hard 13 个任务上准确率最多下降 36%。
- CoT 是模型生成的文本，和其他输出一样可能是事后合理化。
- 审计证据：工具调用、参数、返回、被读取的上下文，这些是可复现的事实。
- 监控 CoT 能发现一部分异常意图；没发现不代表没有。

**追问链**：
1. 那还要不要保留推理日志？→ 要。它对调试有用，能看出模型误解了什么；只是不能单独作为合规或责任判定的依据。
2. 怎么测一个 Agent 的推理是否忠实？→ 做干预实验：改掉推理中声称依赖的信息，看答案是否跟着变；或者加入一个推理里没提的偏置，看答案是否被它影响。
3. 推理模型的隐藏推理怎么办？→ 只能拿到摘要或拿不到时，更要依赖外部可观测的行为轨迹。轨迹怎么采集见 [Trace 与回放](../../tracks/harness/06-tracing-replay/README.md)。

**易错点**：
- 认为“让模型解释理由”就实现了可解释性。
- 把“推理看起来合理”当成“答案正确”的证据。

## core-plan-007 什么时候不该给 Agent 加显式规划
- level: 3
- tags: [core, harness, inference]

**一句话答案**：任务一两步能完成、环境变化快需要边做边看、已经用了推理模型且只是单轮任务、或计划不会真正约束执行时，加显式规划只会多花 token 和延迟。

**要点**：
- 简单任务写计划的成本可能超过任务本身，应路由到单次调用。
- 环境变化快时，计划写完就过时，频繁重规划不如 ReAct。
- 推理模型已经会内部规划，再要求它在输出里列计划，和内部推理重复。
- 计划只写在对话里、执行器不按它推进，就只是装饰。
- 显式规划真正的价值是可控性：可校验、可展示、可恢复。需要这些时才加。

**追问链**：
1. 怎么用数据证明加规划有用？→ 在同一评测集上对比有无规划的成功率、步数、token 和延迟；同时看计划质量和执行忠实度，而不只看终态。
2. 一个客服 Agent 要不要规划？→ 大多数请求一两步就能完成，不要；少数跨系统的复杂工单，例如退货加换货加补偿，可以路由到带计划的流程。
3. 规划和预算怎么配合？→ 计划里每步可以带预算，执行中超支就触发重规划或提前收尾。

**易错点**：
- 默认“加规划一定更好”，说不出代价。
- 把规划和推理混为一谈。前者是系统怎么排步骤，后者是模型单次怎么想。

## core-plan-008 Self-Consistency 的采样数 k 无限增大时，多数票正确率的上限由什么决定
- level: 2
- tags: [core, inference]

**一句话答案**：链独立时，单条正确率 p 大于一半的题趋于全对，小于一半的趋于全错，上限是这类题的占比；链之间错误相关时，上限进一步降到 ρ·p + (1 − ρ)。

**要点**：
- 独立、二选一时，答对链数服从 Binomial(k, p)，多数票正确率是 J > k/2 的概率；大数定律给出 k → ∞ 的极限是 1[p > 1/2]。
- 评测集上单次正确率是 E[p_q]，无限投票的上限是 P(p_q > 1/2)，投票救不了模型多数时候做错的题。
- 用“以概率 ρ 所有链抄同一份”的混合模型，上限是 ρ·p + (1 − ρ)；ρ = 0.5、p = 0.6 时是 0.8。
- 错误答案分散时，众数只需超过每个错误答案，p < 0.5 的题也可能被救回。

**追问链**：
1. 为什么不能用贪心解码重复 k 次？→ 贪心解码每次输出相同，相当于 ρ = 1，投票没有任何收益；要靠温度采样制造独立性。
2. 投票后准确率不涨，先查什么？→ 先查答案归一化是否把同一个正确答案拆成多个票仓，再查 k 条链的去重答案数，判断是不是相关性太高。
3. k 取多大？→ 收益随 k 递减；用 Hoeffding 界粗估，偏离 1/2 越小需要的 k 越大，所以按题目难度分配，简单题少采。

**易错点**：
- 认为采样越多一定越好。p < 1/2 且错误集中时，投票会把正确率压向 0。
- 忽略链之间的相关性，把独立假设下的曲线当成真实收益。

## core-plan-009 没有外部反馈时，自我纠错一轮后正确率上升还是下降，取决于什么
- level: 3
- tags: [core, evaluation]

**一句话答案**：取决于错改对的概率 b 和对改错的概率 a 之比是否超过当前赔率 p/(1−p)；初始正确率越高越容易改差，多轮后收敛到 b/(a+b)，与起点无关。

**要点**：
- 一轮后 p' = p(1 − a) + (1 − p)b，提升条件是 b(1 − p) > a·p。
- 不动点 p* = b/(a + b)：初始正确率高于它时，多轮纠错越改越差。
- 外部检查只把被标出的答案交给模型改，对改错那一项被乘上误报率 f，所以有外部检查时纠错更容易有正收益。
- 和 Huang 等（arXiv 2310.01798）的观察一致：拿掉 oracle 标签后，推理任务上的纠错提升消失甚至变差；模型更常把对的改错，而不是把错的改对。

**追问链**：
1. 怎么在自己的系统里测 a 和 b？→ 在有标签的评测集上跑一轮纠错，统计“对→错”和“错→对”的比例。
2. 多智能体辩论能绕过这个问题吗？→ Huang 等报告，相同回答数下辩论不比 Self-Consistency 好；没有外部信号时，多花的调用直接拿去投票至少一样。
3. 那 Reflexion 为什么有效？→ 它用环境信号（任务成败、测试结果）决定是否需要反思，相当于有外部检查；用自生成测试时会出现假阳性。

**易错点**：
- 只说“自我纠错没用”，说不出它在什么条件下有用。
- 用同一个初始 prompt 弱、纠错 prompt 强的对比，把 prompt 差异当成纠错收益。

## core-plan-010 规划调用有成本、能降低单步错误率时，任务多长才值得先写计划
- level: 3
- tags: [core, harness]

**一句话答案**：出错要整轮重来时，期望成本是一轮成本除以 (1 − e)^n；规划降错误率带来的指数收益超过规划调用成本时才划算，所以短任务亏、长任务赚，不降错误率时永远亏。

**要点**：
- 不规划 E = n·c/(1 − e₀)^n，规划 E = (C_plan + n·c)/(1 − e₁)^n。
- 回本条件 ((1 − e₁)/(1 − e₀))^n > 1 + C_plan/(n·c)：左边随 n 指数增长，右边随 n 减小，所以存在回本步数。
- 例子：c = 1、C_plan = 3、e₀ = 0.05、e₁ = 0.03 时，n = 12 开始回本（本章第 8 节代码）。
- e₁ = e₀ 时左边恒为 1，规划在任何长度都亏，例如推理模型已经在内部做了同样的分解。

**追问链**：
1. 有局部重试时结论怎么变？→ 不规划的成本增长变慢，回本步数后移；但只要单步错误会传给后续步骤，指数项还在。
2. 怎么估 e₀ 和 e₁？→ 在同一评测集上对比有无计划时每步工具调用的失败率和返工率。
3. 除了成本，还有什么理由写计划？→ 可控性：计划可以校验依赖、展示给用户确认、断点恢复；这些需求本身就可能值得付规划成本。

**易错点**：
- 只看规划后的成功率，不算规划调用本身的成本和延迟。
- 认为步数多就一定该规划，忽略了规划若不降低错误率就没有收益。
