# 题目：记忆系统

> 对应知识章：[README.md](README.md)。先闭卷作答，再看答案。

## core-memory-001 Agent 的上下文和记忆有什么区别
- level: 1
- tags: [core, harness]

**一句话答案**：上下文是这一次调用送进模型的 token，记忆是存在模型外部、跨调用保留的信息，用时检索一部分放进上下文。

**要点**：
- 模型本身无状态，所有“记得”都要靠每次装配上下文实现。
- MemGPT 的比喻：上下文窗口是内存，外部存储是磁盘，系统负责换入换出。
- 上下文的风险是太长、重点被淹没；记忆的风险是记错、过时、串号、被投毒。
- 四类记忆：工作记忆、情景记忆、语义记忆、程序性记忆。

**追问链**：
1. 上下文窗口越来越长，还需要记忆吗？→ 需要。长窗口有成本和延迟，放在中间的信息也更容易被忽略；跨会话的信息本来就不在窗口里。
2. 程序性记忆为什么常存成代码？→ 可以执行和测试，能组合复用。Voyager 把验证过的技能存成代码库。
3. Reflexion 属于哪类记忆？→ 情景记忆：把失败后的文字反思存下来，下次尝试时读取，不改权重。

**易错点**：
- 把对话历史等同于记忆。原样保留的历史只是日志，记忆需要筛选、结构化和维护。

## core-memory-002 什么信息值得写进长期记忆，什么时候写
- level: 1
- tags: [core, harness]

**一句话答案**：未来会用到、又没法从别处廉价重新获得的信息才值得记，例如用户的明确偏好、反复的纠正、任务结论和原因；时机可选每轮同步、会话结束批量、后台异步或由模型主动写。

**要点**：
- 不记寒暄、一次性情绪、能从文档或代码里直接查到的内容、未经验证的猜测。
- 每轮同步写不丢信息但增加延迟；会话结束写便宜但异常中断会丢；后台写不影响响应，但新会话可能读不到；当前会话的信息仍在上下文里。
- 模型主动写的一个例子是 Anthropic memory tool：模型用 view、create、str_replace 等命令操作 `/memories` 下的文件，文件操作由应用在客户端执行。
- 每条记忆带来源、时间、置信度、用户 ID。

**追问链**：
1. 模型推断出的信息要不要记？→ 可以记，但标为“推断”、置信度低；和用户明确陈述冲突时以用户为准，必要时向用户确认。
2. 后台异步写导致下一轮读不到怎么办？→ 当前会话的信息仍在上下文里，下一轮直接可用；长期记忆的延迟只影响新会话。
3. 怎么防止记得太多？→ 写入前和已有记忆去重；设单用户条数上限；定期合并相似条目。

**易错点**：
- 回答“全都存下来，检索时再筛”。噪声会拉低检索质量，也增加隐私风险。

## core-memory-003 记忆检索只用向量相似度够吗
- level: 2
- tags: [core, harness]

**一句话答案**：不够。还要考虑时效和重要性；Generative Agents 用时效、重要性、相关性三个信号，各自归一化后加权求和；工程上再按记忆类型选结构化查询、关键词或混合检索。

**要点**：
- Generative Agents（arXiv 2304.03442）：时效按距上次访问的小时数做指数衰减，系数 0.995；重要性由模型在写入时打 1-10 分；相关性是 embedding 余弦相似度。三项 min-max 归一化，权重都是 1。
- 字段明确的偏好用结构化查询最准；专有名词用关键词；措辞多变的用向量。
- 记忆和文档检索的区别：记忆会变，要处理时效和冲突。

**追问链**：
1. 权重怎么调？→ 在自建评测集上调；例如偏好类问题提高重要性，近况类问题提高时效。
2. 重要性在写入时打分有什么问题？→ 写入时的判断可能不准，事后才发现重要；可以在被频繁检索或被用户引用时提高分数。
3. 检索出的记忆怎么放进上下文？→ 标明来源和时间，放在固定位置；数量要控制，避免挤占任务信息。

**易错点**：
- 记不清三个信号或说成“相似度加时间戳”，说不出归一化和组合方式。

## core-memory-004 新旧记忆冲突怎么处理
- level: 2
- tags: [core, harness]

**一句话答案**：写入新事实前先取出最相似的旧记忆，让模型判断新增、更新、删除还是不变；裁决时新的优先、用户明确陈述优先，拿不准就保留两条并标注冲突，删除改为标记失效。

**要点**：
- Mem0（arXiv 2504.19413）：对每条候选事实，先取语义最相似的若干条（论文取 10 条），由模型通过工具调用选择 ADD、UPDATE、DELETE、NOOP。
- 区分状态改变（搬家）和临时情况（出差），后者应设有效期而不是覆盖。
- 来源可信度：用户明确陈述 > 工具返回 > 模型推断。
- 保留历史版本，便于审计和回滚。

**追问链**：
1. 两个写入方同时改同一条记忆怎么办？→ 用版本号做乐观锁，写入时校验版本，冲突就重新读取后再判断；或者按用户串行化写入。
2. 模型判断错了把对的记忆删了怎么办？→ 删除只做软删除，保留历史；关键字段的删除需要更强的证据，例如用户明确说出。
3. Mem0 的方案比把全部历史放进上下文好在哪？→ 只检索相关的少量记忆，输入短，延迟和成本低；代价是漏召回时准确率下降。

**易错点**：
- 只说“用最新的覆盖旧的”，没考虑临时情况和来源可信度。

## core-memory-005 长任务中断后，Agent 怎么恢复到原来的进度
- level: 2
- tags: [core, harness]

**一句话答案**：把上下文当作从持久化状态装配出的视图；持久化完整事件日志、任务状态和进度笔记，恢复时先读状态和笔记，再从断点继续。

**要点**：
- 事件日志：每轮输入、模型输出、工具调用和结果，可重放可审计。
- 任务状态：计划和每步状态，知道做到哪一步、哪些步骤有副作用已经执行。
- 进度笔记：已完成什么、下一步做什么、关键决定。
- Anthropic memory tool 文档的多会话模式：第一个会话建立进度日志和功能清单，之后每个会话开头读、结尾更新，功能端到端验证后才标完成。

**追问链**：
1. 这和上下文压缩有什么区别？→ 压缩在同一会话里缩短历史，会丢细节；记忆把必须保留的信息写到外部，压缩后还能取回。两者常一起用。
2. 恢复时有副作用的步骤怎么处理？→ 状态里记录是否已执行和结果；不确定是否执行成功时，先查询外部系统确认，而不是直接重做。
3. 进度笔记由谁写？→ 可以让模型在关键节点写，也可以由 Harness 按任务状态自动生成；前者灵活，后者可靠。

**易错点**：
- 只保存对话历史，恢复时整段塞回去。历史可能超长，也说不清做到了哪一步。

## core-memory-006 记忆系统有哪些安全和隐私风险，怎么防
- level: 3
- tags: [core, harness]

**一句话答案**：主要有串号、敏感信息落库、记忆投毒、路径越权和删不干净；对应做法是按用户强制过滤和隔离、写入前脱敏、限制写入来源、规范化路径、记录所有副本位置。

**要点**：
- 串号：每条记忆带用户 ID，检索层强制过滤，不依赖模型自觉。
- 投毒：网页或文档中的注入写进记忆后，会在以后每次相关检索时生效，比一次性注入影响更久。只有用户明确陈述能写高权限记忆，工具返回内容标注来源并降权。
- 路径越权：文件型记忆要规范化路径并校验仍在记忆目录内，memory tool 文档给了 `/memories/../../secrets.env` 的例子。
- 删除：用户要求删除时，向量索引、缓存、备份里的副本都要处理。

**追问链**：
1. 怎么发现已经被投毒的记忆？→ 定期扫描记忆里的指令性内容，例如“以后都要”“忽略之前”；对记忆的来源做审计，溯源到写入它的那次会话。
2. 多人共享的团队记忆怎么设计？→ 区分个人和共享空间；共享记忆的写入需要更高权限或审核；检索时标明来自谁。
3. 用户说“忘掉我的地址”，怎么保证真删了？→ 按用户 ID 和内容定位所有副本，包括 embedding；删除后跑一次检索验证不再返回。

**易错点**：
- 只谈加密存储，不谈检索时的隔离和写入来源控制。

## core-memory-007 怎么评测一个记忆系统
- level: 3
- tags: [core, evaluation]

**一句话答案**：按能力拆开测：信息抽取、跨会话推理、时间推理、知识更新、不知道时拒答；再加上写入和检索的延迟、每次请求增加的 token 作为工程指标。

**要点**：
- LongMemEval（arXiv 2410.10813）用这五项能力，500 道人工整理的题，嵌在长度可调的对话历史里；作者报告商用助手和长上下文模型在长期交互中准确率下降约 30%。
- 知识更新的用例：先说 A，后改成 B，问现在是什么，答 A 算错。
- 拒答的用例：问从未提过的信息，编造答案算错。
- 隔离的用例：用 B 用户的会话问 A 用户的信息，必须拿不到。

**追问链**：
1. 怎么区分是写入错了还是检索错了？→ 分层测：先检查记忆库里有没有正确条目，再检查检索有没有取到，最后看生成有没有用上。
2. 线上怎么监控？→ 看用户纠正的频率（“我说过我不吃辣”），以及记忆被检索但没被使用的比例。
3. 和“全部历史放进上下文”的基线怎么比？→ 在同一评测集上比准确率、延迟和 token；记忆系统要在可接受的准确率损失内省下明显的成本。

**易错点**：
- 只用最终回答的准确率，定位不了问题出在写入、检索还是生成。

## core-memory-008 MemGPT 的主上下文和外部上下文各分哪几部分，换页怎么触发
- level: 2
- tags: [core, harness]

**一句话答案**：主上下文是只读系统指令、定长可写的工作上下文和 FIFO 消息队列；外部是 recall 和 archival 两个存储。token 过警告阈值先提醒模型存要事，过清空阈值就换出消息、更新递归摘要。

**要点**：
- 工作上下文只能经函数调用写，存用户关键事实和角色设定；FIFO 第一位放被换出消息的递归摘要。
- 队列管理器把每条消息同时写入 recall storage，换出的消息仍可用函数调用取回。
- 论文举的数字：警告阈值约为窗口的 70%，清空阈值 100%，一次换出约 50%。
- 检索结果分页返回，防止一次检索撑满窗口；`request_heartbeat=true` 让模型串联多个函数调用。

**追问链**：
1. 为什么先警告再换出？→ 递归摘要会丢细节，警告给模型一次机会把必须保留的信息挪到工作上下文或 archival。
2. MemGPT 和 Generative Agents 的检索有什么根本区别？→ MemGPT 由模型自己调用函数决定换入什么；Generative Agents 用固定公式打分。
3. 工程上工作上下文对应什么？→ 每次都装配进 prompt 的固定区，放过敏、预算这类不能靠检索碰运气的关键约束。

**易错点**：
- 把 recall storage 和 archival storage 混为一谈。前者是消息原样记录，由队列管理器写；后者是任意文本的数据库，由模型调用函数写。

## core-memory-009 Generative Agents 的时效分用 min-max 归一化，会带来哪些副作用
- level: 3
- tags: [core, harness]

**一句话答案**：整体变旧时归一化后的时效不变，所以衰减删不掉任何记忆；同时候选集内很小的差异被拉成满量程，时效权重一大，刚写入的寒暄就能挤掉重要的旧记忆。

**要点**：
- 时效 = 0.995 的 Δt 次方，Δt 是距上次访问的游戏小时数；半衰期 ln0.5/ln0.995 ≈ 138 小时。
- 所有记忆再过 s 小时都乘同一个 0.995^s，min-max 后完全消掉，排序不变。
- 0.30、0.31、0.32 归一化后是 0、0.5、1，和差距很大时一样。
- 遗忘要另算不归一化的保留分（如重要性 × 衰减），配 TTL 和容量上限。

**追问链**：
1. 怎么减轻小差异被放大？→ 先用相关性粗筛出候选集再打分；或对关键约束走固定区，不参与排序。
2. 时效按最近访问而不是创建时间算有什么后果？→ 被取出一次就刷新，常用记忆一直新鲜，形成正反馈；冷门的重要记忆越来越难取到。
3. 保留分会把很久不用的过敏信息淘汰吗？→ 会，重要性 9、闲置 1000 小时保留分只有约 0.006；要用“钉住”标记排除。

**易错点**：
- 以为设了衰减系数，旧记忆就会自然淡出或被删除。

## core-memory-010 用户先说住北京、模型推断在上海、又说这周去广州出差、最后说搬到上海，记忆该怎么变
- level: 2
- tags: [core, harness]

**一句话答案**：先记北京；模型推断可信度低，不覆盖，记为冲突待确认；出差是临时情况，叠一层带有效期的值，到期回落北京；用户明确说搬家是状态改变加显式覆盖，当前值改为上海，北京进历史。

**要点**：
- 三条规则：同可信度新的覆盖旧的；用户明确陈述 > 工具结果 > 模型推断；用户说“改成”“以后都”时直接覆盖。
- 区分状态改变（覆盖底值）和临时情况（TTL 叠加，不覆盖）。
- 旧值软删除进历史表，便于审计和回滚；用户的删除请求除外，要真删。
- Mem0 把 ADD/UPDATE/DELETE/NOOP 的判断交给模型，工程上再用上述确定性规则兜底。

**追问链**：
1. 低可信来源的冲突什么时候处理？→ 下次相关话题时向用户确认，确认后按显式覆盖处理，否认就丢弃。
2. 这条规则对投毒有什么作用？→ 网页或工具结果里的内容不能改掉用户自己说过的事，挡住一类写入型注入。
3. 出差 TTL 怎么定？→ 用户给了时间就用它；没给就按类别给默认值，并在到期前允许续期。

**易错点**：
- 一律“最新的覆盖旧的”，出差结束后系统还以为用户在广州。
