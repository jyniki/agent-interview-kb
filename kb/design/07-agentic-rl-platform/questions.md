# 追问题：Agentic RL 训练平台

> 对应设计题：[README.md](README.md)。先白板作答整题，再用这些追问自测。

## design-rlplat-001 估算：8B 模型（36 层、8 个 KV 头、head_dim 128，BF16 权重 16.4 GB）在 H100（3.35 TB/s）上做多轮 rollout，单卡并发 16 条、平均上下文 4,600 token、每条轨迹 1,800 个策略 token 加 5 次 1 秒的工具调用，一条轨迹要多久
- level: 2
- tags: [training, inference]

**一句话答案**：KV 共约 10.9 GB，每步读 27.3 GB 约 8.1 ms，单序列上限约 123 token/s；按 50% 效率约 60 token/s，解码 30 秒加工具 5 秒，约 35 秒。

**要点**：
- 每 token KV = 2 × 36 × 8 × 128 × 2 B = 147,456 B。
- 16 × 4,600 × 147,456 B ≈ 10.9 GB；(16.4 + 10.9) GB / 3.35 TB/s ≈ 8.1 ms。
- 50% 效率是假设，要说明这是带宽下界推出的上限再打折。
- 结论：rollout 一步约 35 秒加长尾，和训练同一量级，是步时的主要部分。

**追问链**：
1. 把单卡并发加到 64 条会怎样？→ KV 约 43 GB，每步约 17.9 ms；单卡总吞吐上升，单条轨迹变慢，长尾更长。按目标是吞吐还是步时来选。
2. 多轮之间不复用前缀，Prefill 多算多少？→ 每条要算 2,000 + 3,000 + … + 7,000 = 27,000 token，复用时只算 5,500 token，约 5 倍。

**易错点**：
- 用带 sparsity 的峰值算力估解码速度。解码先看带宽。
- 忘了工具等待时间，或忘了 KV 也要每步读。

## design-rlplat-002 Agentic RL 平台什么时候该从共卡同步升级到异步 rollout，代价是什么
- level: 3
- tags: [training, inference]

**一句话答案**：量出 rollout 长尾让 GPU 大量空转、或卡数大且工具等待长时再升级；先上部分 rollout，再考虑完全异步。代价是样本来自旧策略，要限滞后、修正目标并监控 clip 比例和 KL。

**要点**：
- 同步：一批等最慢的轨迹，简单、严格 on-policy。
- 部分 rollout（Kimi k1.5）：每轮给 token 预算，没写完的存缓冲下轮接着写；同一轨迹混多个策略版本。
- 完全异步（AReaL）：采样和训练解耦，控制滞后有界，用针对过时样本修改过的 PPO 变体。
- HybridFlow 观察到 16 到 64 卡上全部共卡最好，小规模先不拆。

**追问链**：
1. 怎么判断滞后是否太大？→ 每条样本记生成时的策略版本；看 clip 比例和 KL，滞后越多比率越偏离 1，被 clip 的 token 越多。
2. 异步下权重怎么同步？→ 训练端每步或每几步推送；推理端可短暂暂停或双缓冲，滞后上限决定同步频率。

**易错点**：
- 一上来就设计完全异步，说不出它带来的 off-policy 问题。
- 把工具超时造成的截断当成策略失败给负奖励。

## design-rlplat-003 Agentic RL 需要上千个并发沙箱环境，怎么设计环境层
- level: 2
- tags: [training]

**一句话答案**：环境独立成 CPU 集群；一类环境一个共享镜像，任务是不同初始状态；预热沙箱池、结束后回滚快照复用；同组轨迹同一快照出发；环境故障丢弃重跑，判定材料只读。

**要点**：
- 资源量级：1,024 个沙箱 × 0.5 vCPU、1 GB（假设）≈ 512 vCPU、1 TB 内存；工具调用约 150 次/秒。
- SWE-smith 按仓库共享镜像，5 万个任务的环境约 295 GB；每任务一个镜像要 50 到 150 TB。
- 可验证、可复现、可重置是三个硬要求，见 training/06。
- 训练用模拟服务，评测保留一份真实工具集合检查迁移。

**追问链**：
1. 为什么一组 G 条要从同一状态出发？→ 组内优势是比较同一任务下的轨迹，起点不同，奖励差异里混进了环境差异。
2. 环境故障率升高会怎样？→ 若当成负奖励，策略会学着回避某些工具；应计为环境故障并报警，轨迹丢弃或重跑。

**易错点**：
- 把环境和训练放在同一批节点上，抢 CPU 和内存。
- 只说“用 Docker”，没讲重置、复用和故障区分。

## design-rlplat-004 多轮 Agent RL 训练中奖励先涨后掉，平台层面要提供哪些监控来排查
- level: 2
- tags: [training]

**一句话答案**：按奖励分项、长度和轮数、熵、clip 比例、组内奖励方差、环境故障率分开画；再抽检高分轨迹，并核对工具结果 mask 和 token 边界是否对齐。

**要点**：
- 奖励方差骤降加梯度尖峰，对应 RAGEN 说的 Echo Trap。
- 某一分项涨得异常快、调用次数暴涨，多半是 reward hacking。
- mask 要在 token 序列上做；旧策略、新策略 log 概率和 KL 用同一个 mask。
- 环境故障率上升会让奖励下跌，要先排除。

**追问链**：
1. 确认是 reward hacking 后怎么处理？→ 修奖励，用对抗样本回归测试；回到 hack 出现前的检查点重训，只加大 KL 不解决漏洞。
2. 熵持续下降怎么办？→ 考虑 DAPO 的 Clip-Higher，提高上 clip 边界；同时检查任务难度分布是否太窄。

**易错点**：
- 只看总奖励一条曲线。
- 不区分环境故障和策略退化。
