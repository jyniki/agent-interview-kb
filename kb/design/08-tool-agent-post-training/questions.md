# 追问题：让开源模型学会调用企业内部工具

> 对应设计题：[README.md](README.md)。先白板作答整题，再用这些追问自测。

## design-tooltrain-001 让开源模型学会调用内部 API 时，什么时候 SFT 就够，什么时候要加 DPO 或 RL
- level: 3
- tags: [training, evaluation]

**一句话答案**：格式错、参数错、不会固定流程，SFT 示范就够；会做但常选错（该追问时编参数、该拒绝时硬调用）加 DPO；多步任务成功率低且终态可程序判定，上 RL。先看评测现象再决定。

**要点**：
- 训练前先做不训练的基线：改工具描述、按场景路由、约束解码。
- DPO 的偏好对来自失败轨迹（rejected）和修正轨迹（chosen），参考模型用 SFT 模型。
- RL 奖励参考 ToolRL：格式加正确性，正确性按工具名、参数名、参数值分别比对，权重大于格式。
- 0/N 的题很多时，RL 采不到正样本，要先补教师数据或换基座。

**追问链**：
1. 为什么多步任务更适合 RL 而不是 DPO？→ 多步的轨迹空间大，离线偏好对覆盖不了；DPO 只在数据出现过的回答上调概率，策略变了信号就偏。
2. 上 RL 前要准备什么？→ 可并发重置的预发或模拟环境、程序判定的终态评分器、对奖励做对抗测试，以及 SFT 冷启动模型。

**易错点**：
- 默认“RL 一定比 SFT 好”，说不出评测上的依据。
- 跳过基线，直接训练。

## design-tooltrain-002 估算：8B 模型全参 SFT，3 万条工具调用样本、每条 3,000 token、训 3 个 epoch，H100 稠密 BF16 约 990 TFLOPS、MFU 按 40% 算，要多少算力和时间
- level: 2
- tags: [training]

**一句话答案**：2.7 亿 token × 6 × 8.2e9 ≈ 1.3e19 FLOPs；每卡约 396 TFLOPS，约 9.3 卡·时，8 卡约 1.2 小时。训练很便宜，成本在造数据和评测。

**要点**：
- 3 万 × 3,000 × 3 = 2.7 亿 token。
- 训练每 token 约 6N FLOPs（Kaplan 等第 2.1 节，非嵌入口径）。
- 模型状态 16Ψ ≈ 131 GB，ZeRO-3 切到 8 卡每卡约 16.4 GB；LoRA 下冻结基座约 2Ψ ≈ 16.4 GB。
- 教师通过率 40% 时，要生成约 7.5 万条候选。

**追问链**：
1. 为什么说成本不在训练？→ 一次 SFT 一两个小时；造数据要教师推理、真实执行和人工抽检，评测每次都要在预发环境跑全量，这些花的时间和人力多得多。
2. 改用 LoRA 能省多少？→ 省的是梯度和优化器状态，激活和计算量基本不变，训练时间不会少很多。

**易错点**：
- 用带 sparsity 的 1,979 TFLOPS 算，高估一倍。
- 以为 LoRA 也能把计算量降到几分之一。

## design-tooltrain-003 合成工具调用训练数据时，怎么保证数据是对的
- level: 2
- tags: [training]

**一句话答案**：任务覆盖单步、多步、无需调用、缺参数、报错恢复；轨迹过格式、执行、语义三层校验，格式和执行用程序，语义用评委加人工抽检；按 API × 类型定配额、去重，样本带 API 版本。

**要点**：
- APIGen 的三层：格式检查、真实执行、语义验证。
- ToolACE 的规则层查 schema 和调用合法性，模型层拆成子问题查幻觉参数、一致性和工具结果；整条样本一次判效果差。
- 写操作在预发环境执行后回滚。
- 工具结果不计 loss；混入通用数据防止通用能力退化。

**追问链**：
1. 评委过滤有什么风险？→ 带入评委偏好；要先用人工标注样本测它的放过率和误杀率。
2. API 改了字段，旧数据怎么办？→ 按样本里记录的 API 版本找出受影响的样本，重新生成或删除。

**易错点**：
- 只做格式校验，不真跑。
- 只合成“一路顺利”的样本，没有无需调用和缺参数的样本。

## design-tooltrain-004 内部工具调用模型怎么评测，才能证明可以上线
- level: 2
- tags: [evaluation]

**一句话答案**：按 API 和任务类型分层：单步匹配、执行成功、多步终态与 pass^k、无需调用的误调用率、缺参数的追问率、写操作错误数（目标 0）、留出 API 泛化、通用能力；再经影子和灰度验证。

**要点**：
- 单步可参照 BFCL 的 AST 检查；无需调用参照它的 relevance detection。
- 留出几个 API 不进训练，检验对新 API 的泛化。
- 评测集和训练数据按来源隔离、去污染。
- 影子模式只生成不执行，和现有流程比对；先灰度只读 API。

**追问链**：
1. 为什么要单独报留出 API？→ API 会持续变化和新增；训练 API 上的分数可能来自记忆，留出层才反映读定义再调用的能力。
2. 线上失败怎么回流？→ 先归因：工具描述问题改描述，模型行为问题才构造同类新样本进训练，原题进评测集。

**易错点**：
- 只报一个总正确率。
- 不测通用能力退化。

## design-tooltrain-005 日均 2 万任务、一次转人工 1.5 美元时，8B 工具调用模型提升多少个百分点才值得训练
- level: 3
- tags: [training, evaluation]

**一句话答案**：先测少样本基线再算盈亏：一次性 2.2 万美元摊到日均 2 万任务，提升 5 个点约 15 天回本；日均不到 1,500 任务时，同样的提升回不了本，不该训。

**要点**：
- 盈亏点 =（一次性成本 / 12 + 月维护）/（Δs × 每次转人工省下的钱 × 30 天）。
- 少样本收益饱和：3 个示例换 9.8 个点，第 8 到 20 个只换 0.6 个点，代价是每次调用多 220 毫秒 prefill。
- 推理成本可忽略（每任务约 0.0008 美元），所以“省推理钱”不是训练的理由，成功率才是。
- 失败要按类型分：格式、选错工具、参数值、该追问却编造，前两类靠描述和约束解码解决。

**追问链**：
1. 怎么估 Δs？→ 用 400 题配对跑新老两版，看不一致题的数量；半宽 3.4 个点时，小于这个幅度的提升测不出来。
2. 日均任务量低怎么办？→ 扩大小模型覆盖范围或接受转人工；也可以只做描述改写这类零训练投入的优化。

**易错点**：
- 用“训练能让模型更强”当理由，不落到金额和任务量。
- 用峰值任务量算盈亏，应该用日均。

## design-tooltrain-006 教师每次调用出错概率 6%、任务平均 2.4 次调用时，SFT 的成功率天花板是多少，负样本该怎么配
- level: 3
- tags: [training]

**一句话答案**：天花板是 (1−e)^k，(1−0.06)^2.4≈86%；纠错样本按 1−(1−e)^k≈14% 配，错误那次调用 mask 掉，只训纠错动作。

**要点**：
- 模仿只能到示范的水平：教师每次错 10% 时上界 77.7%，压到 2% 才到 95.3%。
- 负样本比例贴近线上出现率：低于它模型没见过报错后的状态，远高于它模型会学“先犯错再纠正”。
- 工具结果一律不计 loss；一条样本里只有约 7% 的 token 计 loss，放开工具结果会升到 30%。
- 环境类错误（超时、5xx）调用本身是对的，保留并计 loss；模型自己的错才 mask。

**追问链**：
1. e 怎么测？→ 抽 500 条人工标，和评委判定做混淆矩阵，得到评委的放过率和误杀率再反推。
2. 教师错误率高怎么办？→ 换教师，或把长任务拆短：k 变小，(1−e)^k 会上升。

**易错点**：
- 认为数据越多越好，不看天花板。
- 把错误调用也计 loss，模型学会先错后改。

## design-tooltrain-007 内部 API 每月有几个改字段，模型失配后该重训还是只改工具描述
- level: 3
- tags: [training, harness]

**一句话答案**：失配率约 m·(1−r)；靠版本化描述、服务端别名和可操作报错把 r 提到 0.9，一年重训一次就够，成本比每季重训低一半。

**要点**：
- m 是凭记忆不看定义的比例，r 是改描述后救回的比例，两者都从“同批请求在新旧定义下重跑”实测。
- 语义变了（含义、取值范围）别名救不了，r 掉到 0.5 以下，这时才必须重训。
- 新增一整类 API 时看留出 API 层的评测，掉超过 5 个点再补数据。
- 训练时扰动定义（换措辞、调参数顺序）能提高鲁棒性，但会降低对真实定义的熟练度。

**追问链**：
1. 为什么不是改了就重训？→ 一次重训约 1.9 万美元，而一个改动窗口的损失约 3,500 美元；r 高时改描述更便宜。
2. 旧字段名要保留多久？→ 一个弃用期，期间服务端别名映射；期限到了连同训练数据里的旧样本一起清理。

**易错点**：
- 认为模型会“自己适应”新定义，没有别名和版本化就指望它读对。
- 只改描述不看留出 API 层的评测，改完以为没事。

## design-tooltrain-008 写操作要证明失败率低于 0.2%，评测集至少要多少道题且全部通过
- level: 2
- tags: [evaluation]

**一句话答案**：三法则：n 题全过只能说失败率低于约 3/n。300 题对应 1%，证到 0.2% 要约 1,500 题全过；写操作门禁题数由门禁定，不由线上占比定。

**要点**：
- 0/300 的 95% 上界是 1 − 0.05^(1/300) ≈ 1.0%。
- 写操作还要覆盖边界：金额上限、重复提交、他人订单、并发修改。
- 1% 灰度每天只有约 33 次写操作，发现一次错误写要等好几天，所以写操作按 10%/30%/100% 阶梯放量。
- 高风险写操作始终服务端二次校验加用户确认，模型不能绕过。

**追问链**：
1. 为什么不能靠灰度兜底？→ 小流量下错误率的分辨率太低，等统计显著时已经错了上百次。
2. 题数不够时怎么补？→ 用配对比较加分层加权，把高风险层过采样，再按线上比例加权汇总。

**易错点**：
- 用 30 题全过就说“没问题”。
- 只测正常写操作，不测越权、重复和边界金额。
