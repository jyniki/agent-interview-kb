# 追问题：仓库级 Coding Agent

> 对应设计题：[README.md](README.md)。先白板作答整题，再用这些追问自测。

## design-coding-001 仓库级 Coding Agent 怎么防止模型没验证就宣布任务完成
- level: 2
- tags: [harness, evaluation]

**一句话答案**：由 Harness 检查完成证据：先有失败的复现测试，改完后它变通过、相关测试通过、有 diff；不满足就不让结束。再用独立上下文审查 diff，PR 里附上实际命令和输出。

**要点**：
- 修 bug 先复现：写或找到在原代码上失败的测试，复现不了要在 PR 里写明。
- 循环里跑相关测试，提 PR 前跑受影响模块的全部测试，全量交给 CI。
- 测试输出只回写失败用例和几行错误，完整输出存日志。
- 独立审查只给需求和 diff，只报影响正确性的问题。
- 代价：复现和审查多花步数和成本；相关测试会漏远处的回归，要靠 CI 兜底。

**追问链**：
1. Agent 把已有测试改了让它通过怎么办？→ 测试改动单独标出并审查；评测用 Agent 看不到的隐藏测试；必要时测试目录只读、只允许新增测试。
2. 为什么审查要用新上下文？→ 同一个上下文容易被自己的推理说服；新上下文只对照需求看 diff，更容易发现漏改和偏题。

**易错点**：
- 只在提示里写“请确保测试通过”。这是请求，不是检查，模型照样会跳过。

## design-coding-002 Coding Agent 要在沙箱里执行任意命令，怎么设计隔离和凭据
- level: 2
- tags: [harness]

**一句话答案**：每个任务一个一次性容器，文件和网络都隔离，默认断网只放行包镜像；沙箱里不放长期凭据，推送经 git 代理用受限临时凭据，代理只允许推到任务分支。

**要点**：
- 文件隔离和网络隔离缺一不可：没有网络隔离，读到的密钥能发出去；没有文件隔离，能改配置绕过代理。
- 容器用完销毁，不回池复用；冷启动用预热池和依赖缓存掩盖。
- 高危动作单独拦截：删远程分支、改 CI 配置、用偶然发现的凭据。
- issue 文本、依赖说明是不可信输入，读过后收紧对外动作的权限。
- 细节见 harness/03。

**追问链**：
1. 断网后 Agent 要查第三方库文档怎么办？→ 常用文档预先放进镜像或内部代理；新域名要人批准后加进白名单，并记录出口流量。
2. 为什么不让 Agent 用开发者本人的 token？→ token 进沙箱，注入只要让模型读环境变量就能拿到；权限范围也远大于这次任务需要的。

**易错点**：
- 认为“用了 Docker 就安全”。容器只管逃逸，管不住沙箱内合法能做的事，比如用凭据外传。

## design-coding-003 估算：1,500 名开发者、日活三成、每人每天 2 个任务、每任务约 20 分钟，高峰按平均的 2 倍、工作时间 10 小时，需要多少并发沙箱
- level: 1
- tags: [harness]

**一句话答案**：每天约 900 个任务，平均每小时 90 个，高峰 180 个；每个占 20 分钟，同时运行约 60 个沙箱，每天约 300 沙箱小时。

**要点**：
- 1,500 × 30% × 2 = 900 个/天；900 / 10 = 90 个/小时；高峰 × 2 = 180 个/小时。
- 并发 ≈ 到达率 × 时长 = 180 × 20 / 60 = 60。
- 沙箱时长 = 900 × 20 / 60 = 300 小时/天。
- 预热池按高峰并发留余量，空闲时缩容。

**追问链**：
1. 每任务平均 40 步、每步输入 3 万 token，每天输入多少？→ 900 × 40 × 3 万 ≈ 10.8 亿 token；稳定前缀命中缓存后，未命中部分小得多，所以缓存命中率是主要的成本杠杆。
2. 全量测试 15 分钟，循环里跑 3 次会怎样？→ 光测试就 45 分钟，超过 20 分钟的预算，所以循环里只跑相关测试。

**易错点**：
- 用日均算并发，忘了高峰；或者把每天任务数直接当并发数。

## design-coding-004 怎么为公司自己的大仓库建 Coding Agent 的离线评测集，并用它决定是否换模型
- level: 3
- tags: [evaluation, harness]

**一句话答案**：从仓库历史挑修复前测试失败、修复后通过的提交，issue 作题面，修复里的测试作隐藏测试，按 FAIL_TO_PASS 和 PASS_TO_PASS 判分；剔除坏题，分层报分，配对比较新旧版本。

**要点**：
- 自建题没公开过，污染风险比公开 Benchmark 小。
- 坏题标准：题面推不出测试检查的行为，或测试要求题面没提的实现细节。
- 按任务类型、改动规模、模块分层；每题跑多次，报 pass^k 和每解决一题的成本。
- 换模型时同一批题配对比较，看翻转题，不只看总分。
- 线上补充 PR 采纳率、审查者改动量、合并后回退率。

**追问链**：
1. 历史提交的测试不全，错补丁也能过怎么办？→ 人工抽查过关的补丁；为高价值题补测试；线上用回退率兜底，离线分只当上限参考。
2. 新模型解决率高但成本翻倍，换不换？→ 看“每解决一题的成本”和延迟是否在预算内；可以按任务难度路由，只让难题走新模型。

**易错点**：
- 直接拿公开 Benchmark 分数做决定。公开题可能被记住，仓库分布也和自己的不同。
