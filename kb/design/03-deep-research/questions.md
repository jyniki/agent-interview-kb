# 追问题：Deep Research 研究助手

> 对应设计题：[README.md](README.md)。先白板作答整题，再用这些追问自测。

## design-research-001 Deep Research 助手应该在什么时候停止搜索
- level: 2
- tags: [harness]

**一句话答案**：同时设四类条件：token、调用次数、时间的预算上限；计划里每个子问题都有可靠来源；连续几轮没有新信息；来源冲突时查过权威来源仍矛盾就停，并在报告里写出分歧。

**要点**：
- 覆盖和收益递减尽量用代码判：外部维护“子问题 → 证据”表，检查空格子和每轮新增条数。
- 不只靠模型自己说“够了”，模型容易过早结束或无限追查。
- 预算触发时交半成品，报告写明哪些子问题没查到。
- 计划和阶段结论存在上下文外，压缩或截断后能读回。

**追问链**：
1. 怎么判断“没有新信息”？→ 对新抓到的事实做归一化后和已有证据比对，按新增的不同事实数和新来源数计；连续两三轮低于阈值就算收益递减。
2. 预算按什么定？→ 按问题复杂度分档：简单事实题少量调用，比较题和开放研究题逐级放宽；档位在计划阶段决定，并在评测里看每档的质量和成本拐点。

**易错点**：
- 只说“设个最大步数”。只有预算没有覆盖条件，简单题浪费，难题被截断，也不知道漏了什么。

## design-research-002 Deep Research 什么时候该用并行子 Agent，什么时候不该用
- level: 2
- tags: [harness, evaluation]

**一句话答案**：子问题依赖弱、能独立回答、资料多到一个上下文装不下、问题价值够高时才拆；子问题强依赖或要求前后决策一致时用单 Agent。拆了要和同等 token 预算的单 Agent 对照。

**要点**：
- 收益：并行缩短等待时间；独立上下文能读更多资料。
- 代价：token 成倍增加；交接丢信息；一个慢的子 Agent 卡住整批。
- 交接写清目标、输出格式、工具和来源范围、什么时候停；返回结论、证据引用、未解决部分。
- 长笔记写外部存储，只交回引用，减少层层转述走样。
- 派几个子 Agent 应随问题复杂度变化，不是固定配置。

**追问链**：
1. 两个子 Agent 查了重复的内容怎么办？→ 交接时按维度切开范围并写明边界；主 Agent 汇总时统计重复查询率，把它作为过程指标。
2. 怎么证明多 Agent 的收益来自结构？→ 加一组同等 token 预算的单 Agent 基线，同时比质量、成本和时长；token 用量本身就和表现强相关。

**易错点**：
- 一上来就画十个子 Agent。没有说清拆分依据和成本，面试官会追问为什么不用单 Agent。

## design-research-003 怎么校验研究报告里的引用确实支持对应的结论
- level: 2
- tags: [harness, evaluation]

**一句话答案**：每个来源存快照并带稳定 ID，报告每句话标 ID；先比对数字、日期、专名是否在被引段落里，再用小模型判断原文是否支持这句话；对不上的删掉或改成“未找到依据”。

**要点**：
- 快照带 URL 和抓取时间，网页变了也能复核。
- 两层校验：便宜的字符串比对挡掉大部分，模型判定只处理剩下的。
- 关键结论只有一个来源时标“单一来源”；来源冲突单列“分歧”一节。
- 来源质量过滤：优先一手数据和权威来源，低质量站点降权。
- 评测时抽出“结论-来源”对算引用准确率，DeepResearch Bench 的 FACT 框架是同一思路。

**追问链**：
1. 校验模型自己判错怎么办？→ 用人工标注的样本测它的放过率和误杀率，按答错代价调阈值，定期复测。
2. 引用全对，报告就可信吗？→ 不一定。引用对只说明每句话有出处，还要看是否覆盖了关键事实、来源是否权威、有没有漏掉相反证据。

**易错点**：
- 只要求模型“附上出处”。附的出处本身可能是编的，或者并不支持那句话。

## design-research-004 估算：每天 2,000 份报告，每份派 5 个子 Agent、各 15 次工具调用，子 Agent 平均上下文 2 万 token，主 Agent 和引用阶段另需 20 万 token，单次工具调用 3 秒，每天输入多少 token，并行能省多少时间
- level: 1
- tags: [harness]

**一句话答案**：每个子 Agent 累计输入约 30 万，单份约 170 万，每天约 34 亿输入 token；工具等待串行约 225 秒，并行后约 45 秒。并行省时间，不省 token。

**要点**：
- 子 Agent：15 步 × 平均 2 万 = 30 万；5 个共 150 万；加 20 万得 170 万。
- 每天：2,000 × 170 万 = 34 亿 token。
- 工具调用：每份 75 次，每天 15 万次。
- 时间：串行 75 × 3 = 225 秒；并行时每个子 Agent 15 × 3 = 45 秒。

**追问链**：
1. 成本降一半先动哪里？→ 工具结果返回后立即裁剪、旧结果折叠，压低每步上下文；简单问题少派或不派子 Agent；稳定前缀用缓存。
2. 为什么累计输入远大于读进的资料量？→ 每一步都要把历史重新送一次，累计输入随步数近似平方增长。

**易错点**：
- 只算“读了多少网页”，忘了每步重发历史的累计输入。

## design-research-005 开放式研究报告没有标准答案，怎么搭评测集和判分
- level: 3
- tags: [evaluation]

**一句话答案**：分两类题：难找好验证的短答案题测检索坚持度；开放报告题每题写要点清单，判关键事实覆盖。再抽结论-来源对算引用准确率，评委按 rubric 逐项判质量并先与人工校准，同时报成本。

**要点**：
- 题从真实请求分层采样，起步约 20 题即可，早期改动效果大。
- 要点清单由领域人员写，只列必须覆盖的论点和事实，不规定写法。
- 评委逐项判：完整、准确、结构、是否写出分歧；能代码判的（数字、引用存在性）不用评委。
- 评委先和人工算一致率和 kappa，再用来报分。
- 评结果不评路径；过程指标（重复查询、超时、预算截断）用来定位问题。

**追问链**：
1. 网页会变，评测怎么可复现？→ 评测时用固定的网页快照或缓存的搜索结果；另留一份接真实搜索的集合检查迁移。
2. 评委偏爱更长的报告怎么办？→ rubric 写明长度不加分，按要点覆盖判；校准集里放“短而全”和“长而空”的对照样本。

**易错点**：
- 只让评委给整份报告打一个 1-10 分。分数没法解释，也没法和人工逐项对齐。

## design-research-006 估算：每天 2,000 个任务、平均 12 分钟、80% 落在 10 小时工作时段、峰均比 4、每任务 3–5 个并行子 Agent（均值 5）、每个子 Agent 15 次工具调用、每次模型调用 12 秒、工具 4 秒，在途任务、并发子 Agent、模型配额各是多少
- level: 2
- tags: [harness, inference]

**一句话答案**：峰值 640 任务/小时，在途约 128 个任务（Little 定律），并发子 Agent 均值 213、上界 640，峰值约 970 RPM、在途模型调用 194；140 个槽位排队约 12 秒。

**要点**：
- 峰值到达率 = 2,000 × 0.8 / 10 / 3,600 × 4 ≈ 0.178 任务/秒；在途 L = λW = 0.178 × 720 ≈ 128，p99 约 154。
- 每任务调用 = 5 × 15 + 6 + 10 = 91 次；峰值调用率 0.178 × 91 ≈ 16.2 次/秒，约 970 RPM；在途调用 16.2 × 12 ≈ 194。
- 并发子 Agent = λ × 每任务子 Agent 墙钟秒数 = 0.178 × 1,200 ≈ 213；上界是全部在途任务同时派满，128 × 5 = 640。
- 排队用多槽位模型：140 个槽位、ρ = 0.914，M/M/c 平均排队 12.7 秒，M/D/c 模拟约 7 秒；150 个槽位降到 1.2 秒。
- 按天平均算只有 0.023 任务/秒、17 个在途，高峰时差 8 倍，配额按它买一定不够。

**追问链**：
1. 为什么不能按最坏情况配 640 个并发子 Agent？→ 最坏情况只在所有在途任务同时派子 Agent 时出现，概率极低；按均值配池子、用队列吸收突发更便宜，代价是并发高峰时排队。
2. 排队模型怎么选？→ 单队列 M/M/1 在 ρ = 0.9 时给 3,240 秒，多槽位 M/M/c 只给 12.7 秒，差两个数量级；服务时间固定时用 M/D/c 模拟更准。
3. 90 万 RPM 配额够不够？→ 算的是峰值 970 RPM 和峰值每分钟输入；还要按缓存命中率算计入 ITPM 的输入，见第 3.2 节。

**易错点**：
- 把并发子 Agent 数和模型在途调用数混为一谈。子 Agent 有工具耗时，不占模型；两者接近但配额要分别买。
- 只报在途均值 128，不说 p99 154，也不说 640 的上界，容量就配不出余量。

## design-research-007 估算：Deep Research 子 Agent 线性，主 Agent 每轮读入全部子 Agent 摘要、起始 6,000 token、每轮新增 4 份摘要各 1,200 token 加 600 新笔记，跑 5/10/20 轮时单任务多少钱（示例单价输入 $3、输出 $15 每百万 token，缓存命中 0.8）
- level: 2
- tags: [harness]

**一句话答案**：5/10/20 轮分别约 $6.0/$12.3/$26.2。子 Agent 线性，主 Agent 每轮重读全部摘要，输入按轮次二次增长，20 轮时主 Agent 占 16%。

**要点**：
- 第 r 轮主输入 = 6,000 + r × (4 × 1,200 + 600) = 6,000 + 5,400r；前 R 轮合计 R×6,000 + 5,400×R(R−1)/2。
- 5/10/20 轮主 Agent 原始输入 84,000 / 303,000 / 1,146,000；轮次 4 倍，输入 13.6 倍。
- 子 Agent 每轮约 29 万计费 token，随轮次线性；总额 = R × 29 万 + 主 Agent 二次项。
- 单任务金额含输出：$5.99 / $12.33 / $26.24；20 轮的第 1 轮主输入是第 20 轮的 1/18。
- 缓存把输入压到 1/4；不开缓存时 5 轮任务从 $6.0 涨到约 $11。

**追问链**：
1. 为什么成本超线性？→ 每轮都要重读历史，第 r 轮输入随 r 线性增长，合计是二次的。见 core/08 第 3.1 节。
2. 长尾任务怎么定价？→ 按轮数分档定价，并用硬预算截断；10% 的任务跑到 20 轮就能吃掉接近 40% 的成本。
3. 先压哪一块？→ 主 Agent 的摘要长度（每份 1,200 token 已是上限）和轮数上限；子 Agent 的输入靠裁剪工具结果。

**易错点**：
- 只算子 Agent 的 token，忘了主 Agent 每轮重读摘要的二次项，5 轮时低估 5%、20 轮时低估 16%。
- 用平均轮数报成本，不说 5 到 20 轮差 4.4 倍。

## design-research-008 并行派 5 个子 Agent、单个耗时中位 90 秒对数标准差 0.45，一批的期望耗时是多少，截止时间设 180 秒会丢多少结果
- level: 2
- tags: [harness, evaluation]

**一句话答案**：E[max]≈μ·H_N；长尾下 5 个并行平均等 1.6 个。设截止 D=180 秒，平均完成 4.7/5，缺项按子问题权重决定重派还是注明缺失。

**要点**：
- 独立同分布时 E[max] = μ·H_N，H_5 ≈ 2.28、H_10 ≈ 2.93；5 加到 10 只多 28%。
- 长尾（对数正态）下 max 增长更慢：单个均值 100 秒，5 个取最慢 159 秒，10 个 186 秒。
- 截止 D：完成个数期望 = N·P(T ≤ D)。D=150/180/240 秒分别平均完成 4.4/4.7/4.9 个，五个全完成概率 0.50/0.73/0.93。
- D=180 秒只比等到全完成的期望 159 秒多 21 秒，就多拿 0.7 个结果。
- 部分成功能不能接受取决于缺的是谁：缺权重 0.1 的方向覆盖仍 90%，缺权重 0.4 的只剩 60%，要重派。

**追问链**：
1. 为什么不用平均耗时算批次延迟？→ 同步等一批是 max 不是 mean；5 个并行平均等 1.6 个，子 Agent 越多，被最慢者拖住的比例越大。
2. 超时后重派还是标缺失？→ 看重派成本与缺口权重：缺口在高权重子问题上且预算够才重派，否则在报告里注明。
3. 分两批（3+2）比一批 5 个慢多少？→ 两批串行约 597 秒，一批并行约 330 秒；分批是为了用第一批结果规划第二批，不是为速度。

**易错点**：
- 用均值报批次延迟，低估 60%。
- 只说“设个超时”，不说超时后拿什么、缺口怎么处理。
